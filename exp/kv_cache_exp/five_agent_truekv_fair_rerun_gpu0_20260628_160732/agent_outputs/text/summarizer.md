# Skyforge Courier 长规则设计文档

## 1. 游戏概念

《Skyforge Courier》是一款单人 2D 俯视角轻量小游戏。玩家扮演云端工坊的快递员，在漂浮岛屿之间运送能量包。游戏目标不是击败敌人，而是在有限时间内规划路线、管理体力、躲避风暴、完成订单并逐步升级飞行装备。整个设计强调短局、清晰反馈、可扩展系统和低实现成本。

游戏画面采用网格地图。每个关卡由 12x12 到 20x20 的 tile 组成。tile 可以是空中航道、浮岛、云墙、风道、雷暴、补给站、客户点、工坊起点、传送门或临时障碍。玩家每次移动一格，也可以通过技能移动多格。所有系统都应该优先支持键盘方向键和 WASD，同时保留触屏方向按钮的扩展可能。

## 2. 核心循环

基础循环如下：

1. 读取当天地图和订单。
2. 玩家观察订单位置、风向、雷暴和补给站。
3. 玩家规划路线，从工坊起点出发。
4. 每移动一步消耗时间和体力。
5. 到达客户点后自动交付匹配包裹。
6. 交付后获得金币、声望、连送倍率和可能的道具。
7. 玩家选择继续送下一个订单，或返回工坊结束配送日。
8. 配送日结束后进入结算界面。
9. 结算界面展示送达数、迟到数、金币、声望、路线效率、风险事件和升级建议。
10. 玩家使用奖励升级装备或解锁新区域。

该循环必须始终保持简单：每轮新增功能都不能破坏移动、交付、结算这三件核心事情。新增系统必须能被关闭或用默认值运行，方便渐进实现。

## 3. 地图与 tile 规则

地图使用二维数组表示，每个 tile 有 `type` 和可选属性。基础 tile 类型如下：

- `workshop`：玩家出生点和可返回结算点。
- `air`：普通可通行航道。
- `island`：可停靠陆地，可作为客户点或补给站承载 tile。
- `cloud_wall`：不可通行障碍。
- `wind_lane`：风道。进入后会沿风向额外移动一格，仍消耗一次时间，但不额外消耗体力。
- `storm`：雷暴格。进入后损失护盾或体力，并有小概率打乱包裹。
- `supply`：补给站。可以恢复体力、修复护盾或刷新一个普通道具。
- `customer`：客户点。到达后自动检查可交付订单。
- `portal`：传送门。成对出现，进入后传送到另一端。
- `blocked`：临时封锁。由事件生成，可在若干回合后消失。

地图生成要遵守以下基本约束：

- `workshop` 必须存在且只有一个。
- 每个客户点必须从 `workshop` 可达。
- `cloud_wall` 不能完全封死核心订单路线。
- `storm` 不能直接包围 `workshop`。
- `supply` 应至少有一个位于中等距离区域。
- `wind_lane` 应该形成可利用路线，而不是纯惩罚。
- 如果启用 `portal`，必须成对出现。

## 4. 玩家属性

玩家基础属性：

- `time_left`：剩余时间。每局初始 180 秒或 120 回合，具体实现可选秒制或回合制。
- `stamina`：体力。普通移动消耗 1，风道移动不额外消耗，冲刺消耗 3。
- `shield`：护盾。进入雷暴优先扣护盾。
- `cargo_slots`：载货格。基础为 2，可以升级到 4。
- `speed_level`：速度等级，影响冲刺冷却或特殊移动。
- `reputation`：声望，影响高级订单出现概率。
- `coins`：金币，用于局后升级。

失败条件：

- 时间归零且没有完成任何核心订单。
- 玩家体力降为 0 且无法使用补给或返回工坊。
- 特殊挑战模式中，核心包裹全部损坏。

普通模式中，即使部分订单失败，也不应立即结束游戏。游戏要鼓励风险选择，而不是让玩家因为一次错误直接崩溃。

## 5. 订单系统

订单字段：

- `order_id`：唯一编号。
- `customer_id`：目标客户点。
- `package_type`：包裹类型。
- `deadline`：截止时间或截止回合。
- `reward_coins`：金币奖励。
- `reward_rep`：声望奖励。
- `priority`：`core`、`normal`、`bonus`。
- `fragility`：易损等级，影响雷暴损坏概率。
- `weight`：重量，影响体力消耗或 cargo slot 占用。
- `tags`：可扩展标签，比如 `cold_chain`、`urgent`、`hazardous`。

订单类型：

- 核心订单：至少完成一个才算配送日成功。
- 普通订单：提供稳定奖励。
- 奖励订单：高风险高回报，可选。
- 连锁订单：完成后解锁下一站。
- 限时订单：deadline 更短，但奖励更高。
- 脆弱订单：经过雷暴时更容易损坏。

交付规则：

- 到达客户点后，如果存在目标匹配订单，自动交付。
- 若多个订单同一客户，优先交付即将超时的核心订单。
- 迟到订单可以交付，但金币减半，声望不增加。
- 损坏订单可以交付，但只能获得最低安慰奖励。
- 如果 cargo_slots 不足，玩家必须在出发前选择携带哪些订单。

## 6. 移动与体力

基础移动：上下左右移动一格。每步消耗 1 时间和 1 体力。进入 `island` 不额外消耗。进入 `storm` 额外触发风险。进入 `wind_lane` 后自动沿风向推一格，但如果目标是不可通行 tile，则停留在风道格并显示撞风反馈。

冲刺：玩家可以朝方向冲刺两格。冲刺消耗 3 体力，有 3 回合冷却。冲刺不能穿越 `cloud_wall`，可以穿过 `air` 和 `wind_lane`，但经过 `storm` 仍触发一次风险。

等待：玩家可以原地等待一回合，恢复 1 体力，但不能超过体力上限。等待会消耗时间，并可能推进动态天气。

返回工坊：到达 `workshop` 后可以手动结束配送日。若携带未交付包裹，不惩罚，但这些订单视为未完成。

## 7. 天气与风险

天气系统用于制造路线选择。基础天气包括：

- 晴朗：无额外效果。
- 顺风：部分 `wind_lane` 推动距离 +1。
- 乱流：随机若干 `air` tile 临时变成 `blocked`。
- 雷暴：`storm` 范围扩大，进入后扣护盾。
- 浓雾：隐藏远处订单图标，但不隐藏已记住的客户点。

雷暴风险：

- 若 `shield > 0`，进入雷暴扣 1 护盾。
- 若 `shield == 0`，扣 3 体力。
- 脆弱包裹有概率变为 `damaged`。
- 危险品包裹经过雷暴会增加事故计数。

天气必须可预测：UI 至少提前 3 回合提示天气变化。不能突然生成无法避开的失败。

## 8. 道具与升级

局内道具：

- `battery`：恢复 5 体力。
- `shield_cell`：恢复 1 护盾。
- `route_beacon`：显示一条到目标客户点的推荐路线。
- `storm_anchor`：清除半径 1 的雷暴，持续 5 回合。
- `parcel_wrap`：保护一个脆弱包裹免受一次损坏。
- `time_coupon`：延长一个订单 deadline 15 秒或 10 回合。

局后升级：

- 体力上限 +2。
- 护盾上限 +1。
- cargo_slots +1。
- 冲刺冷却 -1。
- 风道掌控：进入 wind_lane 可选择是否接受推动。
- 雷暴抗性：雷暴体力伤害 -1。
- 订单雷达：开局显示奖励订单方向。

升级设计要避免数值膨胀。每个升级都应改变选择空间，而不是单纯提高分数。

## 9. 计分与评价

配送日结算分数由以下部分组成：

- 完成核心订单：每个 +100。
- 完成普通订单：每个 +50。
- 完成奖励订单：每个 +80。
- 准时交付倍率：准时订单越多倍率越高，上限 1.5。
- 路线效率：实际步数接近理论最短路径时加分。
- 风险处理：避开雷暴、使用风道、合理补给会加分。
- 迟到、损坏、事故会扣分。

评价等级：

- S：完成所有核心订单，准时率 >= 90%，无包裹损坏。
- A：完成所有核心订单，准时率 >= 70%。
- B：至少完成一个核心订单，且没有核心包裹损坏。
- C：完成一个核心订单但迟到或损坏较多。
- F：未完成核心订单。

## 10. UI 与反馈

主界面需要显示：

- 地图。
- 玩家当前位置、朝向和状态。
- 剩余时间/回合。
- 体力、护盾、货舱。
- 当前携带订单列表。
- 订单 deadline 和客户方向。
- 天气预报。
- 当前 tile 效果提示。

反馈原则：

- 每次移动都要有明确消耗反馈。
- 交付成功必须弹出奖励摘要。
- 订单即将超时时需要醒目提示。
- 进入雷暴要显示损失原因。
- 使用风道要显示被推动方向。
- 失败时必须说明主要原因。

## 11. 数据结构建议

可以用以下 JSON 风格保存关卡：

```json
{
  "level_id": "day_01",
  "width": 12,
  "height": 12,
  "tiles": [["air", "air"]],
  "workshop": {"x": 1, "y": 1},
  "customers": [{"id": "c01", "x": 8, "y": 3}],
  "orders": [{"order_id": "o01", "customer_id": "c01", "priority": "core"}],
  "weather_script": [{"turn": 20, "weather": "storm"}]
}
```

运行时状态建议分成：

- `GameConfig`：全局规则参数。
- `LevelState`：地图、天气、订单池。
- `PlayerState`：玩家位置、体力、护盾、货舱。
- `OrderState`：订单状态、deadline、损坏状态。
- `RunSummary`：结算统计。

## 12. 实现约束

为了适合作为轻量小游戏，首个版本应满足：

- 可以使用 Python/Pygame、JavaScript/Canvas 或其他轻量框架。
- 不需要联网。
- 不需要复杂物理引擎。
- 地图可以先手写，不要求程序生成。
- 美术可以使用色块和简单图标。
- 所有规则参数应集中配置，方便后续 Agent 修改。
- 每轮新增功能必须明确说明依赖前几轮的哪些系统。
