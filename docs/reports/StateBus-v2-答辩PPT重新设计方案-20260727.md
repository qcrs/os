## 1. 最终主命题

### 1.1 一句话定义

> StateBus v2 是一个面向多 Agent 协作的受控状态交接底座：用类型化合同约束计划，用 StateRef 传递数值状态，用兼容门让验证产物跨任务复用。

### 1.2 两层价值、三个亮点

两层价值：

- **降低协作负担**：少传全文、少让模型重复读取、降低 Token、线路字节和固定实验总耗时。
- **让状态复用可验证**：每次状态晋升都留下授权、消费、效果、验证和释放回执。

三个亮点：

| 亮点 | 解决的问题 | 核心机制 | 主实验锚点 |
| --- | --- | --- | --- |
| 结构化通信 | 全文 handoff 冗长、边界不清、无法提前拒绝 | typed Protobuf、任务合同、Policy、StepGrant | 相同 50 条消息，control bytes `-83.05%` |
| 非文本状态传递 | float32 数值先变文字再恢复，重复序列化且失去对象身份 | StatePool、SemanticStateRef、跨 PID 数值消费 | `9/9` 跨 PID 消费，`9/9` 改变选择 |
| 共享记忆复用 | 相似候选被误当成可复用记忆，旧结果可能污染新任务 | hybrid retrieval、Compatibility Gate、RoleView、effect receipt | actual-use `35%`，不兼容拒绝 `81.25%` |

## 4. 新版总体结构

这不是一套从底层热点逐级推导机制的研究型汇报。主讲始终站在应用系统视角：先让评委知道系统要完成什么任务、传统交接为何妨碍任务，再解释三个机制怎样改善同一条任务链，最后用实验回答改善是否真实发生。

四条应用叙事约束：

1. 真实任务不是实验前的装饰案例，而是全稿的上下文；后续机制页都要能指回该任务中的具体交接对象。
2. 不先介绍类名、协议和数据结构，再要求评委自行推断价值；每个机制必须先出现可感知的问题。
3. “怎么实现”页只展开足以解释价值和可信性的关键机制，不做源码目录式罗列。
4. 实验不是独立章节堆数字，而是逐项回答通信是否更轻、状态是否真被消费、记忆是否真被使用、任务是否仍然正确。

主讲 20 页，不设置目录和章节封面：

```text
P01-P04  系统定义、真实任务、交接问题与系统回答
P05-P06  亮点一：为什么需要结构化通信 / 怎么实现
P07-P08  亮点二：为什么需要非文本状态 / 怎么实现
P09-P10  亮点三：为什么需要共享记忆 / 怎么实现
P11      CodeAct 受约束执行
P12-P14  三个技术难点：执行语义、状态可信、跨任务兼容
P15-P18  任务、实验、结果和完整性
P19-P20  评分闭环与结尾
```

三个亮点使用完全不同的视觉母题：

| 亮点 | “为什么”页 | “怎么实现”页 |
| --- | --- | --- |
| 结构化通信 | 逐步膨胀的消息载荷 | 一张控制合同的结构解剖 + Policy 印章 |
| 非文本状态 | float32 矩阵绕道 JSON 的对照 | 两个进程与共享 StatePool 的系统剖面 |
| 共享记忆 | Q1 记忆误用到 Q2 的具体反例 | 记忆护照 + 兼容闸门 + 消费/效果回执 |

因此六页不会重复成六张箭头流程图。

```text
两期财报 PDF/表格        找到同口径指标                   营收值与环比
```

### P03 任务中的问题｜三种对象都被迫变成文本

**标题**：`问题出在交接：任务约束、数值状态和历史经验被压进同一种文本通道`

主视觉沿用 P02 的三个真实对象，汇入一条“文本漏斗”：

```text
任务合同 ─┐
数值矩阵 ─┼─> 统一转成文本消息 ─> 下游重新理解
历史经验 ─┘
```

漏斗出口下方显示三个具体后果：

- 每一角色重复接收目标、计划和全文证据，通信负担持续增加。
- 数值对象失去 dtype、shape、hash 和身份，下游只能重新解析或计算。
- 相似历史可能绕过当前输入、口径与运行环境检查，把旧结果带进新任务。

唯一结论：`多 Agent 的瓶颈，不只是角色能力，而是交接对象没有被区别对待。`

### P04 StateBus 回答｜同一任务走完一条受控交接轨道

**标题**：`StateBus：四个角色不直接互调，由 Runtime 组织同一任务的状态交接`

**这张图要回答**：`谁在调度？每一跳交接什么？三个亮点落在任务链的哪里？`

P03 与 P04 组成前后对照：P03 的三类对象全部挤入文本漏斗；P04 保留相同的任务合同、数值矩阵和历史经验，但将它们放入三条不同的交接通道。两页使用相同对象图标与颜色，让评委不靠口头解释也能看出变化。

主图采用“角色挂点 + Runtime 轨道 + 交接对象”三层结构：

```text
角色挂点       Planner             Retriever             Executor            Summarizer
                 │                    │                      │                    │
Runtime 轨道  任务编译 ─ 计划批准 ─ 证据召回 ─ 数值选择 ─ 执行验证 ─ 总结提交
              ●────────●────────●────────●────────●────────●
运行时节点    Compiler   Policy      Driver     Selector    Validator     Commit Gate
                                                Worker

交接对象      TaskSpec   Approved    Semantic    selected    Execution     ClaimSet /
                         Plan +      StateRef    IDs +       ArtifactRef   Memory candidate
                         StepGrant               EvidencePack
```

具体画法：

- 上层只放四个 Agent 名称和简洁角色图标，用四条短竖线挂到对应工作阶段，不画 Agent 之间的箭头。
- 中层是一条连续的深墨蓝 Runtime 轨道，六个停靠点从左到右表达时序；Policy 与 Selector Worker 明确画在 Runtime 内，不冒充第五个 Agent。
- 下层在每个停靠点正下方放一个“交接票据”，中文对象名为主、精确类名为小注；票据沿轨道对齐，不做漂浮卡片。
- 右端从 Commit Gate 向“下一任务”保留一条短回弯线，表示只有验证通过的 MemoryRef 才能跨任务进入下一轮。

轨道底部再用三条不等长的细色带标出机制覆盖范围：

- 控制蓝：typed Protobuf、TaskSpec、ApprovedPlan、StepGrant，约束每一步能做什么。
- 状态青绿：StatePool、SemanticStateRef、selected IDs、receipt/release，保持数值对象连续。
- 记忆金棕：ExecutionArtifactRef、Compatibility Gate、MemoryRef，让验证产物进入下一任务。

三个颜色只标交接对象和作用范围，不给整个 Agent 节点染色。这样颜色表达机制，不表达部门或步骤状态。

事实边界：Planner 只提交提议；Selector Worker 消费数值状态；Summarizer 产生 ClaimSet/摘要候选；授权、局部 hydrate、验证和 Memory commit 均由 Runtime/Policy 门完成。

页底结论固定为：`Agent 只处理本阶段的 RoleView；Runtime 校验并重包每次交接，数值状态和验证产物不再作为全文聊天历史搬运。`

主视觉为“消息载荷截面”，不是角色流程：

```text
Planner 消息      [目标 + 计划]
Retriever 消息    [目标 + 计划 + 全文证据]
Executor 消息     [目标 + 计划 + 全文证据 + 工具说明]

```

四条消息画成从薄到厚的纸带/文件层，重复内容使用同一灰色纹理，新增内容用控制蓝标出。

右侧只回答三个问题：

- 哪些字段属于任务身份？
- 当前角色到底允许做什么？
- 哪个字段错误时，能否局部拒绝？

### P06 亮点一·怎么实现｜控制合同解剖

**标题**：`怎么实现结构化通信｜一张合同回答五个执行问题`

主视觉是一张大型“控制合同”，只保留五个中文问题：

| 合同区 | 页面大字 | 小号精确字段 | 解决的问题 |

| 输出 | 必须交付什么？ | `output_contract` | 结果可验证 |
| 边界 | 最多做多少？ | `budget / timeout / tools` | 成本与风险可控 |

```text
DENIED    -> reason code
REPLAN    -> 有限修复
```

页底实验条：

`相同 50 条 Agent 消息：control bytes 25,196 -> 4,270（-83.05%）；wire bytes -68.95%；质量 10/10。`

### P07 亮点二·为什么｜数值对象不应绕道文字

**标题**：`为什么需要非文本状态｜同一张 float32 矩阵，为什么先变成文字再恢复？`

**这张图要回答**：在相同的矩阵输入和数值消费目标之间，文本绕行到底增加了哪些转换？

本页先解释“什么叫非文本”，暂不把 PID 和生命周期塞进来。

主视觉使用一张明确的矩阵对象：

```text
检索阶段已经得到
float32 matrix [rows × 1024]
```

将它分成上下两条路径：

```text
文本绕行：矩阵 -> "[0.031, -0.117, ...]" -> Token -> 解析 -> 新矩阵
直接状态：矩阵留在 StatePool -> 只发送 StateRef -> 数值程序使用同一对象
```

文本绕行使用一条长 JSON 纸带和 token 小块表现；直接状态使用一个小型“行李牌/引用票据”表现。

页面必须用大字给出定义：

> 非文本不是系统里完全没有文字，而是数值载荷始终保持二进制 float32；控制消息只携带引用和校验元数据，下游用数值运算消费它。

明确三点：

- LLM 不直接读取 embedding。
- StateRef 不是把向量换一个字符串名字后继续内联。
- 当前不是 hidden state 或 KV cache 传递。

### P08 亮点二·怎么实现｜跨进程但对象连续

**标题**：`怎么实现非文本状态｜Ref 跨过进程边界，float32 对象始终不变`

**这张图要回答**：什么跨过了进程边界、数值载荷留在哪里、最终由谁真实消费？

复用 P07 的同一张矩阵图，位置和颜色尽量保持一致，让两页视觉连续。

主视觉改成“两个进程 + 共享 StatePool”的系统剖面：

```text
┌ Retriever / Producer PID ┐       ┌ Selector / Consumer PID ┐
│ 生成 query+candidates     │       │ 校验 Ref 后数值 top-k    │
│ publish matrix            │       │ 返回 selected IDs        │
└──────────┬────────────────┘       └────────────┬─────────────┘
           │                                     │
           └──── StatePool：同一块 float32 matrix ┘

上方控制通道：UDS + Protobuf 只传 SemanticStateRef + Grant
下方连续性条：dtype=float32 | shape 不变 | hash 一致 | identity 可核验
```

不要画五个连续方框。围绕同一个矩阵对象放五个编号标记即可：

`1 发布 / 2 授权 / 3 打开校验 / 4 数值消费 / 5 回执释放`

Selector 输出 selected IDs；Runtime 再根据 locator 局部 hydrate EvidencePack 给 Executor。这样“非文本数值选择”和“LLM 阅读少量原始证据”连续起来。

页底实验条：

`3 个语义任务 -> 9 个数值对象 -> 9/9 跨 PID 消费 -> 9/9 改变选择 -> 294,912 B 全量释放。`

### P09 亮点三·为什么｜相似记忆可能最危险

**标题**：`为什么需要兼容记忆｜语义相似，不代表当前任务可以使用`

使用一个具体反例，不用抽象四卡片：

```text
当前任务：ACME 2026Q2 营收
候选记忆：ACME 2026Q1 营收 = 42.3M
语义相似度：0.92
```

中间放大 `0.92 相似`，但右侧并排对照五项：

| 检查项 | 当前任务 | 候选记忆 | 结果 |
| --- | --- | --- | --- |
| 期间 | Q2 | Q1 | 不一致 |
| schema | 当前版本 | 旧版本 | 待检查 |
| lineage | 当前数据 | 旧数据 | 不同 |
| runtime/validator | 当前签名 | 历史签名 | 可能不兼容 |
| 输入绑定 | 当前输入 | 旧数值写死 | 不可直接复用 |

底部一句：`错误记忆往往格式完整、语义相似、不会报错，因此比普通失败更危险。`

本页不展示完整漏斗，先让评委理解为什么必须有兼容门。

### P10 亮点三·怎么实现｜记忆护照与实际消费

**标题**：`怎么实现共享记忆｜通过兼容门、进入角色输入并产生效果，才算复用`

**这张图要回答**：一个检索候选经过哪些状态变化，才有资格被统计为 actual-use？

#### 区域一：候选池

关键词、标签、向量三路召回汇入候选池。只写三个来源，不画底层数据库细节。

#### 区域二：记忆护照 / Compatibility Gate

大型护照对象只回答五个中文问题：

- 是否为同类意图？
- 字段和指标口径是否一致？
- 来源与 lineage 是否可追溯？
- runtime 与 validator 是否兼容？

### P11 CodeAct｜一个受控执行工作区

**标题**：`CodeAct｜模型可以写代码，但不能绕过授权、沙箱和质量门`

**副句**：`CodeAct 是 Executor 的执行扩展，不是第四个赛题支柱。`

**这张图要回答**：LLM 生成的代码怎样从不可信文本变成可引用、可验证的 ExecutionArtifactRef？

使用“受控工作区边界 + 内部五步流程”。流程必须存在，但全部收在 Executor Workspace 内，避免被误读成系统的第四条主链：

```text
外部输入：Approved Step + verified Artifact

┌──────────── Executor Workspace ────────────┐
│  生成代码 -> AST/Policy 审计 -> bwrap 执行 │
│                    -> schema/quality 验证   │
│                         │                   │
│                    有限 repair              │
└────────────────────────────────────────────┘

唯一允许离开的对象：ExecutionArtifactRef
```

Approved Step 从左侧穿过 Workspace 边界进入；ExecutionArtifactRef 从右侧在 Validator 通过后离开。策略拒绝和质量失败向下进入一条短的有限 repair 分支，不能直接写入 Memory。

页内放 6-8 行真实风格 Python，并用两条标注指向“输入来自已验证文件”“输出写入固定路径”。

实验条：`25 个能力任务：18 次 bounded Python + 7 次 DSL，fallback = 0。`

口径：18 条 Python 来自 E5 Adaptive 能力任务的 LLM 生成与受限执行；E1/E2 的确定性执行不描述成临场 CodeAct。

### P12 技术难点一｜格式合法不等于允许执行

**标题**：`难点一｜协议格式合法，为什么仍然不能直接执行？`

**这张图要回答**：typed Protobuf 已经通过 schema 校验后，系统还必须判断什么？

使用一条必要的“双门决策流”，明确格式门和语义授权门不是同一层：

```text
PlanProposal
     │
     ▼
格式门：字段 / 类型 / 必填项 ──失败──> 拒绝解析
     │通过
     ▼
Policy 语义门：能力 / 依赖 / 输入输出合同 / 预算与工具
     ├──通过──> StepGrant
     ├──可修复──> 有限 replan
     └──越权或耗尽──> deny + reason code
```

左上放一个具体反例：计划对象字段全部合法，但请求了 Executor 未获授权的工具，或依赖一个不存在的前驱步骤。高亮一句：`schema 能证明“像一个计划”，不能证明“系统允许这样做”。`

Policy 区只保留四个中文判断：

- 角色是否拥有该能力？
- 前驱步骤和输入引用是否成立？
- 输出是否满足当前合同？
- 工具、预算和风险边界是否允许？

底部展示三种可审计结果：`grant / replan / deny`，每种都带 `proposal_id + decision + reason code`。

与 P06 的区别：P06 解剖控制合同包含什么；P12 展示一份合法合同如何经过语义判定后才获得执行权。

### P13 技术难点二｜对象可打开不等于状态可信

**标题**：`难点二｜共享内存能够打开，怎样确认还是那个正确对象？`

**这张图要回答**：消费者跨 PID 打开状态前，如何验证身份、内容与生命周期？

主视觉使用“两个进程 + StateRef 检查站”，允许一条局部流程，因为这里的核心就是跨边界校验顺序：

```text
Producer PID              StateRef 检查站                 Consumer PID
publish float32   ->  身份 / 血缘 / hash / shape  ->  numeric consume
matrix + Ref          encoder signature / lease          selected IDs
                              │
                              ├─ 不一致：reject + recompute
                              └─ 过期：release / reclaim
```

页面中心放大一张“状态护照”，只保留六个签章：

| 签章 | 回答的问题 |
| --- | --- |
| identity | 是当前任务请求的 state_id 吗？ |

| integrity | payload hash 是否一致？ |

## 6. 图形语言与流程图使用原则

### 6.1 不限制流程图数量，只限制无意义流程图

先判断页面要解释的关系，再决定图形：

| 页面要解释什么 | 首选图形 | 原因 |
| --- | --- | --- |
| 时间先后、责任转移、对象跨边界 | 流程图 / 泳道 / 运行轨道 | 需要看见谁在什么时候接过什么 |
| 旧方式与新方式的差异 | 同起点、同终点的并行路径 | 评委可以直接比较多了什么、少了什么 |
| 一个对象由哪些字段和约束组成 | 对象解剖 / 护照 / 剖面 | 字段之间没有时序，不应硬画箭头 |
| 两个判断维度彼此独立 | 判定矩阵 | 比串行流程更能表达正交关系 |
| 实验原始值与变化 | 双柱、比例条、漏斗 | 直接展示数量和分母 |

必须保留并认真绘制的流程关系：

| 页面 | 流程回答的问题 | 推荐形式 |
| --- | --- | --- |
| P04 | 一个任务由谁调度、每一跳交接什么 | 六停靠点 Runtime 轨道 |
| P08 | float32 怎样从 Producer 跨 PID 被 Consumer 使用并释放 | 两进程 + StatePool 生命周期 |
| P10 | 候选记忆怎样经过兼容门变成 actual-use 和 effect | 主晋升流 + 一条拒绝重算分支 |
| P11 | LLM 代码怎样经过审计、隔离执行和验证形成产物 | Executor Workspace 内部流程 |
| P12 | schema 合法怎样进一步变成执行授权 | 格式门 + Policy 门决策流 |
| P13 | Consumer 打开状态前怎样完成可信检查 | StateRef 检查站局部流程 |

P04 是唯一完整端到端任务流程；P08、P10、P11、P12、P13 都是围绕局部机制或边界的必要流程，不重复四 Agent 全链。

流程图统一遵守：

- 一个页面只有一个主要阅读方向，默认从左到右；异常分支向下，不让连线回穿主线。
- 主线最多六个主要停靠点；一个节点只表达一个动作和一个结果。
- 箭头必须能读成动词，例如“签发”“打开”“消费”“验证”“提交”，不能只表示装饰性连接。
- 节点用名词，连接用动作，票据用对象名；三者不能混成同一层文字。
- Agent 之间不画直接调用箭头；凡由 Runtime 完成的授权、重包、校验和提交，都必须落在 Runtime 轨道上。
- 失败分支只保留最关键的一条，用砖红细线；正常路径使用深墨蓝或对应机制色。

### 6.2 P04 主图的专业画法

P04 的图形不是为了表示“系统里有四个 Agent”，而是为了让评委完成一次完整读图：

1. 先看上层四个角色，确认各自在哪个阶段工作。
2. 再沿中层 Runtime 轨道从左到右阅读六个阶段。
3. 再看轨道下方的交接票据，理解阶段之间实际传递的是哪个对象。
4. 最后看底部三条机制色带，确认三个亮点分别覆盖任务链的哪些部分。

建议版面比例：标题和读图问题占 14%，角色挂点占 16%，Runtime 主轨道和对象票据占 48%，三条机制色带占 12%，页底结论与来源占 10%。

视觉细节：

- Runtime 轨道是一条稳定的 2-3 pt 深墨蓝线，六个停靠点等距；不要使用一根粗大的渐变箭头。
- 四个角色只用名称、简洁图标和短竖线挂接，不放四张同样大小的卡片。
- 交接票据统一为小型直角标签：大字写中文含义，小字写 `TaskSpec`、`SemanticStateRef` 等精确类型。
- Policy、Selector Worker、Validator、Commit Gate 位于轨道内部或下缘，明确它们属于 Runtime，而不是新的 Agent。
- P03 与 P04 复用同一组“合同、矩阵、记忆”对象图标。P03 中它们被压入文本，P04 中它们进入不同通道，形成跨页前后对比。

### 6.3 重要对比必须画成可直接比较的图

- P03/P04：同一任务、同一批对象，比较“统一文本漏斗”和“分层受控交接”。
- P07：同一张 float32 矩阵、同一消费目标，并排比较文本绕行与 StateRef 路径。
- P09/P14：同一个 Q1/Q2 反例，先展示风险，再展示相似度与兼容性是两个维度。
- P17：L0/L3 完整链与 L0/L1 通信专项分成两个面板，各自标明配置，不混用系列。

对比图必须保持相同起点、相同终点、相同对象尺寸和一致语义色；不能用一个复杂流程对比一张简单卡片来人为制造优越感。

### 6.4 六张亮点页的形式平衡

| 页面 | 图形形式 | 主要对象 | 是否依赖流程 |
| --- | --- | --- | --- |
| P05 | 逐步增厚的消息截面 | 重复文本载荷 | 否 |
| P06 | 合同解剖 + Policy 印章 | 控制合同 | 否 |
| P07 | 两条并行路径对比 | float32 matrix | 是，强调绕行差异 |
| P08 | 两进程共享内存剖面 + 生命周期 | 同一矩阵 + StateRef | 是 |
| P09 | 当前任务与候选记忆对照 | Q2 vs Q1 | 否 |
| P10 | 候选晋升、拒绝重算与效果回执 | MemoryRef / RoleView | 是 |

相邻页面不机械追求不同形式，但不能连续出现相同的“若干卡片 + 若干箭头”。每张流程图都必须在标题下写清阅读问题，并在页底给出由图直接推出的结论。

### 6.5 对象必须回答中文问题

禁止只放：

`task_id / capability_id / input_refs / output_schema`

必须先写：

`这是谁的任务？ / 允许做什么？ / 读取哪些对象？ / 必须交付什么？`

英文类名和字段名只作为 10-11 pt 精确注释。

### 6.6 同一对象跨页连续

- P07 与 P08 使用同一张 float32 矩阵图，位置、颜色和形状保持一致。
- P09 的候选记忆在 P10 变成记忆护照中的一个候选实例。
- P05 中被重复搬运的任务字段，在 P06 进入控制合同的五个区域。

这种“同一对象继续被解释”的方式借鉴 RISC-V 参考稿的局部放大，但不借用其研究叙事。

## 7. 图表规范

### 7.1 显示原始值

百分比必须和原始值同时出现，例如：

`总 Token 33,974 -> 17,870（-47.40%）`

### 7.2 不同单位不共享坐标轴

Token、bytes、seconds 和消息数使用独立比例条。禁止再次出现原始值柱体越过页面边界的问题。

### 7.3 质量不画普通柱

质量用 `10/10 = 10/10` 或绿色质量门显示。等高 100/100 柱没有信息价值。

### 7.4 记忆漏斗保留分母

查询级 actual-use 使用 20 为分母；候选级拒绝使用 48 为分母，两者不得混画为同一百分比。

### 7.5 固定对照颜色

- 纯文本基线：中性灰。
- StateBus 总体：深墨蓝。
- 控制机制：控制蓝。
- 状态机制：状态青绿。
- 记忆机制：记忆金棕。
- 拒绝/失败：砖红，仅此用途。

## 9. 主讲中必须统一的事实

1. 四个 Agent 是 `Planner / Retriever / Executor / Summarizer`。
2. Agent 不直接互相调用；中心 Runtime 负责顺序、校验、授权和交接物重打包。
3. Planner 产生提议，Policy/Runtime 才产生 ApprovedPlan 和 StepGrant。
4. `SemanticStateRef` 指向 little-endian float32 语义矩阵，不是 hidden state 或 KV cache。
5. 非文本的含义是数值载荷保持二进制并被数值程序消费，不是系统完全不出现文字。
6. 数值状态由不同 PID 的受控 Selector Worker 消费，返回 selected IDs，再局部 hydrate EvidencePack。
7. `ExecutionArtifactRef` 与 `SemanticStateRef` 是不同引用类型，不能合并。
8. Summarizer 产生 ClaimSet/摘要候选；MemoryRef 必须经过验证和 commit gate。
9. 记忆 candidate、approved、consumed、effect 和 saved work 必须分开。
10. `95/95` 表示 95 次正式执行通过，不表示 95 个互不重复的任务定义。
11. 时延统一写固定 10 个同任务串行对照：`315.678 s -> 295.728 s，-6.32%`。
12. Operating `-17.73%` 是 5 个子集任务亮点，不替代整体 `-6.32%`。
13. E5 的 18 次 bounded Python 是 LLM 在已批准能力内生成；E1/E2 的确定性执行不写成临场 CodeAct。
14. openEuler 口径是 24.03 LTS-SP3 单容器验证，不扩展成任意 Linux、VM 或生产级沙箱承诺。

## 12. 最终叙事

新版应让评委形成这条连续理解：

```text
一项真实任务需要在四个角色之间连续交接
  -> 传统协作把任务约束、数值状态和历史经验都变成文本
  -> StateBus 用控制合同解决任务边界
  -> 用 StateRef 保持 float32 数值对象跨进程连续
  -> 用兼容门把历史候选晋升为真实消费和可观察效果
  -> CodeAct 将已批准步骤变成验证产物
  -> 最后用同任务、连续任务和机制专项实验量化收益
```

这条线属于应用系统叙事，不是底层算子研究叙事；它同时覆盖三个核心亮点、技术难点、CodeAct、四角色、连续任务、openEuler 交付和实验验证。
