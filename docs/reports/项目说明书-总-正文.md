# 摘 要 {-}

随着大模型应用由单 Agent 问答走向多 Agent 分工协作，Agent 之间需要持续交换任务描述、证据、计算结果与历史经验。传统方案通常把中间状态重新组织为自然语言或大段 JSON，再由下游 Agent 解析。这种方式虽然通用，但在多轮、长证据和连续任务中会产生重复上下文、额外 Token、反复编解码以及难以验证的隐式依赖；同时，任务执行形成的证据与策略往往缺少统一身份、兼容约束和可审计的复用记录。

StateBus v2 面向上述基础设施问题，构建了由 Planner、Retriever、Executor、Summarizer 四角色组成的多 Agent 运行时。系统以 UDS 与 typed Protobuf 作为正式控制面，以 `SemanticStateRef`、`ExecutionArtifactRef` 和 `MemoryRef` 作为分层数据对象：短生命周期的 embedding 与稠密数值状态优先存放于 `shared_memory`，可回放对象与清单进入 mmap/CAS，执行结果进入独立任务工作区并以产物引用回传。共享记忆采用候选召回、兼容校验、角色重绑定、真实消费和效果记录的闭环，避免把“检索到相似内容”等同于“发生有效复用”。Executor 进一步支持受限 Python CodeAct 与结构化 DSL 两条执行路径，生成代码需经过能力授权、AST/Policy 审计、非 root bubblewrap 隔离、输出契约和质量门验证后，才能提升为可消费产物。

系统提供 StateBus Studio 产品化界面。Evidence Center 从固定证据快照读取与答辩 PPT 一致的结果；Live Studio 通过白名单配方、单 Worker 队列和 SSE 事件流展示任务在四个 Agent 间的类型化流动、模型生成程序、产物验证和最终结论。前端采用 React、TypeScript、React Flow 与 ECharts，后端采用 FastAPI，浏览器不具备提交任意 Shell 或重启模型服务的权限。

按照固定代码/实验基线 `bda17745ecb8a160221efe3b58ca678644dac81a`，项目完成四层验证：40 次同任务配置对照、20 次连续任务、10 个机制真实性用例和 25 个能力覆盖任务，共 95/95 正式执行通过。在 10 个同任务纯文本与完整 StateBus 串行对照中，总 Token 从 33,974 降至 17,870，降低 47.40%；wire bytes 从 36,069 降至 12,677，降低 64.85%；总耗时从 315.678 秒降至 295.728 秒，降低 6.32%，两组质量均为 10/10。结构化通信专项在相同 50 条消息下将控制面字节降低 83.05%；9/9 个非文本数值状态由不同 PID 的进程真实消费并改变下游选择；两组 10 轮自然连续任务的共享记忆 actual-use 为 7/20，即 35%，且 39/48 个不兼容候选被拒绝。五类 25 个能力任务全部通过，其中 18 个走受限 Python CodeAct、7 个走 DSL，未触发 fallback。

**关键词：** 多智能体；结构化通信；Protobuf；StateRef；共享内存；共享记忆；CodeAct；openEuler

# 绪 论

## 目的与意义

本项目针对赛题“一种面向多智能体协作的低开销通信、状态传递与共享记忆机制”，目标不是再实现一个只会串联大模型接口的工作流，而是把多 Agent 协作中反复出现的通信、状态、产物和记忆问题沉淀为可运行、可验证、可追溯的系统层机制。

多 Agent 系统的关键矛盾在于：角色分工越细，协作消息越多；上下文越长，重复传输越明显；复用越积极，错误历史污染新任务的风险越高。因此，系统不能只追求“传得少”或“命中高”，还必须同时回答以下问题：消息有没有稳定合同，数值状态是否真的由另一进程消费，产物是否可验证，历史记忆是否兼容，以及一项节省是否在质量保持的前提下成立。

在通信层面，StateBus 将 Agent 之间的协作从全文透传收敛为动作、参数、引用、能力和回执。这样做并非排斥自然语言，而是把自然语言保留在真正需要模型理解和生成的位置；任务控制、对象身份与状态变化改由可枚举字段承担。对多轮任务而言，上游不必反复把相同证据、能力描述和历史上下文写回 Prompt，下游也不必从散文中猜测步骤 ID、操作参数和成功条件，因而能够同时降低 LLM 可见上下文和线路载荷。

在状态层面，embedding、语义候选矩阵等对象保持数值形态，通过 `SemanticStateRef` 在独立进程间传递。StateBus 不把“共享内存可读”本身当作成果，而是为数值对象增加 shape、dtype、encoder signature、manifest、hash、lease 和 producer/consumer receipt，使物理传递能够被语义校验。该机制减少“数值状态—文本描述—重新编码”的往返，也让非文本状态是否改变下游选择成为可以直接检查的系统事实。

在知识层面，任务形成的证据、策略、摘要和验证产物不再作为无结构聊天历史保存，而是沉淀为带 ID、来源、时间、任务主题、schema、lineage 和运行兼容条件的记忆单元。后续任务先召回候选，再判断是否兼容、是否允许目标角色查看、是否实际消费以及产生何种行为效果。这样的记忆机制追求的是可控积累，而不是把所有相似历史无条件塞入上下文。

从工程角度看，上述三层还共同提供了可审计性。一次最终结论可以沿 ClaimSet、ExecutionArtifactRef、EvidencePack、StateRef 或 MemoryRef 回到具体输入与验证报告；一次失败也可以定位到计划、协议、状态、代码、产物或记忆 Gate。项目由此把赛题关注的通信效率、状态创新和记忆复用统一在同一个 Runtime，而不是三个相互独立的演示脚本。

## 项目背景

传统 Agent 协作通常由上游角色生成自然语言，下游角色再从自然语言中恢复动作意图、参数和中间事实。长文本虽然表达能力强，但缺少显式的 schema、能力边界和拒绝语义。一个格式合法的 JSON 也不意味着其中的操作被授权、输入引用可访问、输出契约正确或结果可提交。

另一方面，检索系统通常会生成 embedding 与排序分数，但许多多 Agent 框架只把最终选中文本传给下游，数值中间态没有独立身份，也缺少跨进程消费证据。共享记忆也容易停留在“检索到若干候选”的统计层面：语义相似可能来自同一公司、同一指标或相似表述，却不代表统计口径、schema、任务意图和来源链兼容。

赛题要求系统至少覆盖三类 Agent 角色、实现结构化通信、非文本中间状态与共享记忆，设计两组关联连续任务，统计通信、时延和复用数据，并在 openEuler 24.03 LTS-SP3 上可运行。StateBus v2 以四角色完整链、三层基础设施和统一实验门回应这些要求。

系统首先追求“低开销但不减少必要协作”。完整链对照保持同样的角色关系和逻辑消息数，压缩的是消息载荷、重复证据和 Prompt 可见上下文，而不是通过删掉 Agent 或跳过质量门制造节省。与此相配套，引用化不能牺牲可验证性：控制面虽然只传 Ref，但 Ref 必须解析到具有 schema、hash、lineage、状态和生命周期的真实对象，任何裸路径或无法交叉验证的 locator 都不能成为正式输入。

系统其次遵循“复用但不污染、生成但不直接信任”。记忆检索与记忆复用被拆成两个阶段，未通过兼容门的候选不能进入角色输入；LLM 可以产生计划和 Python 程序，但 PlanPolicy、CapabilityGrant、AST/Policy、sandbox、Validator 与 Commit Gate 决定它们是否可执行和提交。所有阶段都记录结构化事件、引用哈希、验证状态和拒绝原因，使工程调试、实验统计和现场展示可以基于同一事实链。

## 主要贡献

项目在运行时层建立了 `CanonicalTaskSpec → ApprovedPlan → EvidencePack → SemanticStateRef / ExecutionArtifactRef → ClaimSet → MemoryRef` 的类型化对象链，并以 task、step、attempt、role 和 hash 保持跨 Agent 关联。与对象链配套的 typed Protobuf/UDS 控制面实现了接收确认、开始、心跳、成功/失败、取消、致命异常和垃圾回收语义，能力授权与计划哈希共同限制每一步可以访问的输入和可以产生的输出。

项目在数据面实现了 `shared_memory`、mmap、memfd/CAS 等分层后端，将短期数值状态与执行产物拆成 `SemanticStateRef` 和 `ExecutionArtifactRef` 两种合同。前者支持 float32 稠密语义状态发布、跨 PID 解析、选择效果和释放回执，后者支持 workspace、输出清单、Validator 与 candidate/verified 生命周期。这一拆分避免用一个模糊“状态引用”掩盖对象类型和验证方式的差异。

项目在知识与执行层实现了候选召回、Compatibility Gate、角色视图重绑定、真实消费与行为效果记录的共享记忆闭环，同时提供 LLM bounded Python CodeAct 与 Transform DSL 两条 Executor 路径。模型生成程序必须经过能力、静态策略、bubblewrap、资源限制和结果验证，DSL 也必须满足结构化参数和输出合同，两者最终进入同一产物质量门。

项目还构建了覆盖完整链效率、连续任务、机制真实性与能力范围的分层实验体系，并将结果固化为与 PPT 同源的 evidence snapshot。StateBus Studio 在此基础上提供固定证据页和真实任务页：前者保证正式数字不被临时运行覆盖，后者把四 Agent 对象流、Python/DSL、StateRef、MemoryRef、Artifact 和质量回执组合成可现场操作的产品界面。

## 项目边界

当前正式控制面是 **UDS + typed Protobuf**，自然语言或 MessagePack 不作为 v2 主合同。非文本状态指 embedding、稠密语义选择对象等具有明确合同的数值中间态，本文不将其描述为跨引擎传递 LLM hidden state 或 KV cache；KV/Prefix 方向只保留为 **Engine-Local Prefix Reuse** 的未来扩展，不进入当前实验主结论。执行文件和数值状态分别使用 `ExecutionArtifactRef` 与 `SemanticStateRef`，共享记忆则以查询级 actual-use 和行为效果为主指标，不把候选数或向量相似度直接称为复用命中率。Studio 固定证据快照与实时运行记录相互隔离，后续临时演示不会自动改写 PPT 和说明书使用的正式数字。

# 技 术 理 论

## 设计思想

StateBus v2 研究的对象不是某一个 Agent 的回答质量，而是多个 Agent 共同完成任务时，中间信息如何被表达、传递、验证和复用。传统多 Agent 系统通常把上一步得到的证据、参数和阶段结论重新写成自然语言，再作为下一步 Prompt 的一部分。这样的方式便于快速搭建原型，却把几类性质不同的信息混在了一起：任务控制与业务证据使用同一文本载体，数值中间态需要先转成文本再由下游恢复，执行文件缺少独立的可信状态，历史经验也常被当成聊天记录直接注入新任务。随着角色、步骤和历史轮次增加，系统不仅会重复传输大量上下文，还很难判断下游究竟使用了哪一份状态、一次复用是否真的发生、失败产物是否已经被后续角色看到。

本项目采用合同驱动的设计思想，将多 Agent 协作理解为一组由 Runtime 管理的对象状态变化。Planner、Retriever、Executor 和 Summarizer 仍然负责需要语言理解、检索判断、程序生成和结论组织的工作，但模型输出首先被视为候选：候选计划需要经过计划策略校验，候选代码需要经过能力授权和安全策略，候选产物需要经过业务 Validator，候选记忆需要经过兼容判断。只有满足当前任务合同的对象才能被提升并交给下一角色。这样既保留了大模型面对开放任务时的适应能力，又把文件访问、能力范围、对象生命周期和可信状态收回到确定性的 Runtime 中。

在系统分层上，StateBus 将控制面、数据面和记忆面分开。控制面表达“由谁在什么条件下做什么”，使用 typed Protobuf 描述动作、参数、角色、能力、引用和运行终态；数据面保存“真正被处理的对象”，包括证据、float32 语义状态以及执行产物，并通过类型化引用交接；记忆面保存跨任务可检索的摘要、策略和验证结果，同时保留来源、任务意图、输入输出合同与运行兼容条件。分层不是为了增加组件数量，而是为了让每一类信息采用与其生命周期相匹配的表示：小而频繁的控制消息直接在线路上传递，大对象留在状态池或工作区，长期对象进入可查询的持久存储。

这种设计还引入了“生成权与批准权分离”的原则。Agent 可以提出步骤、证据候选、Python 程序和总结，但不能自行宣布这些结果已经可信；Runtime 根据任务哈希、能力授权、引用状态、内容哈希、Validator 报告和来源链决定对象是否可以继续流动。一次执行进程正常退出，只能说明程序运行结束，不能直接说明业务答案正确；一条记忆与当前查询相似，只能说明它进入候选集合，不能说明它适合当前期间、schema 或数据版本；一段共享内存能够被打开，也不能替代 dtype、shape、encoder signature、manifest 和内容哈希的语义检查。

项目将失败路径看作设计的一部分，而不是正常流程之外的异常补丁。每个步骤同时具有稳定的 `step_id` 和独立的 `attempt_id`，重试不会覆盖前一次尝试；输入引用带有生命周期和消费条件，失败尝试生成的 candidate 不能被 Summarizer 使用；Worker 失联、策略拒绝、Validator 失败和用户取消分别形成结构化终态，最后进入统一的资源结算与垃圾回收路径。通过这种处理，系统能够保留诊断证据，又不会让一个失败的中间对象沿 Agent 链继续传播。

上述思想最终落到三个相互约束的目标上：通信应当减少重复内容，但不能靠删减必要角色或质量门制造节省；状态应当保持原生数值形态跨进程传递，但必须具有身份、完整性和消费回执；记忆应当为后续任务减少重复工作，但必须先证明兼容并记录真实消费和行为效果。StateBus 因此不是一个把 JSON 换成 Protobuf 的序列化工具，也不是单独的共享内存或向量库封装，而是一套围绕对象合同、状态提升和证据闭环组织起来的多 Agent 运行机制。

**表 2-1 设计问题与 StateBus 的理论回答**

| 设计问题 | 常见做法的局限 | StateBus 的处理原则 | 可验证结果 |
|:--|:--|:--|:--|
| Agent 如何交接任务 | 从长文本中重新解析动作与参数 | 动作、能力、参数和引用进入稳定合同 | schema、plan hash、ACK 与终态事件 |
| 大型中间状态如何流动 | 内联文本或重复序列化 | 控制帧只传 Ref，内容保留在分层数据面 | object hash、producer/consumer receipt |
| LLM 生成结果是否可信 | 生成后直接执行或直接总结 | Agent 提案，Runtime 校验和提升 | Policy、Validator、candidate/verified 状态 |
| 历史知识如何复用 | 相似内容直接注入 Prompt | 先召回，再做兼容判断和角色重绑定 | candidate、compatible、consumed、effect 分层记录 |
| 失败如何处理 | 阅读日志后整体重跑 | attempt 隔离、终态收敛、幂等回收 | error code、last heartbeat、settlement 与 GC |

## 技术路线

项目采用“合同先行、机制分层、证据驱动”的研究方法。首先从赛题要求反向建立可观测问题：结构化通信是否在消息数量不变时减少线路载荷，非文本状态是否由另一进程实际消费并影响选择，共享记忆是否通过兼容门进入后续任务，以及这些机制是否在质量不下降的前提下形成端到端收益。随后为每个问题定义可执行合同、运行事件和验证分母，再实现 Agent 角色与物理载体，最后通过同任务对照、连续任务、机制专项和能力覆盖逐层验证。这样的顺序避免了先写一套演示流程、再从零散日志中寻找支持性数字。


图 2-1 展示了从赛题问题到可交付系统的完整路线。任务进入系统后先被标准化为 `CanonicalTaskSpec`，明确任务意图、数据范围、允许操作、输出字段、质量条件和预算。Planner 基于这份合同提出计划，Runtime 通过 PlanPolicy 和能力目录把候选计划转为 `ApprovedPlan`；Retriever 在受限数据范围内形成带来源定位的 EvidencePack，并可把 query 与候选向量以非文本状态发布；Executor 在一次性授权和独立工作区内执行 Python CodeAct 或 DSL，输出首先登记为 candidate artifact；Summarizer 只接收已经验证的证据与产物，并生成能够回到来源的 ClaimSet。任务结束后，满足写回条件的对象形成 MemoryRef，后续任务仍需经过检索和 Compatibility Gate 才能使用。

支撑这条业务路线的是三层基础设施。UDS 与 typed Protobuf 构成控制面，负责请求、确认、开始、心跳、结果、取消和回收；`SemanticStateRef`、`ExecutionArtifactRef`、状态池、工作区和 CAS 构成数据与产物面，负责数值对象、文件和验证状态；SQLite、FAISS/余弦检索及兼容策略构成记忆面，负责持久化、混合召回、过滤和回放。Telemetry 与 Ledger 横向贯穿各层，把 task、step、attempt、role、Ref、hash 和质量结果关联到同一条 trace 中。产品界面和实验汇总器不另造数据，而是从这些结构化对象和事件中投影出流程、指标与证据。

实现顺序也遵循这一依赖关系。项目先建立 v2 clean-room 包、正式任务注册表和合同模型，再完成 typed Protobuf/UDS 与 Worker 状态语义；在任务和控制合同稳定后接入 EvidencePack、StateRef、分层存储、工作区和产物生命周期；记忆复用建立在可验证输入、产物和运行签名之上；最后增加 CodeAct 隔离、统一 Telemetry、正式 benchmark 和 StateBus Studio。越靠后的能力只能消费前面已经闭合的对象，而不能绕过合同直接访问文件或把临时结果写入长期记忆。

本项目没有把所有潜在方向都纳入当前主线。跨模型引擎的 hidden state 或 KV cache 传递没有被当作已实现能力，相关方向只保留为 Engine-Local Prefix Reuse 的后续研究；正式非文本状态聚焦可解释、可验证的 embedding 与稠密语义选择对象。部署上采用单容器 Docker + openEuler 24.03 LTS-SP3，以满足交付复现；容器承担外层环境一致性，bubblewrap 承担 LLM 生成代码的内层最小执行边界，两者不混写为同一种安全机制。

## 代码原创说明

StateBus v2 的任务合同、计划策略、Protobuf 消息语义、运行时状态机、类型化引用、分层状态路由、语义状态编码与消费、证据定位、记忆兼容门、CodeAct 策略、工作区与产物生命周期、Telemetry、benchmark 汇总及 Studio 业务逻辑均在本项目中实现。正式主线代码位于 `v2/`、`studio-ui/`、`tests/v2/`、`docker/` 和相关 `scripts/`。`v2/control/statebus_v2.proto` 及 `v2/control/schema.py` 中的消息描述由项目定义，运行时使用 Google Protocol Buffers 的公开 API 构造消息类；项目没有把第三方协议实现复制为自己的控制面。

Studio 的 FastAPI/React 组件通过公开包接口调用，Docker 与 openEuler 用于交付环境复现，不作为项目原创算法。pytest、Matplotlib 和 Pillow 分别用于测试与文档制图，不进入 Runtime 的核心协作协议。本文所述系统行为以 `v2/` 当前实现为准，不将上游源码改名后并入项目主实现。

# 项目介绍

## 总体功能与实现架构

StateBus v2 提供一条从真实任务输入到可验证结论的完整多 Agent 链。用户可以选择离线财务报告或运营指标任务，系统随后完成任务标准化、计划、检索、非文本语义选择、受控执行、结果验证、总结和可选记忆写回。项目并未把协议、状态池、记忆库和 CodeAct 做成彼此独立的展示脚本，而是让它们共同服务于同一个任务合同：控制面负责推进步骤，数据面负责保存证据和数值对象，产物面负责区分候选文件与可信结果，记忆面负责跨任务召回与安全复用。


图 3-1 中，入口层由 benchmark、任务目录和 StateBus Studio 构成。`TaskCompiler` 从注册任务、数据清单和用户允许参数生成 CanonicalTaskSpec，随后由 Runtime 管理 Planner、Retriever、Executor 与 Summarizer。UDS/Protobuf 只传递控制帧和 Ref，StatePool、Workspace 与 CAS 保存真实对象，MemoryStore 保存经过提交门的长期记忆，Telemetry 与 Ledger 记录所有关键交接。各层之间没有共享可变的全局 Python 对象，下游只能按合同解析已登记的 Ref；因此同一条链既可以被正式 benchmark 调用，也可以被 Studio 以事件方式还原。

一次 Run 的建立从任务身份开始，而不是从调用某个 Agent 开始。任务目录把数据集 ID、数据清单、任务族、操作类型、目标实体、时间范围、必需输出、允许工具和资源预算组合为编译输入；正式模式下，`TaskCompiler` 只接受注册过的任务族、intent、输出字段和工具名称，并把 tuple 字段、按键排序的 arguments 与 schema version 纳入 canonical payload。由此生成的 `spec_hash` 会继续进入计划、检索、授权、产物和记忆对象。后续如果数据范围、输出合同或工具集合发生变化，即使自然语言问题相似，也会形成不同的任务身份，避免两个表面相近而实际口径不同的任务共享同一条执行链。

Runtime 内部不是一个把四个 Python 函数依次调用完的循环。`RuntimeDriver` 持有 Run 级 trace、任务合同、批准计划、对象注册表和事件发射器；`RuntimeSupervisor` 管理每个 step 的 attempt 状态；Dispatcher 负责将批准步骤投影成目标角色真正可见的请求；StateStore、ArtifactLifecycleManager 与 MemoryIndexStore 分别管理短期数值对象、执行产物和长期知识。组件间通过不可变数据类、hash 和显式状态迁移衔接，使业务对象的生命周期与进程生命周期解耦：Worker 退出并不代表产物可信，文件存在也不代表它可以被下一角色消费。

## 多 Agent 协作与结构化运行时

以“比较 ACME 两季度营收并给出带来源的环比结论”为例，系统首先从任务注册表取得公司、季度、指标、单位、允许数据源、输出字段、Validator 和资源预算。`v2/runtime/compiler.py` 将这些内容编译为 CanonicalTaskSpec，并计算稳定的 spec hash。Planner 得到的是任务合同和能力目录，而不是一个可以任意扩写的系统权限；它提出步骤、角色、依赖边和 capability 后，`semantic_plan.py` 负责结构化解析，`plan_policy.py` 检查依赖图、角色匹配、步骤预算、输出合同以及模型执行是否具备 Validator。计划只有在形成 ApprovedPlan 后才能被 Driver 接受。

编译器明确区分正式 benchmark 与交互任务。`benchmark_strict` 模式必须由任务注册表提供预编译 CanonicalTaskSpec；缺少规范任务、使用未注册的 task family、intent、required output 或 tool 都会直接返回 rejected，而不会从一句自然语言临时猜测实验对象。交互模式可以解析符合 schema 的 JSON，也可以进行有限启发式编译；无法可靠结构化时只标记为 opaque freeform，不能冒充正式任务进入严格基线。这一分流保证答辩中的自由输入具有可用性，同时保证实验中的任务边界、分母和输出合同不会因模型解释而漂移。

Planner 的模型输出首先被解析为 `PlanProposal`，还不是可执行计划。`PlanPolicyValidator` 会检查 schema version、task ID、步骤数、Planner Token 预算、角色基数、step ID 唯一性、依赖边、最大 DAG 深度、输入 Ref 是否存在、capability 是否在任务白名单、capability owner 是否与角色一致、输出合同是否匹配，以及 Executor 步骤是否声明质量 Validator。系统允许一次“仅修 schema”的受控修复，但修复前后 task、图结构、capability、依赖、预算和失败策略必须保持相同；任何语义变化都不能借修复名义扩大权限。修复仍失败时只能使用已登记的确定性 fallback 计划，并重新经过同一组 Policy，而不是接受模型自行改写后的新权限。

Runtime 为批准的步骤创建状态并签发一次性 CapabilityGrant。`driver.py` 保存 Run 上下文、对象注册表、事件和阶段指标，`supervisor.py` 管理 step/attempt、ACK、心跳、超时、取消和资源结算，`adaptive_dispatcher.py` 在真正分发前再次比对 task、step、session、owner role、plan hash、grant hash、执行种类和到期时间。这次校验很重要：Planner 的计划即使曾经合法，也不能保证后来注入的 Ref 或授权没有变化。只有 envelope、ApprovedPlan、Grant 和输入对象一致，Worker 才会进入运行阶段。

Grant 不是一个只写着“允许执行”的布尔值。它把 task、session、step、attempt、capability ID/version、批准计划 hash、输入 Ref 集合、输出合同、workspace root、最大运行时间和过期时间编码进 canonical payload，再计算 `grant_hash`；Dispatcher 另外从 capability registry 核对 owner role 与质量 Validator。组装请求时，Dispatcher 重新解析当前 Ref Registry，将 EvidencePack、SemanticStateRef、ExecutionArtifactRef 和 MemoryRef 分别放入对应字段，并计算 input manifest hash。模型无法通过输出新增一个未授权输入，前端也不能通过额外参数扩大 capability；请求字段与 Grant 或 capability descriptor 不一致时，执行在进入 Worker 之前即被拒绝。


Retriever 接到的是从 ApprovedPlan 投影出的检索目标、source scope 和 evidence budget。它在指定数据集内定位财报段落或表格单元格，保存 source hash、页码或表格位置，并构造 CanonicalEvidencePack。需要比较多个语义候选时，Retriever 还会发布 SemanticStateRef；MemoryStore 同时可以返回历史分析策略，但候选记忆在通过兼容门前不会进入任何角色 Prompt。Executor 因此获得的是经过批准的步骤、验证过的 EvidencePack、允许消费的 StateRef/MemoryRef、能力授权和独立 workspace，而不是 Planner 与 Retriever 的完整对话历史。

执行结果同样不以自由文本回传。Executor 生成 Python 或 DSL 并在工作区执行，输出文件先登记为 candidate。Validator 检查季度、指标、单位、计算公式、输出 schema、内容哈希和来源关系后，Runtime 才发布 verified ExecutionArtifactRef。Summarizer 只消费已验证产物及原始证据定位，生成由 claim 与 citation 组成的 ClaimSet；如果摘要、策略或产物满足写回条件，才会形成 MemoryRef。整条业务对象链可以概括为 `CanonicalTaskSpec → ApprovedPlan → EvidencePack / SemanticStateRef / MemoryRef → ExecutionArtifactRef → ClaimSet`。

控制面用 typed Protobuf 显式表达这条对象链的运行状态。所有帧都含 trace、task、step、attempt、目标角色、事件类型和 schema version；`ExecRequest` 携带 operation、能力授权哈希、输入 manifest 哈希和 Ref 句柄，不内联完整证据。UDS 传输为每个 payload 添加四字节长度前缀，并通过精确读取恢复完整帧。Worker 返回 ACK 只表示请求已完整接收，`RunStart` 表示前置校验通过，Heartbeat 表示当前 attempt 仍存活，`SuccessResult` 或 `ErrorResult` 才结束执行；成功结果仍需经过 Ref、schema、hash 和业务 Validator 检查。

真实控制链按 `ExecRequest → ACK_RECV → RUN_START → HEARTBEAT → RES_SUCC/RES_ERR → CMD_GC` 推进。Supervisor 在 dispatch 时登记时间戳，ACK 到达后只改变“已接收”状态，RunStart 后才进入 running；长步骤按 lease 更新 heartbeat。ACK 超时与心跳过期分别形成不同 trap reason，便于区分请求未送达和 Worker 运行中失联。终态帧包含 attempt 身份，因此旧 attempt 的晚到消息无法更新新 attempt。成功帧提供的是 Worker 声明和输出引用，Driver 还要完成 schema、hash、消费回执和业务质量检查；完成 settlement 后才发送 GC 并关闭输入 lease、进程和工作区台账。

`AdaptiveCapabilityDispatcher` 使运行时能够在同一 ApprovedPlan 下选择已登记的执行表示。检索、总结和固定转换走各自 owner role 的 capability；Executor 只有在 Grant 明确允许时才进入 bounded Python CodeAct 或 Transform DSL。Dispatcher 不把“模型建议使用 Python”当作授权，也不会把某个路径失败解释为可以任意换用另一条路径。发生允许的 fallback 或 replan 时，Runtime 生成结构化原因、签发新 Grant、创建新 attempt，并把变化写入 Telemetry，因而正式报告能够区分主路径成功、受控 fallback 和无授权降级。

Runtime 对重试和失败采用 attempt 隔离。旧 attempt 的晚到心跳或结果不会覆盖新 attempt；协议错误与能力拒绝在程序启动前结束，策略拒绝保留审计报告，Validator 失败保留候选文件但阻止下游消费，Worker 失联只终止目标进程组。completed、failed、trapped 和 cancelled 最后都进入 settlement 与 GC，因此成功和失败使用同一套资源台账。

对于包含并行检索或多个上游产物的计划，Driver 按 ApprovedPlan 的依赖边执行 fan-in。一个下游步骤只有在所有必需输入均已登记且达到相应可信状态后才可 dispatch；可选输入缺失会形成显式 projection outcome，不能默默改变 Prompt。某个 attempt 失败时，已经 verified 的其他上游对象仍可复用，失败 attempt 产生的 candidate 则被关闭提升通道。新 attempt 使用新的 workspace、Grant 和状态记录，但继续引用未变化的 verified 上游，从而实现局部恢复，而不是把整条多 Agent 链从头重跑。

| Retriever | Approved step、source scope、evidence budget | EvidencePack、SemanticStateRef | locator、source hash、manifest、encoder contract |
| Executor | Grant、验证输入 Ref、独立 workspace | Python/DSL、candidate ArtifactRef | Policy、sandbox、output schema、业务 Validator |
| Summarizer | EvidencePack、verified ArtifactRef、兼容 MemoryRef | ClaimSet、memory commit proposal | citation、provenance、质量门和写回条件 |

## 非文本状态传递与引用化数据面

非文本状态传递是 StateBus 区别于纯文本协作的核心实现之一。这里的“非文本”并不是把向量转成 Base64 或 JSON 数组后继续塞入消息，而是让 query embedding、candidate embedding 和稠密选择矩阵保持 little-endian float32、C-order 的数值表示，真实字节存放在共享内存或 mmap 中，控制面只携带 SemanticStateRef。消费者在独立进程中解析同一物理对象，完成语义排序或证据选择，再通过结构化结果返回选中的 candidate ID、row index、score、producer PID、consumer PID 和 encoder signature。

`v2/state/semantic_state.py` 负责数值合同。编码时第 0 行固定为 query，第 1 行起为候选；系统检查向量维度、有限值和归一化状态，并为矩阵生成 HydrateManifest。Manifest 将 row index 与 candidate ID、证据来源、业务类别和字节提示绑定，因此下游返回 row index 后，Runtime 能够确定它选择了哪条真实证据，而不是只获得一个脱离来源的分数。矩阵、Manifest 和来源文档哈希共同构成状态身份。

发布过程由数值 blob 与解释 sidecar 同步完成。Retriever 将 query 与候选向量按行堆叠，转换为 little-endian float32、C-order 连续字节，计算 blob hash；同时生成包含 shape、dtype、row contract、encoder signature、candidate locator 和 manifest hash 的 sidecar。StateStore 先做存储决策，再创建物理对象，Registry 最后登记逻辑 Ref 和 lease。只有物理对象、sidecar 与 Registry 三者均成功，Runtime 才发出 `STATE_PUBLISHED`。任一阶段失败都会回收已经创建的部分对象，避免控制面出现一个无法解析的“悬空 Ref”。


`LayeredStateStore` 根据对象类型、大小、生命周期和消费者可解析能力选择载体。短期 dense semantic state 优先进入 Python shared_memory，以便不同 PID 直接映射；需要回放或保存更久的状态可进入 mmap/CAS；执行结果不复用这类数值状态合同，而是进入任务工作区并形成 ExecutionArtifactRef。发布时 Registry 记录 state ID、storage kind、blob hash、manifest、schema 与 metadata，控制面只看到逻辑句柄。若 shared_memory 不可用，系统可以按明确策略选择可解析的 mmap 后端，并把 fallback 原因写入 StorageDecision，而不是静默改变语义。

分层路由并不单纯按大小选择。`LayeredStoragePolicy` 同时查看 object kind、expected lifetime、replay requirement、跨进程消费者和后端能力：短时稠密矩阵优先 shared_memory，需跨 Run 回放或长期保存的对象使用 mmap/CAS，EvidencePack 和 manifest 采用可校验的结构化文件，执行输出始终留在 attempt workspace 后再提升为 ArtifactRef。每次选择都会留下 requested backend、actual backend 和原因；如果消费者不具备某种载体的解析能力，系统在发布前就改走明确的兼容路径，而不是让消费者在运行中猜测字节含义。

消费端取得 Ref 后不会立即读取。它先比对 task/step lineage、状态类型、长度、blob hash、dtype、shape、encoder signature、manifest hash、状态是否 active 以及 lease 是否有效，再以只读方式映射数值对象。计算完成后，SuccessResult 中的消费回执与 Ref Registry 交叉核对；只有 producer 与 consumer、对象哈希和选择结果闭合，Runtime 才把 selected IDs 应用到 EvidencePack 的可见集合。这意味着 StateRef 的作用发生在 LLM Prompt 构造之前，能够直接改变下游 decision surface。

在消费者进程中，解析器依据 sidecar 构造只读 ndarray，并再次检查总字节数是否与 `rows × dimensions × 4` 一致。相似度计算返回 row index 后，HydrateManifest 将其反向映射为 candidate ID 和来源 locator；Runtime 对照请求前后的 decision surface hash，记录候选集合是否真的改变。回执中的 producer PID、consumer PID、state ID、blob hash、selected IDs 和 scores 必须与 Registry 闭合。这样既能证明字节跨越了进程边界，也能证明这些字节参与了业务选择，而不是被读取后丢弃。

对象结束使用后，Runtime 减少 lease，进入释放状态并删除共享内存或回收 mmap 资源；重复释放按幂等操作处理。Telemetry 分别记录 publish、resolve、consume、effect 和 release，避免把“对象创建了”误写为“对象使用了”。实验中的 9/9 跨 PID 消费、9/9 改变选择和发布/释放字节闭合，正是从这些独立事件与回执中核验，而不是从 encoder 调用次数推测。

状态清理同样由 Runtime 驱动。正常完成、消费校验失败、Worker trap、取消和重试都会进入统一 settlement；Registry 先阻止新的 resolve，再等待或撤销 lease，随后关闭 shared_memory 句柄、unlink 所有者对象或回收 mmap 文件。释放事件保存对象大小与终态，重复 GC 只返回幂等结果。此设计解决了现场演示中常见的第二次运行污染问题：上一 Run 即使失败，也不能把活跃 Ref、旧 PID 或未关闭映射带入下一 Run。

StateBus 特意将 SemanticStateRef 与 ExecutionArtifactRef 分开。前者面向短期数值状态，关注 dtype、shape、encoder、载体和消费；后者面向 Python/DSL 输出，关注工作区、文件 hash、output schema、Validator 和 candidate/verified 生命周期。MemoryRef 则面向跨任务对象，关注来源角色、主题、兼容签名和提交状态。三种引用都包含身份与来源，但不能用同一套读取和验证规则互相替代。

**表 3-3 类型化引用与物理载体**

| 引用类型 | 典型内容 | 主要载体 | 消费前关键检查 | 结束方式 |
|:--|:--|:--|:--|:--|
| SemanticStateRef | embedding、query/candidate float32 矩阵 | shared_memory 优先，mmap/CAS 可选 | dtype、shape、encoder、manifest、hash、lease | 消费回执后 release/GC |
| ExecutionArtifactRef | JSON、表格、计算结果、报告 | task workspace + artifact root/CAS | output schema、blob hash、Validator、verification state | verified 后下游可见或 invalidated |
| MemoryRef | 摘要、策略、证据链、已验证产物视图 | SQLite + embedding/index + sidecar/CAS | intent、schema、manifest、lineage、runtime signature | commit、assist/replay 或 reject |

## 共享记忆与跨任务复用

共享记忆的目标不是提高“检索到历史”的比例，而是在连续任务中让经过验证的历史对象安全地减少重复工作。`MemoryIndexStore` 保存 MemoryRef、结构化 embedding 和 commit 状态；持久模式下使用 SQLite 保存索引与元数据，向量候选可由 FAISS 的归一化内积检索产生，FAISS 不可用时使用受控余弦计算。关键词、标签和向量三路候选经过 Reciprocal Rank Fusion 合并，这一步只决定候选顺序，不决定是否允许复用。

混合查询由一个带当前 task/spec hash、query text、tags、query embedding、允许记忆类型、目标角色和 limit 的 `MemoryQuery` 驱动。MemoryIndexStore 分别取关键词、标签与向量 Top-K，记录每路 rank，再用固定 `rrf_k` 做 Reciprocal Rank Fusion；相同得分以稳定 memory ID 排序，保证重复运行的候选顺序可解释。SQLite/FTS 承担持久元数据和关键词查询，FAISS 使用归一化向量的内积近似余弦；缺少 FAISS 时回到逐项余弦，但会保留 matched-on 信息。召回阶段输出完整 candidate pool、taxonomy 和 rerank record，尚未把任何摘要注入 Agent。

每条 MemoryRef 除记忆 ID、来源 Agent、创建时间、主题和摘要外，还记录 memory type、task/spec hash、输入输出 schema、数据 manifest、来源 lineage、Validator 状态、运行兼容签名和 replay class。后续查询同样携带当前任务意图、允许的记忆类型、目标角色、数据范围和运行签名。Compatibility Gate 逐项比较这些字段；语义分数再高，只要期间、单位、schema、数据来源或运行环境不满足当前合同，就只能留下 incompatible reason，不能注入角色上下文。


通过兼容门的记忆还要重绑定为当前角色可以看到的视图。Planner 只获得可用于计划的策略摘要，Executor 获得已验证的操作模板或产物引用，Summarizer 获得带来源的事实和结论；一个角色不能因为持有 memory ID 就读取整条历史对象。Runtime 随后记录 MemoryRef 是否真正进入角色输入、是否改变了计划/证据/执行路径，以及是否跳过步骤或模型调用。项目将查询分为 candidate found、compatible、consumed 和 behavioral effect 四层，只有 consumed 才计入 actual-use，只有可观察的步骤变化才计入 effect。

角色重绑定由 Runtime 生成新的最小视图，而不是把数据库行原样复制进 Prompt。视图保存 source memory ID、目标角色、允许字段和 view hash；真正构造角色输入后，系统再写入 consumption record，记录 consumed-by、进入了哪个 step、采用 assist/replay 哪一类策略以及输入 decision surface。步骤跳过、检索范围缩减、采用历史产物或执行计划变化分别形成 effect 字段。只有候选但未生成角色视图，或生成视图后未进入实际请求，都不会计入 actual-use，从统计层面阻止“召回即复用”的口径膨胀。

复用强度也有边界。assist 类记忆只能提供提示，不能跳过当前计算；validated replay 要求历史产物能够在当前输出合同和 Validator 下重新确认；exact replay 还要求任务、输入 manifest 和 runtime signature 更严格一致。任何条件不满足时，系统回到当前任务的正常检索和执行路径。拒绝历史不是错误，而是一种安全结果，它说明系统没有用高命中率掩盖不兼容数据。

新记忆只能从已经闭合的来源链写回。Summarizer 或 Runtime 提出 commit proposal 后，MemoryStore 检查上游 EvidencePack、verified ArtifactRef、ClaimSet、质量门和 answer adopted 状态，再决定保存为 committed、candidate 或 invalidated。失败 attempt 的文件即使仍在工作区，也不会成为长期知识。这样的写回约束与读取时的兼容门共同防止错误历史在连续任务中累积。

写回时 `RuntimeCommitGate` 同时接收产物生命周期、MemoryCommit、质量门结果、answer adopted、输入 Validator 和输出 Validator。所有条件通过，candidate ArtifactRef 才被标记为 verified，MemoryRef 才进入 committed 状态并保留 replay class；任一条件失败，产物转为 invalidated，记忆仅保留为不可直接 replay 的 candidate 或被显式失效，并生成 settlement 与 invalidation record。读侧 Compatibility Gate 与写侧 Commit Gate 因此构成闭环：前者防止旧对象错误进入当前任务，后者防止当前错误变成未来历史。

## CodeAct、DSL 与可信产物

Executor 支持 LLM bounded Python CodeAct 和 Transform DSL 两类执行表示。两类任务都经过 Planner、Retriever、Executor、Summarizer 四角色链，区别只发生在 Executor 如何表达计算。对组合清洗、统计和跨表逻辑，模型可以根据批准输入生成 Python；对于字段稳定、操作可枚举的任务，计划可以选择 DSL capability，并给出结构化参数。DSL 不是预先写好的最终答案，Python 也不因为由 LLM 生成就自动获得执行权限。

Python 路径由 `LlmCodeActRunner` 组织为生成、审计、物化、隔离执行、验证和提交六个阶段。生成请求只包含 ApprovedPlan 中该步骤的目标、输入 manifest、逻辑文件名、允许库、输出 schema 和 Policy，不暴露宿主机绝对路径。模型返回后，Runtime 提取单一 Python 程序并分别计算 generation request hash、raw response hash 和 source hash；因此后续 Policy、执行记录与产物能够精确指向哪一版代码，而不是只保存最终 stdout。

Python 路径从 CapabilityGrant 开始。Grant 绑定 task、session、step、attempt、允许 capability、输入 Ref、输出合同、workspace、运行预算和有效时间；Runtime 再用 capability descriptor 校验 owner role 与质量 Validator。模型只能看到被物化到当前 workspace 的逻辑输入名，无法通过 Prompt 扩大路径范围。生成源码先经过 AST 与 Policy 审计，系统拒绝 `eval`、`exec`、动态 import、危险模块、路径穿越和未授权文件访问，并限制语法树规模、调用、循环与输出位置。策略失败时程序不会启动，source hash 和拒绝原因被保留。

代码修复也被纳入同一信任边界。Policy repair、runtime repair 和 quality repair 各有独立预算，修复请求只能携带结构化错误摘要和既有合同，不能增加输入 Ref、capability 或输出路径。每次修复都会产生新的 source hash，并从 AST/Policy 与 readiness 重新开始；上一版失败源码和报告仍保留在 attempt workspace。达到预算后明确失败，不把有问题的程序切换到无隔离执行，也不把部分输出拼接成正式产物。


正式 LLM CodeAct 在执行前必须通过 bubblewrap readiness probe。Probe 不只检查命令是否存在，还实际验证进程为非 root、网络不可用、批准输入只读、输出目录可写、仓库与其他任务工作区不可见。执行时生成源码只读挂载为 `/sandbox/generated.py`，输入映射到 `/sandbox/inputs`，只有 `/sandbox/outputs` 可写，并设置超时、CPU、地址空间、文件大小、打开文件数和进程数限制。正式路径不会在 bwrap 不可用时悄悄改成无隔离运行。

Sandbox Runner 使用显式 argv 启动 bubblewrap，不通过 shell 拼接命令；运行环境只保留必要变量，网络 namespace、挂载点和 UID/GID 由 readiness 结果约束。bwrap 以 `--die-with-parent`、`--new-session` 和独立 PID/network namespace 运行，Python 子进程同时受 timeout 与 rlimit 约束；超时会形成返回码 124 和结构化 `sandbox_timeout`，资源超限则保留相应 exit 状态。Runner 收集有限长度的 stdout/stderr，并把 sandbox backend、policy digest、UID/GID、exit reason 与执行耗时写入结果合同。操作系统隔离只回答“代码能访问什么”，不能回答计算是否正确，所以它与后续业务 Validator 不能互相替代。

WorkspaceManager 以 task/step/attempt 建立独立目录，保存 input manifest、程序、Policy 报告、stdout/stderr、output manifest、Validator 报告和 settlement。进程返回 0 后，输出仍处于 candidate：Runtime 检查文件是否位于当前 outputs 目录、是否为符号链接、hash 与 schema 是否一致，再由 capability Validator 对业务字段、预期事实和必要的独立重算进行检查。全部通过后 `ArtifactLifecycleManager` 才将对象标记为 verified；否则标记为 invalidated，保留诊断但禁止 Summarizer 和 MemoryStore 消费。

DSL 路径使用注册 opcode、参数 schema、字段类型和输出合同，由确定性解释器执行。它不需要承担 Python 的全部语法和导入风险，但同样只能访问批准输入，同样进入 workspace，并经过输出 Validator 与 Commit Gate。项目正式能力任务中 18 个使用受限 Python、7 个使用 DSL，反映的是任务执行表示的差异，不代表其中 7 个任务绕过了 LLM 角色链。

当前 DSL 只开放 select、rename、filter、sort、limit、group/aggregate、safe derive、period compare、key join、anomaly check 和 claim projection 等注册操作。`TransformProgramValidator` 在执行前检查 schema version、授权输入 Ref、操作数、行列与输出字节预算、字段是否存在、join 的右侧 Ref 是否获准，并拒绝 path、file、expr、python 等可能引入解释器或文件访问面的参数。解释器输出仍会形成 candidate ExecutionArtifactRef，再经过与 Python 路径相同的质量报告和 verified 提升，因此 DSL 的确定性来自受限指令集，而不是绕过产物可信链。

## 正式任务、质量门与可观测性

正式 benchmark 选择离线财务报告和运营指标作为默认任务领域。与自由问答相比，这类任务既包含长文本检索，也包含表格定位、跨期对齐、统计计算和异常检测，输出能够通过外部规则复核。数据在进入 Runtime 前形成 dataset manifest，记录文件 checksum、字段、来源版本和可见范围；任务注册表将 dataset ID 与 operation、required output、completion criteria、Validator 和预算绑定。Golden answer 与 expected facts 只在任务结束后进入评分侧，不暴露给 Agent。

五类能力任务覆盖财务指标抽取、多期趋势、跨表关联、条件聚合和异常检测；连续任务由 Operating metrics 与 Financial reports 两条各 10 轮的链构成。前几轮建立基础事实和策略，后续逐步加入跨数据集、schema drift、清洗、不兼容候选和 lineage 汇总，使共享记忆有真实历史可以检索，也能观察系统是否拒绝错误复用。

**表 3-4 正式任务族与验证重点**

| 任务族 | 代表操作 | 主要产物 | 重点验证 |
|:--|:--|:--|:--|
| 财务指标抽取 | `lookup_metric` | 指标、期间、单位、citation | 表格/段落定位、数值和单位 |
| 多期趋势 | `compute_trend`、`compute_delta` | 序列、增量、趋势方向 | 期间排序、分母、方向与重算 |
| 跨表关联 | `compare_metric` | 对齐后的比较表 | entity、period、schema 对齐 |
| 条件聚合 | aggregate、extreme、groupby | 分组统计、极值记录 | 缺失值、过滤条件、聚合口径 |
| 异常检测 | IQR、规则检测与清洗 | 异常点、阈值、清洗结果 | 算法参数、边界点、来源行号 |

质量控制贯穿对象生命周期，而不是只在最终答案处做一次 pass/fail。入口 manifest 确认数据身份，TaskCompiler 固化任务 hash，PlanPolicy 检查执行图，EvidencePack 保存来源 locator，StateRef 保存数值合同和消费回执，ArtifactRef 保存输入/输出 hash 与验证状态，ClaimSet 将结论绑定到 citation。长期记忆只有在这些关系闭合后才能提交。任何对象被 invalidated，文件仍存在也不能继续向后流动。

质量门本身由任务注册表选择，而不是由生成答案的 Agent 决定。输入 Validator 先确认文件 checksum、字段、季度/实体范围和必要行；capability Validator 再核对输出 schema、数值类型、单位、公式参数和来源 locator，必要时用独立确定性代码重算；Summarizer 的 ClaimSet 还要满足 required citation 与 supported claim。Golden answer 只在外部评分侧比较 expected facts。这样即使模型文本看起来合理，只要数值、来源或执行合同不闭合，也不能得到正式 PASS。

Telemetry 用结构化事件记录上述过程。`STEP_DISPATCHED` 和 `STEP_COMPLETED` 描述角色步骤，`STATE_PUBLISHED/CONSUMED/RELEASED` 描述数值对象，`ARTIFACT_VALIDATED` 描述产物提升，`MEMORY_HYBRID_QUERIED`、`REPLAY_DECIDED` 和 consumption/effect 描述记忆漏斗，`TASK_SUMMARY_METRICS` 聚合 Token、control bytes、wire bytes、阶段耗时与质量。所有事件共用 trace/task/step/attempt 和对象 ID，Studio、实验汇总器和审计脚本可以从同一事实链生成不同视图。

为避免汇总时重复计数，Telemetry 区分 additive event 与 snapshot event。状态发布、协议帧、步骤和产物事件中的增量指标逐条求和；`TASK_SUMMARY_METRICS` 只取每个 task 的最新快照，再跨任务相加。运行事实另外写入紧凑 JSONL，事件写入与 flush 本身也记录阶段耗时。Replay Ledger 保存 candidate、MemoryRef、ArtifactRef、兼容 verdict、runtime signature、spec/handoff hash、replay class 和 skipped step count，并为整条记录生成 ledger hash。实验汇总、Studio 和审计工具都读取这些持久事实，而不是从控制台文本反推指标。

## 软件界面、前后端与部署

StateBus Studio 面向中文答辩场景，只保留“实验与证据”和“任务演示”两个一级页面。数据集详情、Agent 全记录、代码、StateRef、MemoryRef、Artifact 和质量报告通过详情面板或二级视图展开，避免把产品做成堆满脚本按钮的运维页面。界面不展示模型隐式思维过程，而是展示可以审计的输入合同、结构化输出、生成程序、对象哈希、消费回执和 Validator 结果。

Evidence Center 读取 `v2/studio/data/evidence_snapshot_20260726.json`。顶部固定展示质量、总 Token、wire bytes 和 10 任务总耗时，随后展开结构化通信、非文本状态、共享记忆和能力覆盖。页面只负责渲染固定字段，不在浏览器中重新计算正式结论；临时 Run 存入独立历史，不能覆盖快照。这样说明书、PPT 与网页使用相同分母、单位和数字。


Live Studio 从白名单选择快速任务、连续场景或正式实验。任务启动后，上半区以 Planner、Retriever、Executor、Summarizer 和类型化对象节点构成动态流程，当前 Agent 由真实事件高亮，对象标签在完成交接后沿连接线移动；下半区紧凑呈现当前 Agent 的输入、转换和输出。选择 Executor 时可以查看完整生成 Python/DSL、Policy、bubblewrap、产物与验证回执，选择 Retriever 时可以查看查询、候选、EvidencePack 和 StateRef 消费。任务失败会冻结在发生错误的角色，并显示中文阶段和根因，不伪造后续节点。


前端位于 `studio-ui/`，使用 React、TypeScript、Vite、React Flow、ECharts 和 Lucide。页面维护当前 Run、流程节点、选中 Agent 和详情状态，通过 SSE 接收结构化事件；网络中断不会取消后端任务，刷新后可以按 Run ID 恢复。任务完成后“新建运行”只重置当前画布和选中状态，不删除历史 Run，新的 SSE 订阅也会忽略上一 Run 的晚到事件。

后端位于 `v2/studio/`，采用 FastAPI。`catalog.py` 读取任务和数据目录，`recipes.py` 将前端 recipe ID 映射为固定 Runner 参数，`jobs.py` 负责单 Worker 队列、独立进程组、事件索引、持久化、取消和恢复，`task_flow.py` 从 summary、trace、program 与 artifact 重建四角色视图。浏览器不能提交任意 Shell、路径或 Python 参数，也不能启动或重启 vLLM；创建运行时只提交白名单 recipe 和该 recipe 明确允许的字段。

创建作业前，API 并行检查既有 vLLM health、Embedding 模型目录与设备、Planner Worker import、项目根目录是否进入 `PYTHONPATH` 以及单 Worker 队列是否存活；任一关键项失败，“开始运行”会返回中文阶段原因而不是先排队后崩溃。`recipes.py` 直接构造 argv 列表，每个 recipe 固定 runner、suite、role path、embedding mode、socket 和输出目录，不经过 shell。`jobs.py` 为每个 Run 建立独立目录和进程组，将长任务 stdout/stderr 完整重定向，尾随结构化 runtime event 并分配递增 SSE ID。取消只向当前 Run 的进程组发送信号，不触碰既有 vLLM 或其他历史目录。

任务详情的恢复也采用受限读取。`task_flow.py` 只在当前 Run 根目录内寻找 summary、planner trace、program、Validator 和 artifact，解析前同时检查路径归属、文件类型与大小上限；不能通过产物中的路径字段读取仓库其他位置。服务重启时 JobManager 从 `studio_job.json` 与事件 JSONL 恢复终态和序号，前端刷新后以 Run ID 和 last event ID 继续订阅。“新建运行”清空的只是页面中的当前 Run、选中 Agent 和动画状态，历史证据与后端任务不被删除，也不会让上一 Run 的晚到事件覆盖新流程。

## 验证问题与实验分层

实验按“性能对照 → 连续复用 → 机制真实性 → 能力覆盖”逐层展开，避免用单一任务同时承担所有结论。完整链效率实验回答相同任务条件下 Token、线路字节、总耗时与质量是否变化；通信专项固定消息数量，只观察控制载体变化；连续任务和记忆真实性用例分别回答自然历史中是否发生 actual-use，以及兼容候选、拒绝重算和行为效果能否追踪；非文本 holdout 直接检查物理 StateRef 是否跨 PID 消费并改变选择；能力覆盖任务再验证五类操作、四 Agent 和两条 Executor 路径能否稳定闭环。分层后，每项结果都有清晰的任务分母和机制边界。

**表 4-2 实验层次与验证问题**

| 实验层 | 规模 | 任务内容 | 主要回答的问题 |
|:--|--:|:--|:--|
| 同任务效率对照 | 2 类 × 5 轮 × 4 配置 = 40 次执行 | Operating 5 件 + Financial 5 件 | 纯文本与 StateBus 在 Token、通信、耗时和质量上的差异 |
| 连续任务 | 2 类 × 10 轮 = 20 次执行 | 基础任务、长链扩展、schema drift、lineage 汇总 | 系统能否连续运行，历史记忆是否进入后续任务 |
| 记忆真实性 | 6 次执行 | 连续财务任务 + 不兼容记忆负例 | 候选、兼容、消费、效果、拒绝与重算是否可追踪 |
| 非文本状态 | 4 次 holdout | 长文本、表格对照、文本+表格 | 数值状态是否由另一进程消费并改变选择 |
| 能力覆盖 | 5 类共 25 次执行 | 抽取、趋势、跨表、聚合、异常 | 四角色、Python/DSL 和质量门是否闭环 |

## 结果总览

**表 4-5 答辩与说明书统一主结果**

| 验证维度 | 主结果 | 对应样本 | 结论定位 |
|:--|--:|:--|:--|
| 任务质量 | 95/95 正式任务执行通过 | 效率、连续、真实性与能力覆盖 | 全部机制结论的质量基线 |
| 总 Token | 33,974 → 17,870，**-47.40%** | 10 个同任务对照 | 完整链核心结果 |
| wire bytes | 36,069 → 12,677，**-64.85%** | 10 个同任务对照 | 完整链核心结果 |
| 总耗时 | 315.678 s → 295.728 s，**-6.32%** | 10 个同任务串行对照 | 完整链核心结果 |
| 结构化控制 | 相同 50 条消息，control bytes **-83.05%** | 纯文本 vs 结构化 | 通信专项 |

一句话结论为：在同任务、同模型、同角色链和同质量门的对照中，StateBus 将总 Token 降低 47.40%、wire bytes 降低 64.85%、10 任务总耗时降低 6.32%，并通过专项任务证明非文本状态跨进程真实消费和共享记忆跨任务实际使用。

## 完整链效率结果


**表 4-6 十个同任务整体对比**

| 指标 | 纯文本协作 | 完整 StateBus | 变化 |
|:--|--:|--:|--:|
| 任务数 / 质量通过 | 10 / 10 | 10 / 10 | 质量保持 |
| Agent 消息数 | 50 | 50 | 0 |
| control bytes | 25,196 | 5,357 | -78.74% |
| wire bytes | 36,069 | 12,677 | -64.85% |
| LLM 可见原始证据字节 | 73,266 | 11,687 | -84.05% |
| Prompt 可见字节 | 75,926 | 15,847 | -79.13% |
| Prompt Token | 29,876 | 13,885 | -53.52% |
| 总 Token | 33,974 | 17,870 | -47.40% |
| 10 任务总耗时 | 315.678 s | 295.728 s | -6.32% |

结果表明，完整 StateBus 的主要收益来自原始证据引用化、Prompt 可见上下文收敛和控制帧压缩。消息数保持 50 不变，因此 wire bytes 的下降不是靠少发消息获得。质量均为 10/10，说明该组节省没有以牺牲任务正确性为代价。

时延主结果统一使用全部 10 个匹配任务的总耗时。Operating 子集只作为工作负载亮点：5 个任务总耗时从 159.896 秒降至 131.551 秒，降低 17.73%，5/5 更快。该子集结果不替代系统总指标，也不与 -6.32% 并列为两个“整体时延”。

**表 4-7 相同消息数下的控制面结果**

| 指标 | 纯文本 | 结构化协议 | 变化 |
|:--|--:|--:|--:|
| 任务质量 | 10/10 | 10/10 | 保持 |

| control bytes | 25,196 | 4,270 | **-83.05%** |

## 非文本状态专项


**表 4-8 StateRef 机制真实性结果**

| 检查点 | 结果 | 解释 |
|:--|--:|:--|
| holdout 质量 | 4/4 | 两个长文本、一个表格对照、一个文本+表格任务全部通过 |
| 使用语义状态的任务 | 3 | 表格任务作为不强制状态的路由对照 |
| 物理数值选择对象 | 9 | 独立 float32 数值对象 |
| 跨 PID 消费回执 | 9/9 | producer 与 consumer 为不同进程 |

## 共享记忆专项


**表 4-9 自然连续任务记忆漏斗**

| 漏斗层 | 数量 | 相对 20 次查询 | 含义 |
|:--|--:|--:|:--|
| 全部查询 | 20 | 100% | 两组 10 轮任务 |
| 有候选 | 18 | 90% | 只说明检索到历史 |
| 通过兼容门 | 7 | 35% | 查询级可用记忆 |
| 真实消费并产生效果 | 7 | 35% | PPT 与说明书主指标 |
| 跳过执行步骤 | 2 | 10% | 可观察的重复工作减少 |

候选级共 48 条，其中 9 条兼容、39 条不兼容，拒绝率为 81.25%。9 条消费回执分布于 7 轮查询，一次查询可以消费多条记忆，因此“候选级兼容数”不能替代“查询级 actual-use”。两组连续任务质量为 20/20。

补充真实性用例共 6/6 通过，记录 23 条 consumption 和 23 条 effect，其中 Executor 8 条、Summarizer 15 条。故意放入的一个不兼容记忆被拒绝并触发当前任务重算；同时观察到一次跳过步骤和一次跳过 LLM call。该结果证明系统既能利用安全历史，也能拒绝不应复用的相似内容。

# 技术亮点与关键实现难点

## 核心技术亮点

StateBus 的核心创新并不是把四个 Agent 排成一个固定工作流，而是为多 Agent 之间建立一套可以验证、可以拒绝、可以恢复的系统对象模型。传统实现往往把上一角色的自然语言回答直接拼进下一角色 Prompt，角色之间虽然“有流程”，运行时却不知道一段文本究竟是计划、证据、授权还是结果。StateBus 将这些语义分别落实为 CanonicalTaskSpec、ApprovedPlan、EvidencePack、SemanticStateRef、ExecutionArtifactRef、ClaimSet 和 MemoryRef，并为每类对象规定产生者、消费者、hash、状态和校验条件。Runtime 统一维护对象从 proposal/candidate 到 approved、consumed、verified、committed 的变化，任何角色都不能仅凭一段自述把对象提升为可信状态。

这种对象化协作带来的直接价值是控制与数据可以分别优化。控制面只传递 operation、参数、能力、Ref 和回执，证据文本、稠密矩阵、程序输出与长期记忆保留在适合它们的载体中。Planner 的详细解释不需要在 Retriever、Executor 和 Summarizer 之间反复复制；Executor 也不需要重新解析整个对话才能判断允许访问哪些输入。通信专项在 50 条逻辑消息数完全相同的条件下，将 control bytes 从 25,196 降到 4,270，下降 83.05%。因此这项收益来自消息表示和对象引用的收敛，而不是通过减少 Agent、跳过步骤或降低任务质量取得。

结构化控制的另一层亮点是把协议帧与运行状态机连接起来。ControlHeader 让 trace、task、step、attempt 和角色身份贯穿请求、ACK、开始、心跳、终态与 GC；CapabilityGrant 将计划许可具体化为输入 Ref、输出合同、Validator、预算和有效期。系统能够明确区分“请求已经送达”“Worker 已完成前置校验”“执行仍然存活”“程序产生了候选输出”“候选产物已经验证”等不同事实。正因为这些状态互不混淆，失败时才可以只终止目标 attempt、保留已经验证的上游对象，并继续完成资源结算，而不是将一切折叠为一次无法定位的 Agent 调用失败。

非文本状态传递同时证明物理真实性和业务效果。Retriever 生成的 query/candidate embedding 以 float32 连续矩阵保存在 shared_memory 或 mmap 中，Protobuf 只传 SemanticStateRef；另一个 PID 依据 DenseSemanticStateContract 与 HydrateManifest 只读映射同一数值对象，返回 row index、candidate ID、score 和消费回执。Runtime 随后验证 producer/consumer PID、blob hash、encoder signature 与 decision surface。这样既排除了“把向量编码成 JSON 继续传文本”的做法，也排除了“创建了 embedding 文件但下游没有使用”的弱证明。正式状态实验中的 9/9 跨 PID 消费、9/9 改变选择以及发布/释放字节闭合，来自完整生命周期事件而不是间接推断。

共享记忆的创新点也不在于简单增加一个向量库。系统把关键词、标签和向量 RRF 用作候选召回，把任务意图、I/O schema、数据 manifest、lineage、runtime signature 与目标角色可见性作为硬兼容条件，再用 consumption/effect 记录是否真正进入当前角色以及是否改变执行行为。旧季度、旧字段或旧 Validator 即使具有很高相似度，也可以被拒绝并回到当前任务重算。正式结果中 20 次查询有 7 次 actual-use，同时 48 个不兼容候选中有 39 个被拒绝；这组结果体现的是“能复用，也能阻止错误复用”，而不是用宽松召回制造表面命中率。

CodeAct 则把 LLM 的适应性放进了操作系统和业务质量共同约束的执行链。模型产生的 Python 只是候选源码，需要先匹配 CapabilityGrant，再经过 AST/路径 Policy、non-root bubblewrap、只读输入与最小可写输出、资源上限、schema/expected facts/recomputation/provenance Validator，最后由 Commit Gate 决定是否形成 verified ArtifactRef。Transform DSL 为字段稳定的表格操作提供注册指令集，但继续使用相同的输入授权、workspace、产物和质量门。25 个正式能力任务由 18 个 bounded Python 与 7 个 DSL 覆盖，25/25 通过且 0 fallback，说明两条执行表示能够共存，而不是以硬编码答案替代模型执行。

项目最后将上述运行事实贯通到实验和产品界面。Runtime 事件、对象 hash、消费回执、Validator 报告和 Ledger 首先落入 Run 证据目录，再由汇总器生成固定证据快照；PPT、说明书与 Evidence Center 从同一快照读取正式数字，Live Studio 则从单次真实 Run 重建 Agent 输入输出、代码和验证过程。临时演示不会改写固定实验结果，界面也不需要为了动画虚构模型内部过程。实现、实验与展示由同一事实链连接，是 StateBus 从研究原型进一步形成可审计产品的关键基础。

## 关键实现难点与工程取舍

协议实现的难点在于，Protobuf 能证明消息“格式合法”，却不能证明请求“语义获准”。一个字段类型完全正确的 `ExecRequest` 仍可能指向错误角色、过期 Ref、未批准能力或被篡改的输出合同。StateBus 将这类检查分布在 PlanPolicy、CapabilityGrant 与 dispatch 前复核三处：计划阶段检查执行图和能力，授权阶段把 task/step/session/role/inputs/outputs/expiry 绑定到 hash，真正发送前再从当前对象重新计算。采用多处校验会增加少量固定开销，但它防止一次早期批准被后续对象替换所绕过，且能把拒绝定位到具体边界。


图 5-1 所示的三重校验不是重复执行同一段 schema 判断。PlanPolicy 面向模型提出的 DAG，限制步骤、角色、能力和预算；CapabilityGrant 面向一次具体 attempt，把批准计划投影成最小权限；dispatch 前复核面向发送瞬间的真实对象，重新确认 Ref 状态、manifest、hash 和有效期。三层输入和失败语义不同，分别防止非法计划、越权执行与 TOCTOU 式对象替换。为了让这组约束可以审计，每层都产生独立 report/hash，拒绝结果也写入结构化事件，而不是只抛出异常字符串。

跨进程状态的难点在于，低复制与可验证性通常存在张力。若只传共享内存名称，消费快速但缺少 schema 与来源；若把全部向量重新序列化到消息，验证容易却失去非文本直传的意义。项目选择“数值 blob + 小型合同 sidecar + Ref”的组合：blob 保持连续数值布局，sidecar 保存合同，Ref 在控制面建立身份。消费者仍需计算 hash 并检查矩阵，这带来固定校验成本，但避免 silent corruption、encoder 空间混用和过期对象复用。短期对象优先 shared_memory，需回放对象使用 mmap/CAS，也是性能、可恢复性和生命周期之间的折中。

多 Agent fan-in 和重试的难点在于对象身份必须跨步骤稳定，同时失败 attempt 不能污染新 attempt。系统将 step_id 作为业务节点、attempt_id 作为一次执行尝试，ApprovedPlan 的依赖边决定何时可以汇合输入；只有 verified 必需输入齐备才 dispatch。失败后保留可复用的 verified 上游对象，关闭当前 candidate 的提升路径，并为重试签发新 grant。这样没有采用简单的全链重跑，降低了重复计算，但也要求 Supervisor、Ref Registry、Workspace 和 Telemetry 对 attempt 有一致理解。


局部恢复还必须处理晚到事件与资源所有权。一次 heartbeat timeout 后，旧 Worker 可能稍后才发送 SuccessResult；如果只按 step ID 更新状态，旧结果就可能覆盖重试。StateBus 在所有控制帧、workspace、Grant、ArtifactRef 和事件中携带 attempt ID，Supervisor 只接受当前 attempt 的合法状态迁移。旧 candidate 被 invalidated 后仍保留诊断 hash，但不能重新提升；新 attempt 可以引用未变化的 verified 上游，并在新的 workspace 中执行。无论新旧 attempt 最终成功、失败、被取消还是 trapped，都进入同一 settlement/GC 路径，从而把恢复正确性与资源清理统一起来。

记忆复用的难点不是召回算法本身，而是判断“相似到什么程度才允许改变当前任务”。季度、币种、聚合粒度、字段版本、数据来源和 Validator 的任一变化都可能使历史结果失效。项目没有将这些条件压成单一相似度阈值，而采用硬兼容条件与 degraded assist 分支。该选择会使候选拒绝率看起来较高，也不会为了展示而制造高命中率，但它让 exact replay、validated replay 和 assist 的声明边界清晰，负例被拒绝后仍能沿正常路径完成任务。

CodeAct 的难点同时存在于运行安全和结果可信两个层面。AST 白名单无法替代操作系统隔离，bubblewrap 也无法判断营收计算是否正确；因此必须同时有 CapabilityGrant、静态 Policy、动态沙箱、workspace、业务 Validator 与 Commit Gate。正式 LLM 路径要求 bwrap readiness，宁可在环境不满足时明确失败，也不静默降级为宿主机执行。相应代价是更复杂的工作区准备和固定校验时间，但换来的是模型代码不会直接获得仓库、网络和任意写权限，错误结果也不会因进程正常退出而进入总结。

工程上还需要处理“安全通过但业务错误”与“业务上可修复但策略越权”两类相反情况。前者由输入/输出 Validator、独立重算和 citation/provenance 发现，后者在 AST/路径 Policy 阶段直接终止，不能交给模型以“修复计算”为由扩权。修复预算按 policy、runtime 和 quality 分开，每次新源码都重新计算 hash 并重走完整链。这样的设计比直接执行模型代码更重，但它使每次失败都能定位到授权、静态策略、系统隔离、程序运行或业务验证中的一个明确层次。

统一证据口径也是一个容易被低估的实现难点。同一指标可能同时出现在 Worker 事件、任务 summary、实验汇总、网页组件和 PPT 图表中；如果各处独立计算，分母、快照时点和失败样本处理很容易发生漂移。StateBus 将逐事件增量与任务终态快照分开聚合，并用 trace/task/step/attempt、对象 ID 和 hash 建立关联。Run 目录作为事实源，固定 evidence snapshot 作为展示发布物，实时 Run 只作为独立演示对象。


如图 5-3 所示，实验报告、PPT、Evidence Center 与说明书并不是四份手工维护的数据。Runtime 先产生 typed objects、events、receipts、Validator reports 与 Ledger，汇总器按固定分母形成 evidence snapshot，再由不同视图做适合场景的呈现。Live Studio 读取实时 Run，但不会回写正式快照。这一边界既保证评委看到的数字一致，也保留了工程人员追溯到单任务、单 attempt 和单对象的能力。

实验设计的难点在于端到端收益与机制真实性不能由同一数字替代。Token、wire bytes 和总耗时对照说明完整系统的整体效果，却不能证明某一个 StateRef 被使用；publish/consume 事件说明对象存在与读取，却不能证明选择发生改变；记忆候选说明召回，却不能证明实际消费。项目因此将 E1 的整体效率、E2/E3 的连续记忆、E4 的非文本真实性和 E5 的能力覆盖分开，并让它们共享 Telemetry。这样的证据结构比“用一个最好看的结果解释全部机制”更复杂，但能够把性能、正确性和真实性各自落到合适分母。

## 失败路径与恢复原则

系统把失败设计为可观察状态，而不是异常日志中的偶然分支。请求在进入 Worker 前失败时不会创建可执行产物；Worker 失联时由 attempt 和最后心跳定位目标进程；StateRef 校验失败时禁止消费并进入 release；记忆不兼容时不视为系统失败，而是记录原因并重算；CodeAct Policy 或 bwrap readiness 失败时程序不运行；Validator 失败时保留 candidate 与报告，但关闭下游可见性。所有路径最终都需要关闭 lease、workspace 与 Ref 台账，避免一次现场演示失败影响下一次 Run。

恢复控制器首先判断失败发生在计划前、dispatch 前、Worker 运行中还是产物验证后，再决定拒绝、重签 Grant、重试、replan 或结束任务。重试只适用于仍在任务预算内且输入合同未改变的步骤；输入 manifest 或输出合同已经变化时必须回到 replan，不能沿用旧 Grant。恢复前 Runtime 会冻结失败 attempt 的 candidate 和消费权，恢复后再以新的 attempt ID 重新建立 ACK/heartbeat lease。这个顺序使“可以重试”与“旧结果仍可写入”彻底分离。

资源结算不依赖业务是否成功。StateRef lease、Worker 进程组、workspace、候选 ArtifactRef 和 Memory commit proposal 都登记在 attempt 台账中；终态到来后，系统先关闭下游可见性，再完成对象 settlement，最后发出 GC。若 GC 本身被重复调用，Registry 和 WorkspaceManager 按幂等规则返回当前状态。Studio 的第二次运行因此获得新的 Run 根目录和事件序列，不会继续消费上一任务的旧 Ref 或界面状态。

| Artifact/Claim | 输出 schema、事实复算、provenance/citation 失败 | invalidated/unsupported，不给下游或长期记忆 | validator report、candidate hash、settlement |

# 总 结

StateBus v2 已从概念设计发展为可运行的多 Agent 基础设施原型。系统实现 Planner、Retriever、Executor、Summarizer 四角色协作，以 UDS + typed Protobuf 建立可验证控制合同，以 StateRef 和分层状态池传递非文本数值中间态，以 Compatibility Gate 约束共享记忆复用，并通过受限 Python CodeAct/DSL、工作区和提交质量门形成完整执行闭环。

固定实验基线完成 95/95 正式执行记录。在质量保持的 10 个同任务对照中，总 Token 降低 47.40%、wire bytes 降低 64.85%、总耗时降低 6.32%；通信专项在相同消息数下降低控制面字节 83.05%；非文本状态 9/9 跨 PID 消费并改变选择；共享记忆 actual-use 为 35%，同时拒绝 81.25% 的不兼容候选；五类 25 个能力任务全部通过，18 个受限 Python 和 7 个 DSL 均未触发 fallback。这些结果共同说明：StateBus 的优势不只在“少传文本”，而在把协作升级为低通信负担、可验证、可追踪、可安全复用的状态系统。

StateBus Studio 进一步把工程机制转化为可操作产品。固定证据页保证答辩、报告与网页数字一致；实时任务页展示类型化对象、Agent 输入输出、模型生成程序、验证回执和最终结论；白名单 API、单 Worker 队列与既有模型服务复用保证网页不会演变为任意命令执行入口。

后续工作包括：扩展更多行业任务与公开数据集；在更多硬件与并发条件下重复串行时延实验；增强长期记忆的压缩、失效和冲突解决；完善 Ref 租约与跨节点数据面；在保持“Engine-Local”边界的前提下研究 Prefix/KV 复用；补充 openEuler 上的一键安装、离线镜像与长期稳定性验证。所有未来能力在完成代码和实验前均不并入当前正式结论。
