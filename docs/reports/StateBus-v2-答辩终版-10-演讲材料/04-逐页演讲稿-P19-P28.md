## P20 实验设计：任务与四层验证｜约 40 秒

**演讲稿**

实验面向离线财报和经营数据分析，完整保留 Planner、Retriever、Executor、Summarizer 四角色链，输出不仅有数值结论，还包含来源、执行产物和验证结果。连续场景包含 Financial 与 Operating 两组任务，能力覆盖包括财报指标抽取、多期趋势、跨表关联、条件聚合和异常检测五类。

正式证据分为四层：40 次同任务效率配置，用于比较文本与 StateBus 各机制组合；20 次连续运行，由两组各十轮构成；10 次机制真实性用例，包括 4 个状态和 6 个记忆用例；25 次能力覆盖，检查五类任务和两条执行路径。合计 95 次正式执行，95/95 通过。

公平条件保持同任务、同输入、同模型、同四角色链、同 Validator，并串行运行。95 是正式执行记录数，不是 95 个不同任务；工程回归另计。

## P21 实验总览｜约 40 秒

**演讲稿**

在 10 个同任务、同模型、同角色链和统一质量门的串行对照中，两组任务质量都是 10/10，完整实验体系 95/95 通过。在质量保持的前提下，总 Token 从 33,974 降到 17,870，降低 47.40%；UDS 线路 wire bytes 从 36,069 B 降到 12,677 B，降低 64.85%；10 个匹配任务总耗时从 315.678 秒降到 295.728 秒，降低 6.32%。

下方三项是机制专项的锚点：结构化 control bytes 降低 83.05%；9/9 个非文本状态由不同 PID 消费并改变选择；共享记忆 actual-use 为 7/20，也就是 35%。

这里的收益不是减少 Agent 数量或砍掉协作步骤，而是减少每次交接中的重复文本、线路载荷和重建工作。

**讲述动作**

先指最上方质量等式，再从左到右讲 Token、wire 和总耗时，最后只点出下方三项机制，告诉评委后面逐页展开。

## P22 完整链与结构化通信专项｜约 40 秒

**演讲稿**

这页放了两组不同目的的实验。左侧 L0 对 L3 比较纯文本协作与完整 StateBus，重复上一页的三项总结果，并补充 Operating 子集的总耗时从 159.896 秒降到 131.551 秒，降低 17.73%，5/5 任务更快。

右侧 L0 对 L1 只看结构化协议。两组都是相同的 10 个任务、50 条 Agent 逻辑消息、质量 10/10；消息数没有减少，但 control bytes 从 25,196 B 降到 4,270 B，降低 83.05%，wire bytes 也降低 68.95%。这说明节省来自每次交接的控制载荷变小，而不是人为减少协作轮次。

L0、L1、L3 只是配置标识，不能把这两组图解释成严格的逐层相邻消融；完整链和控制面专项回答的是两个不同问题。

## P23 非文本状态专项｜约 35 秒

**演讲稿**

非文本状态实验的判断标准不是“是否发布了向量”，而是物理对象是否被另一进程读取、使用，并在结束后释放。4 个 holdout 任务全部通过，其中 3 个任务使用语义状态，1 个表格任务作为不强制状态的路由对照。

3 个语义任务共发布 9 个 `float32` 状态。9/9 都有 producer PID 不等于 consumer PID 的真实消费回执，9/9 都改变了下游选择，共选中证据 27 次；发布的 294,912 B 最终全部释放，生命周期闭合。

因此这组证据同时覆盖物理真实性、行为有效性和资源结算，而不是把“配置了 shared memory”当成实验结论。

## P24 共享记忆专项｜约 40 秒

**演讲稿**

两组自然连续任务共 20 轮，质量 20/20。左侧使用查询级分母：20 次查询中，18 次找到候选，但只有 7 次候选真正进入 RoleView 并留下消费与行为效果，因此 actual-use 是 7/20，也就是 35%；其中 2 次可观察地跳过了执行步骤。

右侧使用候选级分母：48 个候选经过 Compatibility Gate，9 个兼容，39 个因为任务、schema、lineage 或 Runtime 条件不满足而被拒绝，拒绝率 81.25%。负例也证明，即使语义相似，只要任务签名不兼容，系统会拒绝历史并按当前输入重新计算。

所以 18/20 是“找到候选”，不能包装成复用率；7/20 才是实际使用。39/48 的拒绝也不是失败，而是系统防止历史污染的安全行为。

## P25 系统完整性｜约 35 秒

**演讲稿**

最后这页证明 StateBus 不是围绕一个样例写的脚本。五类 25 个能力任务全部通过统一 Validator；其中 18 个使用受限 Python CodeAct，7 个使用结构化 DSL，fallback 为 0。两组连续任务共 20 轮全部通过，25/25 能力任务都观察到四角色进入主链。

固定基线还包含 `tests/v2` 的 558 项完整回归，以及 openEuler 24.03 LTS-SP3 单容器验证。18 和 7 只是 Executor 执行表示的任务分布，不是 Python 与 DSL 的优劣比较。

从任务能力、执行路径、连续运行到交付环境，系统使用的是同一套 Runtime、对象合同和质量门。

## P27 作品演示播放｜约 90 秒

**演讲稿**

这里先看系统健康状态，vLLM、Embedding 和单 Worker 队列都由后端检查。我们选择白名单中的运营指标 IQR 异常检测任务并开始运行，浏览器提交的是 recipe ID，不是任意 Shell 命令。

任务开始后，上方流程会沿 Planner、Retriever、Executor、Summarizer 动态推进。Planner 的输入是预编译 TaskSpec，输出需要经过 PlanPolicy 批准；Retriever 形成 EvidencePack，并发布语义状态；不同 PID 的消费者返回 selected IDs 和状态回执；Executor 根据 CapabilityGrant 生成或选择 Python/DSL，经过 Policy、隔离执行和 Validator 后形成 verified Artifact；Summarizer 只读取验证产物和证据引用，形成最终 ClaimSet。

下方详细区可以看到当前 Agent 的类型化输入、转换和输出。切换到程序记录，可以查看实际 Python 或 DSL、策略审计和产物 hash；切换到质量与回执，可以看到 StateRef 消费、Artifact Validator 和最终质量门。页面动画来自 SSE 和 task-flow 中的真实事件，不展示或伪造模型内部思维过程。

任务完成后，我们查看最终结论和质量状态。点击“新建运行”只清空当前工作台，历史 Run 和磁盘证据仍保留，可以再次选择任务运行。
