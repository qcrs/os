# 逐页演讲稿：P10—P18

这一册覆盖非文本状态、共享记忆、CodeAct 和三项技术难点，建议用时约 4 分半。这里最容易出现概念越界：不要把 SemanticStateRef 讲成 KV cache，也不要把记忆候选数讲成实际复用数。

## P10 亮点二：非文本状态成为 Runtime 对象｜约 35 秒

**演讲稿**

许多系统已经能生成 embedding、保存到共享内存，再返回一个 handle。但这最多证明“有一个矩阵被创建”，不能证明另一个角色读到了正确对象，更不能证明它改变了后续行为。

StateBus 把连续 `float32` 载荷、状态合同和可信引用组合成一个 Runtime 对象。合同记录类型、来源、布局和编码空间，`SemanticStateRef` 负责把这些身份与物理载荷绑定。随后我们要求三类证据同时成立：对象是二进制数值并跨 PID 消费；Selector 真正执行 top-k 并返回 selected IDs，从而改变后续证据面；发布、消费、回执和释放形成完整生命周期。

这里的事实边界也很明确：它不是 hidden state 或 KV cache，LLM 不直接读取 embedding。LLM 读取的是 Runtime 根据数值选择局部加载后的原始证据。

## P11 非文本状态的机制实现｜约 40 秒

**演讲稿**

左侧 Retriever 作为 Producer，生成 query 和候选 embedding，把它们按行写成连续 `float32` 矩阵，并发布 `SemanticStateRef`。矩阵本身留在 StatePool 的 shared memory 或 mmap；UDS + typed Protobuf 控制通道只传 Ref 和当前步骤授权。

右侧 Selector 在不同 PID 中打开 Ref。它先校验 dtype、shape、hash、encoder signature、manifest 和 lease，再只读映射同一矩阵，执行数值 top-k，返回 selected IDs、行号、分数以及 producer/consumer PID。Runtime 根据 selected IDs 局部恢复 EvidencePack，Executor 或 LLM 只看到被选中的可追溯原始证据。

因此对象连续性可以被核验：`float32` 不变、shape 不变、载荷 hash 一致、编码器签名一致、状态身份一致。实验中 9/9 个状态跨 PID 消费并改变选择，发布和释放字节也完全闭合。

**讲述动作**

按“左侧 Producer → 中间 StatePool → 右侧 Consumer → 下方 EvidencePack”指图，不要从每个 sidecar 字段逐字念起。

## P12 亮点三：候选命中不等于共享记忆复用｜约 35 秒

**演讲稿**

普通共享记忆常见的流程是：对当前查询做向量排序，把 top-k 历史直接拼进 Prompt。这个流程只能证明“检索到相似候选”。同一家公司、同一个指标甚至相似的句子，都不代表期间、schema、数据来源和运行条件兼容。

StateBus 把候选召回、兼容分类、角色重绑定、真实消费和行为效果分成不同事实。候选先经过 Compatibility Gate，不兼容就拒绝并按当前输入重算；兼容记忆也只向获准角色生成最小 RoleView；只有真正进入角色请求并留下消费记录，才计入 actual-use；是否改变选择、减少工作或跳过步骤，再单独记录效果。

所以这一页最重要的数字边界是：18/20 找到候选，只能叫召回覆盖；真正的主指标是 actual-use 7/20。

## P13 共享记忆的机制实现｜约 40 秒

**演讲稿**

左侧是候选召回。SQLite FTS 提供关键词排名，元数据做标签过滤，FAISS 或余弦提供向量排名，RRF 将多路名次融合成稳定候选顺序。RRF 只决定“先检查谁”，没有复用授权。

中间是 Memory Passport 和 Compatibility Gate，它核对任务意图、字段与指标口径、数据 manifest、lineage、Runtime 和 Validator 条件。根据结果，候选可以被拒绝、降为辅助参考，或者允许验证复用。拒绝不是任务失败，而是记录原因后使用当前输入正常重算。

右侧才是角色输入和使用记录。通过的记忆被重绑定到当前 RoleView；系统记录哪个角色、哪个步骤消费了哪个 `MemoryRef`，再观察它是否改变选择、减少工作或跳过步骤。生成过视图但没有进入真实请求，不计 actual-use。

**收束句**

融合排序负责“先看谁”，兼容门负责“能不能用”，消费记录负责“是否真的用了”，效果记录负责“用了以后发生什么”。

## P14 Executor 扩展：CodeAct 与可信产物｜约 40 秒

**演讲稿**

CodeAct 解决的是准确计算任务里“答案看起来合理但不可验证”的问题。模型可以生成 Python，但源码本身没有可信身份，进程退出码为零也不代表业务结果正确。

因此 Executor 只在 CapabilityGrant 允许的输入和 workspace 内生成候选程序。第一道门检查 AST 和 Policy，拒绝危险导入、动态执行、路径穿越和未授权文件；第二道门使用非 root bubblewrap，关闭网络、只读挂载输入、只允许输出目录写入并限制资源；第三道门检查输出 schema、必需字段、数值事实、独立重算和来源链。

任何策略、运行或质量失败都只产生结构化错误摘要，并在不扩权的前提下进行有限修复，新源码还要重新走完整链。唯一能离开工作区、进入 Summarizer 或 Memory 的，是 verified `ExecutionArtifactRef`。

## P15 技术难点章节页｜约 3 秒

**演讲稿**

我们把关键难点归纳为执行语义、状态可信和跨任务兼容三类。

## P16 难点一：格式正确不等于真正获准｜约 40 秒

**演讲稿**

Protobuf 可以验证字段类型和消息结构，但无法回答“这个角色此刻是否真的有权使用这些对象”。StateBus 用三道不同的检查把模型提议逐层收窄。

第一道是 PlanPolicy，检查执行图是否成立、角色与能力是否匹配、依赖和预算是否合理。第二道是 CapabilityGrant，把任务、步骤、尝试、角色、输入、输出、Validator、有效期和 hash 绑定为一次最小授权。第三道发生在发送瞬间，重新检查输入 Ref 是否仍为已验证状态、清单和 hash 是否一致、lease 是否过期。

任一检查失败，系统只能有限重规划或拒绝并记录原因；三层全部通过，当前请求才进入 Worker。Protobuf 保证“消息长得正确”，三重校验保证“这个角色此刻确实有权完成这一步”。

## P17 难点二：低复制与状态可信如何同时成立｜约 40 秒

**演讲稿**

非文本状态存在两个错误极端。只传共享内存名称，复制很少，但没有类型、来源和对象身份；把完整矩阵重新塞进消息，容易整体校验，却失去了非文本直传和低复制的价值。

StateBus 的折中是三件东西绑定在一起：连续数值 blob 保存真实 `float32`；小型 sidecar 解释类型、来源、布局和编码空间；`SemanticStateRef` 建立可信身份。消费者在打开前逐项核对任务与状态 ID、producer 与原始输入、载荷 hash、dtype/shape、encoder signature、lease 和释放状态。通过才只读映射，不通过则拒绝、重算或回收。

所以 StateRef 不是一个文件名，也不是普通指针；它是连接物理载荷、解释合同、对象身份和生命周期的可信引用。

## P18 难点三：相似历史为什么仍可能被拒绝｜约 40 秒

**演讲稿**

这页把语义相似度和业务兼容性放在两个维度上。高相似但不兼容是最危险的区域。比如当前任务问 ACME 2026Q2 营收，历史记忆是 2026Q1 营收 42.3M，相似度可以达到 0.92，但期间不同，旧数值不能直接改变当前结论，系统必须拒绝并重算。

只有相似且任务意图、期间、币种、聚合粒度、schema、manifest、lineage、Runtime signature、Validator 和目标角色可见性都满足当前合同，历史策略才有资格进入 RoleView，而且仍需通过当前任务质量门。兼容但证据不足的候选只能作为受控参考；不相似且不兼容的直接忽略。

共享记忆真正困难的不是召回更多历史，而是在允许安全历史改变当前任务的同时，阻止相似但过期或口径不同的结果污染执行。
