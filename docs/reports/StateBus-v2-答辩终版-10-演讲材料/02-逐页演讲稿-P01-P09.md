## P04 一条文本通道的三类问题｜约 40 秒

**演讲稿**

传统多 Agent 工作流通常只有一条文本 handoff。Planner 先传目标和计划，Retriever 再把全文证据追加进去，Executor 继续追加工具和执行历史，到了 Summarizer，整条链的上下文越来越长。

真正的问题不只是 Token 多，而是三类不同对象被压进了同一条文本通道。控制合同变成自然语言后，下游要重新解释能力、预算和输出边界；embedding 或候选矩阵变成数字列表、摘要以后，下游要重新编码，也无法证明谁消费了它；历史经验被直接拼入当前上下文后，语义相似很容易被误当成可复用。

所以这里有三类系统成本：通信负担膨胀、非文本对象反复重建，以及历史复用边界失控。StateBus 的出发点，就是不再让一种载体承担所有语义。

**转场**

为了说明这不是抽象的架构问题，我们用一条真实的连续财报任务来看四个角色到底需要交付什么。

## P05 三轮跨期财报任务｜约 40 秒

**演讲稿**

这是一条三轮因果任务链。R1 从原始财报中提取 ACME 2026Q1 营收，得到验证事实 120；R2 提取 2025Q4 营收，得到 109；R3 绑定前两轮的证据和 lineage，计算出差值 11、环比增长 10.09%。

四个角色各自负责不同工作：Planner 固定公司、期间、指标和输出合同；Retriever 定位原始证据并召回候选；Executor 用受限 Python 或 DSL 计算，产生执行产物；Summarizer 形成带引用的 ClaimSet，并决定是否生成记忆候选。

这条链最终必须同时满足四个交付标准：口径正确、证据可追溯、计算可验证、结果可复用。也就是说，我们既不能只追求少传文本，也不能为了复用而放松质量门。

**转场**

围绕这四个交付标准，StateBus 给出的不是四个独立插件，而是一个统一 Runtime。

## P06 StateBus Runtime 总体回答｜约 45 秒

**演讲稿**

这页是整套系统的总地图。最上方仍然是 Planner、Retriever、Executor、Summarizer 四角色，角色负责计划、检索、执行和总结。变化发生在角色之间：它们不再直接搬运完整上下文，而是由 StateBus Runtime 负责校验、授权、引用、回执和提交。

Runtime 内有三条相互关联的对象链。第一条是控制合同：TaskSpec 经过 Policy 审查，形成针对当前步骤和尝试的最小授权，Worker 再返回 ACK 或 Result。第二条是非文本状态：真实 embedding 和矩阵留在 StatePool，控制面只传 `SemanticStateRef`，不同 PID 的 Selector 打开并消费，再返回 selected IDs 和回执。第三条是验证产物与记忆：Executor 的文件先形成 `ExecutionArtifactRef`，通过 Validator 后才可信；历史也只有兼容后才能提交到下一任务。

一句话概括：Agent 处理本阶段的语义，Runtime 决定哪些对象能进入、怎样消费、何时可信以及失败后去哪里。

**讲述提示**

图中 PPT 使用 `StepGrant` 表示面向步骤的授权；实现中对应的是绑定 task、session、step、attempt 和输入 Ref 的 `CapabilityGrant`。现场不必展开类名差异，除非评委追问。

## P08 亮点一：结构化通信不是只有固定字段｜约 35 秒

**演讲稿**

一般结构化协议解决的是“消息能不能被机器解析”，例如来源、目标、动作、参数和结果字段是否合法。StateBus 在此基础上再推进一步：协议字段要连接 Runtime 的 Policy、状态机和对象生命周期。

因此一次消息不只是一个 JSON 或 Protobuf 包，而是一段可执行生命周期。任务、步骤和尝试身份贯穿请求、ACK、心跳、终态与释放；角色、能力和输入引用形成最小授权，越权请求可以在执行前拒绝；输出合同和 Validator 决定结果能否被下游消费；失败则保留重规划、拒绝和原因码。

亮点不在“使用了 Protobuf”，而在于消息从字段合法升级为语义获准，返回结果也要经过验证后才能成为可信对象。

## P09 结构化通信的机制实现｜约 40 秒

**演讲稿**

左边有两类提议来源：预编译的 `CanonicalTaskSpec` 固定任务身份、输入清单和输出要求；Planner 只能提出步骤、依赖、建议能力和预算。Planner 的输出还不是执行权。

中间的 Policy 把提议收窄为最小控制合同，它要回答五个问题：这是哪个任务和尝试，允许哪个角色使用哪项能力，只能读取哪些已验证对象，必须交付什么输出，以及预算和有效期是多少。全部通过后才签发面向当前 step/attempt 的 Grant；可以有限修复的只重新提交受约束内容，无法通过则记录原因，根本不进入 Worker。

右边是 RoleView。同一任务会被投影成不同的最小视图：Retriever 只看到检索目标和数据范围；Executor 只看到执行能力和获准输入；Summarizer 只读取完整 EvidencePack 与已验证产物。这样模型仍可做语义决策，但无法通过自然语言扩大权限。
