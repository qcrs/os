## 1. 结论先行

截至当前归档，最准确的整体描述是：

> StateBus v2 已形成四角色、类型化控制、StateRef 语义状态、共享记忆/回放、任务工作区和评测的功能原型；P0/P1 留有多条实际执行记录。它已经可以展示机制和任务闭环，但尚不能作为“全部阶段全绿、纯协议载体单独带来优势、Agent 间 KV/隐藏状态迁移、或 openEuler 最终交付已完成”的结论。

把结果按可信程度分层，结论更容易理解：

```text
代码实现  ──>  有执行记录  ──>  有原始产物/指标  ──>  有下游行为  ──>  有公平重复 A/B
   |               |                  |                    |                    |
   |               |                  |                    |                    +-- 最强，可谈因果收益
   |               |                  |                    +-- 可谈某路径被使用
   |               |                  +-- 可核查数值和质量门槛
   |               +-- 可谈功能跑过
   +-- 只能谈设计存在

StateBus 当前最强：记忆/回放的分级记录。
中等强度：类型化 UDS、三种状态后端、StateRef 的发布与水合。
仅遥测或诊断：LogitState、loopback 后端、单次时延。
尚未完成：openEuler 最终交付、全新完整全绿矩阵、Agent 间 KV/隐藏状态迁移。
```

## 2. 如何读本报告中的“通过”和“效果”

实验报告中的词很容易造成误解，下面先给出统一解释。

| 术语 | 在本报告中的意思 | 不代表什么 |
| --- | --- | --- |
| 质量通过 | 该任务通过了记录的确定性检查、事实覆盖或质量门槛 | 不自动代表开放式人类主观质量全面更好 |
| 状态发布/水合 | 某状态被登记、传递，且接收端根据引用读取了内容 | 不自动代表下游角色因它而改变决策 |
| 记忆命中 | 检索到相似历史记忆 | 不自动代表少调用模型、少跑工具或节省时间 |
| 经验证回放 | 历史对象通过当前任务所需的兼容性/验证规则后被采用 | 不等于所有步骤都跳过 |
| 完全回放 | 任务与历史对象满足更严格匹配条件 | 仍需看具体输出、产物和跳过步骤记录 |
| 词元/字节减少 | 当前系统看到或发送的文字量较小 | 不自动代表端到端耗时更小 |
| 时延更小 | 在可比条件下的任务时间更短 | 需要匹配任务、模型、服务负载和缓存政策的串行重复才可作结论 |

全文坚持如下阅读原则：

```text
质量相同 + 词元更少        => 可以谈“记录中的文本负担较低”
质量相同 + 实际跳过步骤    => 可以谈“该案例存在复用带来的减少工作”
一次耗时更短              => 只能当观察值
多次匹配且控制变量一致更短 => 才可能谈时延优势
```

## 4. 任务、数据集与实验层级

### 4.1 任务集：横向题型与纵向连续链同时存在

```text
                 横向任务覆盖                         纵向状态/记忆验证

    25 个独立正式样例、5 类任务                 8 条连续链、每条 10 轮
    --------------------------                 ----------------------
    财报指标提取：8                              CSV 表格画像
    多期趋势分析：5                              跨期财务分析
    跨表关联分析：5                              CSV 相关性回放
    条件聚合：4                                  长文档指标回放
    异常检测：3                                  长文档表格
                                                   网格状态世界
                                                   事件诊断
                                                   前缀缓存探针

    回答：系统题型覆盖够不够？                   回答：状态和记忆能否跨轮积累？
```

25 个正式样例用于覆盖不同数据操作和推理形状；十轮连续任务用于验证前一轮产生的画像、策略、指标、产物和记忆是否能在后续轮次被检索、验证和使用。两者不是重复计数，也不是任选一个即可。

直接对应赛题“至少两组关联性连续任务、每组不少于 10 轮”的核心记录是：

- `csv_table_profile`：疾病表与天气表之间复用字段画像、缺失处理、异常检测和清洗策略；
- `cross_period_financial`：在 ACME/BETA 跨季度收入提取、比较和趋势分析中复用指标事实与经过验证的执行策略。

八条连续任务族的设计用途和证据位置如下。每一族的清单都定义 10 个有依赖关系的轮次，因此连续任务定义一共是 80 轮；加上 25 个独立正式样例，仓库中的任务**定义**总数为 105。这个数不能误读为“某一次实验一次性执行了 105 个等强度样本”：正式矩阵、两条核心连续链、后续刷新和前缀探针分别在不同阶段执行，记录数以阶段总表为准。

| 连续任务族 | 十轮主要考察什么 | 归档证据应如何使用 |
| --- | --- | --- |
| CSV 表格画像 | 字段画像、缺失处理、异常检测、清洗产物及跨数据集策略复用 | Stage 04 核心链，L0--L3 均为 10/10 质量通过 |
| 跨期财务 | 多公司、多季度的指标提取、比较、趋势分析与执行策略复用 | Stage 05 核心链，L0--L3 均为 10/10 质量通过 |

### 4.2 实验层级：L0 到 L3，以及诊断层 T2

```text
L0  纯文本交接、全量材料、无语义裁剪、无回放
 |
L1  在 L0 上只增加类型化控制
 |
L2  在 L1 上增加语义选择、StateRef 与按引用水合
 |
L3  在 L2 上增加记忆检索、验证与回放策略
 |
T2  诊断对照：保持与 L2 相同的语义选择，但用文本交接而非语义 StateRef

L0 -> L1：控制协议本身的工程效果
L1 -> L2：证据裁剪和非文本状态路线
L2 -> L3：记忆/回放路线
L2 <-> T2：尝试区分“选得更少”与“使用非文本引用”
```

T2 是诊断层，不能与 L0--L3 正式阶梯混为一条结论。它的意义是防止把“先筛掉无关证据”带来的收益误写成“传了神经状态所以收益”。

### 4.3 指标如何放在同一张表里读

不是每个阶段都测了同一类东西。把没有采集的值填成 `0` 会制造错误结论，因此后文表格使用下列约定：

| 指标 | 含义 | 适用阶段 | 不能据此说明什么 |
| --- | --- | --- | --- |
| 提示词词元 / 总词元 | 该阶段任务记录中模型输入文字量 / 输入加输出文字量的累计值 | 有任务指标行的阶段 | 不自动等于网络字节、协议字节或端到端时延 |
| 前缀命中率 | 已记录命中数除以查询数；Stage 09/10/18 为引擎计数器，其他任务阶段为任务侧观测字段 | 有命中与查询分母的阶段 | 不可横比为“模型质量”；不同层的提示长度和服务历史不同 |
| 任务耗时 | 任务行的 `task_ms` 累计或均值 | 有任务指标行的阶段 | 未做串行匹配 A/B 时，不能作为时延优势 |
| TTFT | 从请求发出到首个词元的时间 | 09、10、18 前缀探针 | 不是整项多角色任务用时，也不能证明 Agent 间 KV 迁移 |
| 质量通过 | 确定性检查、事实覆盖和质量门槛均通过 | 有任务质量门的阶段 | 不等同开放式人工评测的全面优势 |

后文将“未采集”明确写为 `--`，将“有记录但不具可比性”的耗时写为“观察值”。这是为了让新读者一眼区分“没有数据”“有数据但不能比较”和“可以做同条件比较”。

### 7.1 Stage 03 的回放分类结果


这是当前较强的一组机制证据，因为分类、产物、步骤和质量检查是分开保存的。它支持“在该批有资格的回放案例中，系统记录到了经过验证的回放、产物复用和跳过步骤”。

它仍不支持两个夸张说法：

- 不能把所有“记忆命中”都当作“跳过步骤”；
- 不能把 Stage 03 的聚合值推广成所有未来任务都会减少同样数量的模型调用或时间。

### 7.2 连续任务中的回放应如何理解

连续任务并不是每一轮都应该回放。以跨期财务链为例，提取“某公司某季度某指标”的策略可以在合同相同的轮次中经验证复用；但后续的趋势计算、跨公司比较和最终报告仍需要基于当前轮的事实重新组合。因此好的连续任务设计应同时有：

```text
可复用：字段画像、缺失策略、已验证执行模板、已核验的指标事实、产物清单
必须重新做：本轮特有输入核验、新事实抽取、输出合同检查、最终组合判断

如果所有十轮都直接返回历史答案，不能证明系统会协作；
如果每轮都完全重做，也无法验证记忆复用。
```

## 8. 结果分析：多进程、状态后端与 StateRef

### 8.1 UDS 子进程路径

P0 Stage 07 在正式任务上留下 100 条 StateBus 记录，质量为 **100/100**。它表明类型化 UDS/子进程执行路径确实被运行到，而不是只有协议定义文件。

这是一条功能证明，不是 IPC 性能证明：当前不是四个角色都必然各占一个独立进程，也没有同一任务下“本进程 vs 子进程”的匹配时延 A/B。

### 8.2 三种状态后端矩阵

P1 Stage 16 记录 75 条任务，质量为 **75/75**，覆盖三种状态后端：

| 变体 | 请求后端 | 实际后端 | 进程边界 | 结论 |
| --- | --- | --- | --- | --- |
| `mmap_loopback` | `mmap` | 文件映射 | 本进程回环 | 文件映射状态路径可用 |
| `shared_memory_loopback` | `shared_memory` | 共享内存 | 本进程回环 | 共享内存状态路径可用 |
| `memfd_subprocess` | `memfd` | 匿名内存文件 | 子进程 | 有限的子进程状态路径可用 |

```text
mmap_loopback          shared_memory_loopback        memfd_subprocess
主进程 -> 主进程       主进程 -> 主进程              主进程 -> 子进程
      |                       |                             |
  功能可用                  功能可用                    功能可用 + 外部边界

前两项不能证明跨进程共享内存；三项都不能据此宣称谁更快。
```

### 8.3 StateRef：记录到“接收端读取”，尚未记录到“影响决策”

审计累计到的运行时事件为：

```text
STATE_PUBLISHED  = 1,380    状态被发布/登记
STATE_HYDRATED   = 4,140    接收端按引用读取并恢复对象
STATE_CONSUME    = 0        没有独立的“被哪个角色/字段使用并影响决定”事件
```

这已经能证明状态引用不是只写在设计图里：发布和接收端水合均有记录。可它仍留下一个关键逻辑缺口：某角色可以把状态读进来，却完全不根据它选择工具、路线或输出。因此当前证据停在“传递与水合”，不能上升为“非文本状态已被证明改变下游行为”。

后续应给每次消费记录如下链路：

```text
StateRef 编号 -> 接收角色 -> 读取的字段/对象 -> 路由或工具选择 -> 产物/答案
                                  |
                                  +-> StateRef 关闭或字段扰动后的对照
```

## 9. 结果分析：前缀缓存、KV 与 LogitState

P0 的前缀观测记录为：

| 条件 | 命中/查询 | 重算命中率 | warm TTFT 均值 |
| --- | ---: | ---: | ---: |
| 共享前缀（Stage 09） | 1,376 / 1,769 | 77.78% | 262.67 ms |
| 独立前缀（Stage 10） | 0 / 1,810 | 0.00% | 2,315.24 ms |

P1 Stage 18 进一步保留两份语料、四组 AB/BA 顺序的配对请求产物。聚合后共享条件为 5,691/7,553（75.35%），独立条件为 66/7,571（0.87%）；四个已保留配对的请求合同均可通过修复后的静态校验。

这些数字直观说明：相同前缀在**同一推理引擎**内的缓存计数更高，这是预期的引擎行为。但它们不能直接成为 StateBus 通信收益：

```text
可以说：同引擎、同会话/模型/分词器、相同前缀时，观察到较高的前缀命中。

不能说：Agent A 把 KV cache 传给了 Agent B。
不能说：StateRef 搬运了隐藏状态。
不能说：当前记录已经公平证明整体任务时延更快。
```

原因有两个：第一，前缀缓存绑定引擎、会话、模型、分词器和前缀哈希；第二，P1 Stage 18 明确记录 `clean_service_requested=False`，服务窗口为连续服务，而不是每个重复都干净重启。缓存暖机和请求顺序因此会混入 TTFT 观察。更严谨的下一步是分别跑“每轮干净服务”和“连续服务”两组实验，每组对每份语料做四组 AB/BA，并保存前后计数器。

### 9.2 LogitState：当前是输出不确定性遥测，不是神经状态交接

LogitState 会从模型返回的候选词元对数概率生成紧凑概率负载，并计算熵、置信度代理、最高不确定位置、熵方差等指标。它的设计目标是为未来的“低置信度复核/路由”提供输入。

当前归档记录显示：

```text
带正 logit_state_transfer_count 的主记录行：848
transfer_count 总和：848
持久化 logit_state_bytes 的有效记录行：0
记录名中含 LOGIT 的遥测事件：0
置信度门触发总和：0
```

所以目前只能说“系统记录了来自 top-logprob 的不确定性指标投影”。没有持久化负载字节数/哈希，也没有引用登记、接收角色、消费事件、路由/工具/重试效果或开关 A/B。因此它不是已完成的非文本状态闭环，更不是隐藏状态或 KV cache 传输。

## 10. 时延和通信结果应如何解读

### 10.1 已有的积极信号

- P0 的连续 CSV 和跨期财务链，L2/L3 均记录到比 L0 更低的提示词/总词元，同时质量门槛保持通过。
- Stage 02、12、13 形成了同题系统级比较及重复记录。
- P1 Stage 17 继续在 CSV、长文档、跨期财务、财报和事件诊断上记录 L0/L1/L2/L3/T2；StateRef 压力摘要为 6 个任务族中 5 个通过压力判定、1 个仅诊断性，累计可见提示节省 13,112 字节。

### 10.2 为什么当前不能写“时延优势”

审计给出的结论很明确：三个串行 P0 比较的任务时间差中，**0/3** 对 StateBus 有利，并且原始汇总显式写入 `latency_superiority_claim_allowed=False`。

```text
当前证据链

文本/提示负担降低  ---->  已有多个任务族记录
          |
          +----> 端到端时延降低？
                    |
                    +-- 当前：不能成立为正式优势结论
                        原因：三次串行比较没有一个给出有利任务时间差，且控制变量不完全冻结
```

这不是说系统一定更慢，而是说现有证据不足以判断“更快”。模型服务排队、缓存冷热、网络/API 波动、工具时间、提示排布、语义选择、比较器实现差异都可能改变总时间。正确做法是新建一套匹配实验：同一任务、同一模型、同一证据、同一工具、同一评分、同一缓存策略；串行 AB/BA 轮换，报告中位数与尾延迟，而不是从词元减少推断时延减少。

## 12. 推荐的后续实验顺序

这些工作有先后依赖，不应先跑一轮大矩阵再补日志字段：

```text
1. 补 StateRef 消费与 LogitState 链路日志
       |
2. 修复并回归：角色调用统计、回放账本、Stage 18 校验器、指标分母
       |
3. 冻结文本 vs 结构化的单变量合同，做串行 AB/BA 重复
       |

       |

       |
6. 在 openEuler 制作不可变交付包和提交清单
```

每一步都应产出可单独审阅的原始文件：任务清单、配置、运行日志、逐案例指标、评分结果、哈希、分析脚本版本和结论边界。这样即使后续某一阶段失败，也不会污染前一阶段已确认的证据。

## 14. 总结

当前实验的价值在于：它没有只展示一条“看起来能跑”的链路，而是把正式任务、两条核心十轮连续任务、回放、UDS、三种状态后端、前缀探针、泛化检查和比较重复都纳入了可追溯账本。较强的结果是：任务质量门槛、连续任务闭环和分级回放记录；较弱但已落地的结果是：StateRef 水合、多进程状态路径和引擎前缀观测；尚待补足的是公平因果比较、状态消费证据、最终部署交付和完整全绿复跑。

因此，下一阶段不应再堆叠更多未隔离的机制，而应把“状态是否实际改变决策”“结构化载体是否在冻结条件下有效”“前缀缓存是否在明确服务政策下可复现”“最终系统能否在 openEuler 交付”逐项做成可复查证据。
