## 1. 当前对象重述

  当前对象不是“证明 rich state_ref 已经低开销胜出”，而是先判断 StateBus benchmark 是否能公平支撑赛题三条 claim：低开销通信、非文本状态传递、共享记忆复用。赛题原文要求同任务条件下比较纯文本与结构化协议，并统计消息、文本开销、非文本状态规模、任务耗时、记忆命
  中与性能提升，docs/reference/题目.md:1。

  当前实现对象可以成立为 host-side prototype：有多 Agent、protocol/text 双模式、StateRef、memory、eval runner。但 claim 必须分层。README 已经写明：state_transfer 机制真实性支持为 typed non-text handoff authenticity，低开销效率 claim 尚未被当前 rich
  state_ref 支持；assist_only 也不能打包成 memory headline，README.md:187。

  ## 2. 当前 benchmark 问题清单

  1. text_brief 不是自然文本 baseline。它由同一套 feature_bundle/decision_packet 派生，含 route、tool、confidence、signals、tags、candidate 等字段；本质是 structured packet 的 textual shadow，agents/sample_agents.py:395、runtime/executor_runtime.py:1188。
  2. natural_handoff_text 也还不够自然。它虽然写成短自然文本，但生成时直接读 decision_packet.route 和 decision_packet.tool_name，所以仍泄漏结构化决策，runtime/executor_runtime.py:1435。
  3. 全局 text/protocol aggregate 不可作为结论。runner 会按 allowed_modes 过滤任务，当前 manifest 是 protocol=38、text=23，而报告也提示 aggregate 混合 internal regression、communication、state_transfer、memory lanes，eval/runner.py:590、runs/
     host_goal_eval_20260610_state_transfer_refresh_api_repeat3_serial/benchmark_report.md:17、runs/host_goal_eval_20260610_state_transfer_refresh_api_repeat3_serial/benchmark_report.md:34。

  4. 任务设计仍过窄。state_transfer 只覆盖 cache/latency/session 三类 repo-local triage，且任务显式给 query/corpus_doc_ids/evidence_text/summary_hint，适合机制回归，不适合开放自然协作 claim，tasks/sample_benchmark.yaml:334。
  5. Planner 仍是固定三步 pipeline。retrieve -> execute -> summarize 在 sample task 和 planner prompt 都被强约束，说明当前是受控 pipeline runtime，不是自然开放多 Agent planning benchmark，tasks/sample_tasks.py:234、agents/sample_agents.py:989。

  ## 4. 新 benchmark 设计方案

  新设计应拆成三层，不再让一张 state_ref vs text_brief 表承担全部结论。这个方向也与本地 redesign 文档一致：docs/planning/state_transfer_benchmark_redesign_20260610.md:330。

  第一层：Mechanism Authenticity。保留 rich state_ref，目标只写“typed non-text state 被下游消费”，不写“低开销”。

  第二层：Carrier Efficiency。正式 headline 改为 text_packet_minimal vs state_packet_minimal，要求两边语义字段完全同构，只换文本载体和非文本 StateRef 载体。

  第三层：Natural Text Support。重新生成 natural_handoff_text，不得读 decision_packet.route/tool_name；只允许从 retriever evidence 和任务目标生成自由 handoff，让 executor 自己恢复 route/tool。

  ## 5. prompt redesign 原则

  文本 baseline 的 prompt 不能要求“保持同一 diagnosis”，也不能显式喂 route/tool/candidate。自然文本 baseline 应由独立 summarizer prompt 从 evidence 生成，不从 decision packet 反向口语化。

  protocol prompt 可以保留结构合同，但 text prompt 要像真实 agent handoff：目标、证据摘要、不确定性、下一步建议。parser 约束只能用于实验记录，不能让文本 agent 收到结构化字段名。

  报告 prompt 必须强制区分 carrier metrics 和 end-to-end metrics：handoff_textual_bytes/nontext_bytes 解释载体，llm_total_tokens/task_ms 解释端到端系统，不得互相替代。

  ## 6. task redesign 原则

  任务应从三类 incident 扩成多组等价 paired tasks，但不要扩大成开放世界。每个 task family 至少有 clean case、distractor case、route-ambiguous case、memory-reuse case。

  corpus_doc_ids、task_theme、reuse_tags 可以留作 benchmark 控制字段，但不能作为自然语言 prompt 的显式捷径。当前这些字段太容易把 route prior 注入任务，tasks/sample_benchmark.yaml:337。

  每条 claim 单独成包：communication 包、carrier 包、natural-text support 包、memory replay 包。每包都固定任务数、repeat、模型、序列化运行方式和报告字段，不再混用 internal regression。

  ## 8. 明确的下一步执行顺序

  1. 先改 benchmark contract，不动 state_ref 性能：把 text_brief vs state_ref 改名为 typed handoff authenticity，从 headline 移出。
  2. 再固定 carrier headline：只保留 text_packet_minimal vs state_packet_minimal 作为 state-transfer efficiency 主表，并检查字段完全同构。
  3. 然后重写 natural_handoff_text：禁止从 decision_packet 生成，改成 evidence-only natural handoff。
  4. 再重写任务包：扩大 incident family、去掉 prompt 泄漏、保留 paired design，明确 train/dev/test 或 formal/support/regression 分包。
  5. 最后才重跑 serialized API repeat benchmark，并只读 lane-local 表，不再用 aggregate 讲总胜出。

  结论：当前第一问题不是 rich state_ref overhead，而是 benchmark 对象污染。最先要改的是 baseline 与 lane contract：把 authenticity、carrier efficiency、natural-text support 分开。原因很直接：如果 text_brief 和 natural_handoff_text 都带着结构化语义泄漏，那
  么后续讨论 state_ref 开销只是在比较“载体 + 泄漏结构 + 任务先验”的混合物，无法判断非文本状态传递本身是否低开销。先修 benchmark 设计，再讨论 state_ref overhead。
