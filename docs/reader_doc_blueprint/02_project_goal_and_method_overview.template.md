# 模板 02：项目目标与整体方法总览

建议目标文件：

- `docs/reader_guide/02_project_goal_and_method_overview.md`

## 一、文档目标

这份文档回答：

1. 这个项目不是普通 workflow，它到底在解决什么系统问题。
2. StateBus 的方法由哪些核心机制组成。
3. 为什么 `memory`、中间状态、结构化传递必须一起理解。

## 二、必须使用的输入

1. `docs/reference/题目.md`
2. `README.md`
3. 当前约束与功能边界文档
4. 与整体方法有关的代码入口

## 三、建议章节结构

### 1. 赛题在问什么

要求：

1. 用中文重新解释赛题，不要直接复制原文。
2. 明确这是“系统层机制问题”，不是“谁调了几个工具”的问题。

### 2. StateBus 回答的三个核心问题

必须覆盖：

1. 低开销通信
2. 非文本中间状态传递
3. 共享记忆复用

### 3. 当前方法总览

要求：

1. 用一张总图说明方法全貌。
2. 说明为什么这不是单一模块，而是一套协作基础设施。

### 4. 为什么不是普通纯文本多 Agent

要求：

1. 解释纯文本协作的典型问题。
2. 解释 StateBus 的改进点，但不要过度宣传。

### 5. 方法的三大组成，但不要拆散

要求：

1. 结构化控制与交接
2. 中间状态与非文本传递
3. 记忆沉淀与复用

这里必须强调：

`memory` 是整体方法的一部分，不要单独写成外插模块。

### 6. 当前实现边界

要求：

1. 说明已经实现到哪。
2. 说明还没有实现或不该夸大的地方。

## 四、必须解释的术语

至少解释：

- `Plan（执行计划）`
- `StateRef（状态引用）`
- `MemoryCommit（记忆写入记录）`
- `Protocol（结构化协议路径）`
- `Text mode（纯文本协作路径）`

## 五、验收清单

1. 读者看完能知道“项目到底在做什么”。
2. 读者能理解三大问题之间的关系。
3. 不会把 memory 理解成独立外挂。
4. 文档没有被实验口径细节淹没。
