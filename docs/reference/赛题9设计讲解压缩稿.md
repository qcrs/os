# 赛题9设计讲解压缩稿

适用对象：对外讲清楚当前 `StateBus` 方案  
依据文档：`statebus_architecture_evolution_feasibility_report.md`、`statebus_architecture_and_implementation_plan.md`、`statebus_dual_plane_deep_design.md`

---

## 1. 这份方案怎么讲最清楚

这套方案最适合的讲法，不是先讲一堆模块，也不是先讲一堆开源框架，而是先抓住赛题 9 的三个核心对象：

1. **低开销通信**
2. **非文本状态传递**
3. **共享记忆复用**

所以最自然的主线是：

> 先按“三个面”讲清楚系统在传什么、怎么传、为什么这样传；再按“五个模块”讲清楚系统怎么落地。

这样讲的好处是：

- 前半段对齐赛题要求
- 后半段对齐工程实现
- 逻辑更稳，不容易散

---

## 2. 问题定义

我们想解决的不是“多 Agent 能不能串起来”，而是多 Agent 串起来之后的三个系统问题：

### 2.1 通信问题

现在很多多 Agent 协作还是靠自然语言或长 JSON 传中间结果。  
问题是：

- 消息长
- 重复上下文多
- token 开销高
- 路由和交接本身就可能消耗大量成本

### 2.2 状态传递问题

很多中间结果本来不是文本，而是：

- embedding
- 检索证据块
- hidden state
- 工具执行产物

但系统又把它们转成文本，再让下游重新解析，导致：

- 序列化和反序列化开销大
- 时延增加
- 语义损耗

### 2.3 记忆复用问题

任务执行过程中会产生很多可复用信息，例如：

- 摘要
- 证据链
- 结论
- 经验
- 策略

如果这些内容不能沉淀成统一记忆单元，那么下一次相似任务还得从头开始。

---

## 3. 核心思路

StateBus 的核心思路可以压成一句话：

> 把多 Agent 协作从“长文本搬运”改成“结构化控制面 + 非文本数据面 + 可复用记忆面”。

这三部分分别解决不同问题：

- **控制面**解决通信冗长和协议不统一
- **数据面**解决中间大状态反复文本化
- **记忆面**解决跨任务无法积累和复用

## 5. 先按三个面来讲

这是最推荐的讲法。

### 5.1 控制面：传协作骨架

控制面负责解决“谁来做、做什么、做到哪一步、结果是否有效”。

它传输的不是大段正文，而是高密度结构化语义单元。

#### 控制面传什么

| 类别 | 作用 | 典型字段 |
|---|---|---|
| 握手信息 | 让 Agent 接入系统 | `agent_id` `role` `protocol_version` |
| 能力信息 | 描述 Agent 能做什么 | `actions` `input_schema` `output_schema` |
| 任务规划 | 描述 DAG 和依赖关系 | `task_id` `steps` `depends_on` |
| 执行控制 | 发起工具调用或任务执行 | `action` `tool_name` `args` |
| 结果状态 | 标记成功、失败、心跳 | `ack` `error` `heartbeat` |
| 状态引用 | 告诉下游去哪里拿数据 | `state_ref` |

#### 控制面的关键特点

- 小而固定
- 可解析
- 可校验
- 可调度
- 不直接搬运 embedding 或大证据块

#### 控制面的核心协议字段

| 字段 | 含义 |
|---|---|
| `msg_id` | 当前消息唯一 ID |
| `trace_id` | 一次任务的全局跟踪 ID |
| `from_agent` | 发送方 |
| `to_agent` | 接收方 |
| `version` | 协议版本 |
| `action` | 当前动作类型 |
| `args` | 当前动作参数 |
| `result` | 当前动作结果 |
| `state_ref` | 当前动作引用的中间状态 |
| `ack/error` | 执行闭环状态 |

### 5.2 数据面：传真实中间状态

数据面负责解决“中间状态太重，不适合文本传”的问题。

#### 数据面传什么

| 状态类型 | 例子 | 为什么不直接走文本 |
|---|---|---|
| `EMBEDDING` | 语义向量 | 本来就是数值表示，转成文本毫无必要 |
| `DENSE_EVIDENCE` | 检索证据块 | 可能很大，重复拼进 prompt 成本高 |
| `HIDDEN_STATE` | 模型中间状态 | 只能同构消费，不适合文本化 |
| `TOOL_ARTIFACT` | 工具执行结果 blob | 二进制或结构化对象，直接引用更自然 |

#### 数据面怎么传

```text
Agent 产生中间状态
  -> 写入 shm / mmap / memfd
  -> 生成 StateRef
  -> 控制面把 StateRef 发给下游
  -> 下游按 StateRef 直接读取状态
```

#### `StateRef` 至少要包含什么

| 字段 | 含义 |
|---|---|
| `state_id` | 逻辑状态 ID |
| `kind` | 状态类型，如 `EMBEDDING` `DENSE_EVIDENCE` |
| `storage` | 存储方式，如 `SHM` `MMAP` `MEMFD` |
| `handle` | 共享状态句柄 |
| `offset` | 偏移量 |
| `length` | 状态大小 |
| `dtype` | 数据类型 |
| `shape` | 数据形状 |
| `checksum` | 完整性校验 |
| `lease_id` | 生命周期租约 |

#### 数据面的关键特点

- 控制面只传引用，不传大状态正文
- 数据面只负责对象生命周期，不懂任务语义
- 一个状态只允许单写，多方只读

### 5.3 记忆面：传跨任务可复用知识

记忆面负责解决“任务做完就忘”的问题。

#### 记忆面传什么

| 记忆内容 | 含义 |
|---|---|
| 摘要 | 当前任务的压缩结论 |
| 证据链 | 支撑结论的证据引用 |
| 策略 | 下次相似任务可直接复用的经验 |
| 标签 | 方便过滤和检索 |
| embedding | 支持语义召回 |

#### 一条记忆至少有什么字段

| 字段 | 含义 |
|---|---|
| `memory_id` | 记忆唯一标识 |
| `source_agent` | 来源 Agent |
| `created_at` | 创建时间 |
| `task_theme` | 任务主题 |
| `summary` | 摘要 |
| `tags` | 标签 |
| `evidence_refs` | 证据引用 |
| `embedding_state_id` | 对应 embedding 的状态引用 |
| `confidence` | 记忆置信度 |

#### 记忆面的关键特点

- 不是普通日志
- 不是把全部上下文原样存库
- 目标是“可检索、可筛选、可复用”

## 6. 再按五个模块来落地

前面的“三个面”是讲清楚系统在干什么。  
后面的“五个模块”是讲清楚系统怎么做出来。

### 6.1 五个模块

```text
┌────────────────────────────────────────┐
│ 1. 多 Agent 运行时 Runtime             │
│    负责任务生命周期、DAG 调度、回滚    │
├────────────────────────────────────────┤
│ 2. 协议与调度模块 Protocol Engine      │
│    负责握手、能力发现、协议解析、路由  │
├────────────────────────────────────────┤
│ 3. 状态交换模块 StatePool              │
│    负责共享内存、StateRef、租约回收    │
├────────────────────────────────────────┤
│ 4. 共享记忆模块 Memory Store           │
│    负责 SQLite、FAISS、MemoryQuery     │
├────────────────────────────────────────┤
│ 5. 评测模块 Eval / Telemetry           │
│    负责 text/protocol 对照和指标统计   │
└────────────────────────────────────────┘
```

### 6.2 五个模块分别做什么

| 模块 | 作用 | 对应三个面 |
|---|---|---|
| `Runtime` | 管理任务生命周期、DAG、失败恢复 | 统筹三个面 |
| `Protocol Engine` | 管理控制帧、握手、能力发现、映射 | 控制面 |
| `StatePool` | 管理共享状态、`StateRef`、回收 | 数据面 |
| `Memory Store` | 管理共享记忆、语义检索、复用 | 记忆面 |
| `Eval/Telemetry` | 记录通信、状态、时延、复用收益 | 横跨三个面 |

## 7. 协议是怎么定义的

这部分不要讲成“我们设计了很多 message”，而要讲成“协议有三层结构”。

### 7.1 协议的三层表达

```text
第 1 层：Envelope
  负责消息包装、来源、去向、版本、追踪

第 2 层：Control Body
  负责具体动作，如 Hello / Capability / Plan / Ack

第 3 层：StateRef
  负责把重状态从文本里剥离出来，按引用传递
```

### 7.2 最外层 `Envelope`

```proto
message Envelope {
  string msg_id = 1;
  string trace_id = 2;
  string from_agent = 3;
  string to_agent = 4;
  uint64 ts_ns = 5;
  uint32 ttl_ms = 6;
  uint32 version = 7;
  oneof body {
    Hello hello = 10;
    Capability capability = 11;
    Plan plan = 12;
    CallTool call_tool = 13;
    StateRef state_ref = 14;
    MemoryCommit memory_commit = 15;
    Ack ack = 16;
    Error error = 17;
    Heartbeat heartbeat = 18;
  }
}
```

### 7.3 协议里最重要的 5 类消息

| 消息类型 | 作用 | 关键字段 |
|---|---|---|
| `Hello` | Agent 注册 | `agent_id` `role` `supported_protocols` |
| `Capability` | 能力描述 | `actions` `input_schema` `output_schema` |
| `Plan` | DAG 任务规划 | `task_id` `steps` `depends_on` |
| `StateRef` | 引用中间状态 | `state_id` `kind` `storage` `handle` |
| `MemoryCommit` | 提交共享记忆 | `memory_id` `summary` `tags` `embedding_state_id` |

### 7.4 协议工作流图

```text
Agent 启动
  -> Hello
  -> Capability
  -> Runtime 注册能力表
  -> Planner 生成 Plan
  -> Runtime 调度 PlanStep
  -> Retriever / Executor 产生 StateRef
  -> Summarizer 生成 MemoryCommit
  -> Runtime 返回 Ack / Error / Heartbeat
```

## 8. embedding 在哪里体现

这里不要把“词嵌入”讲窄了。  
更准确地讲，embedding 只是非文本中间状态的一种典型例子。

### 8.1 embedding 在系统中的三个位置

#### 位置 1：检索输入

Retriever 把日志、文档、证据片段编码成 embedding，用于：

- 相似检索
- rerank
- 证据选择

这时 embedding 主要属于数据面。

#### 位置 2：记忆写入

当一条任务经验要沉淀成记忆时，系统会为摘要或主题生成 embedding，写入向量索引。

这时 embedding 连接的是数据面和记忆面。

#### 位置 3：跨任务复用

新任务进来时，Runtime 会先生成 query embedding，然后：

```text
query embedding
  -> FAISS topK
  -> SQLite 过滤
  -> MemoryHit
  -> GraphPruning / Reuse
```

这时 embedding 用来触发记忆命中和复用。

### 8.2 更稳的表述

不要说：

> 我们的 Agent 之间主要靠词嵌入交流。

更稳的说法是：

> embedding 是系统内部用于检索、匹配和复用的一类非文本中间表示；真正进入 Agent 协作主流程的，仍然是结构化字段、状态引用和必要文本摘要。

## 10. 用一个完整例子把框架讲清楚

前面的“三个面”和“五个模块”还是偏抽象。  
真正要让别人听懂，最好的办法是拿一个完整任务，把系统一轮怎么跑、第二轮怎么复用，按时间线讲清楚。

### 10.1 例子的任务定义

我们用两个连续任务来讲。

**任务 1：**

> 在 openEuler 上，用户发现 `service-A` 启动很慢，希望系统分析根因并给出优化建议。

这个任务不是一句问答，而是一个多步骤协作任务，至少包含：

- 拆解任务
- 检索系统日志
- 检索历史资料和文档
- 执行探针或工具
- 汇总结论

**任务 2：**

> 过一会儿，用户又来分析 `service-B` 启动慢的问题，但运行环境、系统版本和故障现象很相似。

第二个任务的意义是用来说明：

- 第一轮积累的记忆到底怎么复用
- StateBus 的“共享记忆面”不是摆设

### 10.2 先看系统里有哪些参与者

| 参与者 | 角色 |
|---|---|
| `Planner Agent` | 把任务拆成 DAG |
| `Retriever Agent` | 检索日志、文档、历史案例 |
| `Executor Agent` | 运行探针、脚本或 CodeAct |
| `Summarizer Agent` | 汇总证据并生成结论 |
| `Runtime` | 调度整个任务流程 |
| `MemoryProxy` | 统一提交和检索共享记忆 |

### 10.3 在这个例子里，三个面各自负责什么

| 层面 | 在这个例子里的职责 |
|---|---|
| 控制面 | 告诉系统“谁做什么、下一步交给谁、当前结果是否可用” |
| 数据面 | 存放日志 embedding、证据块、探针产物等重状态 |
| 记忆面 | 存放第一轮任务沉淀出来的摘要、证据链、策略 |

---

### 10.4 任务 1 是怎么跑起来的

这部分要按时间顺序讲。

#### 第 0 步：Agent 先注册自己

系统启动时，不是立刻就能调度，所有 Agent 先要向 Runtime 报到。

控制面里会先出现两类消息：

```text
Planner    -> Hello(agent_id="planner-1", role="planner")
Retriever  -> Hello(agent_id="retriever-1", role="retriever")
Executor   -> Hello(agent_id="executor-1", role="executor")
Summarizer -> Hello(agent_id="summarizer-1", role="summarizer")
```

接着每个 Agent 再发自己的能力描述：

```text
Capability(
  agent_id="retriever-1",
  actions=["RETRIEVE"],
  input_schema="RetrieveInput",
  output_schema="RetrieveOutput",
  accepted_state_kinds=[],
  produced_state_kinds=["EMBEDDING", "DENSE_EVIDENCE"]
)
```

Runtime 收齐这些信息后，内部会形成一张能力表：

| Agent | 能做的动作 | 能产出的状态 |
|---|---|---|
| `planner-1` | `PLAN` | `Plan` |
| `retriever-1` | `RETRIEVE` | `EMBEDDING` `DENSE_EVIDENCE` |
| `executor-1` | `EXECUTE` | `TOOL_ARTIFACT` |
| `summarizer-1` | `SUMMARIZE` | `SUMMARY` `MEMORY_CANDIDATE` |

这一步的意义是：

- 后面 Runtime 调度时，不用再问 LLM “谁适合做这一步”
- 直接按能力表路由

#### 第 1 步：Planner 把任务拆成 DAG

用户输入：

> 请分析 `service-A` 在 openEuler 上启动慢的原因，并给出优化建议。

Planner 不会直接开始写结论，而是先把任务编译成结构化步骤。

它返回的不是一大段解释文本，而是一个 `Plan`：

```text
Plan(
  task_id="task_service_A",
  goal="分析 service-A 启动慢",
  steps=[
    {step_id="s1", action="RETRIEVE", tool="query_logs", depends_on=[]},
    {step_id="s2", action="RETRIEVE", tool="search_docs", depends_on=[]},
    {step_id="s3", action="EXECUTE",  tool="run_probe",  depends_on=["s1"]},
    {step_id="s4", action="SUMMARIZE",                 depends_on=["s1","s2","s3"]}
  ]
)
```

这时候控制面真正传输的是：

| 字段 | 示例 |
|---|---|
| `task_id` | `task_service_A` |
| `step_id` | `s1` `s2` `s3` `s4` |
| `action` | `RETRIEVE` `EXECUTE` `SUMMARIZE` |
| `tool_name` | `query_logs` `search_docs` `run_probe` |
| `depends_on` | `[]` `["s1"]` `["s1","s2","s3"]` |

这一步说明了控制面的作用：

- 把任务骨架结构化
- 把执行顺序显式化
- 让后续调度可自动完成

#### 第 2 步：Runtime 先插入一次记忆查询

在正式执行 DAG 之前，Runtime 会先问一句：

> 以前有没有处理过“服务启动慢”这类任务？

于是记忆面会触发：

```text
MemoryQuery(
  task_theme="service_start_slow",
  query_text="service-A startup slow on openEuler",
  top_k=5
)
```

如果这是第一次遇到这类问题，FAISS 和 SQLite 查不到高置信度命中，于是 Runtime 继续执行原始 DAG。

这一步说明了记忆面的作用：

- 不是任务结束后才出现
- 而是在任务开始前就有机会参与决策

#### 第 3 步：Retriever 开始干活，并产生第一个 StateRef

接下来 `s1` 和 `s2` 都是 `RETRIEVE`，而且没有依赖，所以可以并行执行。

`Retriever Agent` 做两件事：

1. 检索 `service-A` 的系统日志
2. 检索与“启动慢”相关的系统文档和历史案例

这里会产生两类中间结果：

- 日志语义表示
- 文档证据块

这些东西如果直接拼进文本，很长，也没必要。  
所以 Retriever 会把它们写入数据面状态池：

```text
state_id = "state_logs_emb_001"
kind     = "EMBEDDING"
storage  = "MEMFD"
length   = 32768
```

以及：

```text
state_id = "state_docs_evidence_001"
kind     = "DENSE_EVIDENCE"
storage  = "MEMFD"
length   = 81920
```

然后控制面只返回轻量引用：

```text
StepResult(
  step_id="s1",
  output_refs=["state_logs_emb_001", "state_docs_evidence_001"]
)
```

这一步最能说明数据面的作用：

- Retriever 产出的是重状态
- 控制面只传 `StateRef`
- 下游不用再读一大段复制出来的文本

#### 第 4 步：Executor 读取 StateRef，而不是读长文本

现在 `s3` 依赖 `s1`，所以 Runtime 把 `s3` 分发给 `Executor Agent`。

Executor 拿到的输入不是“请你阅读下面 8000 字日志”，而是：

| 输入 | 类型 |
|---|---|
| `state_logs_emb_001` | `EMBEDDING` |
| `state_docs_evidence_001` | `DENSE_EVIDENCE` |
| `tool_name=run_probe` | 控制面字段 |

如果 Executor 跑在 `nsjail` 沙箱里，Runtime 还会通过：

- `SCM_RIGHTS`
- 或只读 bind mount

把底层 `memfd` 注入沙箱。

所以 Executor 在沙箱内做的是：

```text
读取 StateRef
  -> mmap 共享状态
  -> 根据证据运行探针
  -> 生成探针执行结果
```

然后 Executor 产生新的数据面状态：

```text
state_id = "state_probe_artifact_001"
kind     = "TOOL_ARTIFACT"
storage  = "MEMFD"
length   = 24576
```

控制面仍然只看到：

```text
StepResult(
  step_id="s3",
  output_refs=["state_probe_artifact_001"]
)
```

#### 第 5 步：Summarizer 汇总所有 StateRef

现在 `s4` 的依赖都完成了，于是 Runtime 调度 `Summarizer Agent`。

它拿到的输入包括：

- `state_docs_evidence_001`
- `state_probe_artifact_001`
- 必要的短文本说明

它不会看到完整原始上下文的重复拷贝，而是只消费这些状态引用。

Summarizer 输出两类结果：

1. 面向用户的总结
2. 面向系统的记忆候选

例如：

```text
summary =
"service-A 启动慢的主要原因是磁盘初始化阶段 I/O 抖动，systemd 依赖链中多个服务串行等待，建议延迟非关键服务启动并优化磁盘预热策略。"
```

以及：

```text
memory_candidate = {
  task_theme: "service_start_slow",
  summary: "启动慢问题与 I/O 抖动和依赖链串行化相关",
  evidence_refs: ["state_docs_evidence_001", "state_probe_artifact_001"],
  tags: ["openEuler", "startup", "systemd", "io"]
}
```

#### 第 6 步：MemoryProxy 统一提交共享记忆

到这一步，记忆面才真正落库。

MemoryProxy 负责做两件事：

1. 把记忆元数据写入 SQLite
2. 把记忆对应的 embedding 写入 FAISS

记忆条目的结构可以长成这样：

| 字段 | 示例值 |
|---|---|
| `memory_id` | `mem_startup_001` |
| `source_agent` | `summarizer-1` |
| `task_theme` | `service_start_slow` |
| `summary` | `启动慢与 I/O 抖动和依赖链串行化相关` |
| `tags` | `["openEuler","startup","systemd","io"]` |
| `evidence_refs` | `["state_docs_evidence_001","state_probe_artifact_001"]` |
| `embedding_state_id` | `state_memory_emb_001` |
| `confidence` | `0.91` |

这里 embedding 的位置终于明确了：

- 它不是给另一个 Agent 当自然语言看的
- 它是给记忆检索和下次复用用的

---

### 10.5 任务 2 是怎么复用任务 1 的

现在第二个任务来了：

> 请继续分析 `service-B` 的启动慢问题，环境与前一个任务类似。

这时系统不是重新全量走一遍。

#### 第 1 步：Runtime 先做 MemoryQuery

Runtime 先根据新任务生成 query embedding：

```text
query = "service-B startup slow on openEuler"
  -> query embedding
  -> FAISS topK
  -> SQLite filter(status='active', confidence>=threshold)
```

如果命中了 `mem_startup_001`，系统就能知道：

- 历史上处理过很像的“启动慢”问题
- 有一套可复用的证据组织方式和分析策略

#### 第 2 步：GraphPruning 剪掉重复步骤

这时 Runtime 会做一个关键动作：不是直接把旧结论拿来复读，而是做编排裁剪。

例如原始 DAG 是：

```text
RETRIEVE logs
RETRIEVE docs
EXECUTE probe
SUMMARIZE
```

如果记忆命中高，而且文档和历史案例已经很稳定，就可以：

- 保留新的日志检索
- 保留新的探针执行
- 复用历史文档证据组织方式
- 跳过部分重复资料检索

于是新 DAG 可能变成：

```text
RETRIEVE new_logs
EXECUTE new_probe
SUMMARIZE with reused_strategy
```

#### 第 3 步：复用的是“结构”和“证据组织方式”，不是盲抄答案

这一步很关键。

StateBus 的复用不是：

> 上次说磁盘有问题，这次也直接说磁盘有问题。

而是：

> 上次已经证明“启动慢”类问题里，哪些证据、哪些探针、哪些步骤最有价值；这次优先复用这些结构，再对新任务做验证。

所以记忆面真正复用的是：

- 任务主题级别的经验
- 证据组织方式
- 检索策略
- 分析步骤模板

而不是直接复用最终答案。

---

### 10.6 用这个例子回头看，三个面到底是怎么工作的

#### 控制面在这个故事里做了什么

- Agent 注册自己
- Runtime 维护能力表
- Planner 输出结构化 DAG
- Runtime 按依赖调度各 step
- 各 step 返回 `StepResult`
- 整个任务有 `Ack/Error/Heartbeat`

一句话：  
**控制面决定协作骨架。**

#### 数据面在这个故事里做了什么

- Retriever 写入日志 embedding
- Retriever 写入文档证据块
- Executor 读取这些状态
- Executor 再写入探针执行产物
- Summarizer 再消费这些状态

一句话：  
**数据面承载真正的中间状态。**

#### 记忆面在这个故事里做了什么

- 任务开始前先查相似记忆
- 任务结束后沉淀摘要、证据和策略
- 下一轮任务命中后剪枝复用

一句话：  
**记忆面负责跨任务积累和复用。**

### 10.7 为什么这个例子能把框架讲清楚

因为它不是只给一个静态架构图，而是把以下关系全部跑通了：

1. 控制面怎么把任务拆开
2. 数据面怎么承载非文本中间状态
3. embedding 到底在哪里使用
4. MemoryProxy 为什么要独立存在
5. 第二个任务为什么可以比第一个任务更快

也就是说，这个例子能把前面的框架真正落到“系统如何工作”上。

## 11. 讲难点时只保留四个

后面不要再散着讲十几个难点了。  
只保留最能支撑系统性的四个。

### 11.1 协议治理

不同 Agent 的输入输出格式不一致，必须通过：

- `Hello`
- `Capability`
- `ProtocolMapper`
- `SchemaInterceptor`

统一接到标准协议上。

### 11.2 状态生命周期管理

`StateRef` 背后是共享对象，不是普通字符串 ID。  
所以必须处理：

- lease
- refcount
- checksum
- 单写多读
- 回滚回收

### 11.3 记忆一致性与复用安全

共享记忆要同时解决：

- SQLite 和 FAISS 的一致性
- 记忆命中后是否真的可以复用

所以需要：

- `pending -> active`
- outbox 单写者
- 置信度过滤
- 保留验证节点的 GraphPruning

### 11.4 沙箱与共享状态边界

CodeAct 既要隔离，又要能读共享状态。  
所以要平衡：

- `nsjail`
- namespace / cgroup
- `SCM_RIGHTS`
- read-only 映射

- `Docker / WASM`：可作为替代思路，但不是当前主路径

## 13. 最后收束的一段话

可以直接这样讲：

> 我们的重点不是做一个能聊天的多 Agent Demo，而是做一个多 Agent 协作运行时。这个运行时从三个面来解决问题：控制面把协作骨架结构化，数据面把 embedding、证据块、工具产物等中间状态从文本里剥离出来，记忆面把任务中形成的摘要、证据和策略沉淀成可复用记忆。再往工程上看，它落成运行时、协议引擎、状态池、记忆存储和评测模块五部分。这样才能真正把多 Agent 从“一次性对话协作”推进到“可调度、可传状态、可跨任务复用”的系统级机制。
