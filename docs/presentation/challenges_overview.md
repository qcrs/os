# 技术难点部分的叙事导航

这份文档用于安排技术难点部分的三页内容。它先说明三页为什么放在一起，再说明每页各自要解决什么问题、和前面亮点页怎样衔接，以及实验结果应该承担什么证明作用。

这里的“难点”指系统设计中需要作出明确取舍、并且会影响整条任务链的部分。页面不需要把所有底层实现都称为难点，也不需要把源码中的模块逐个列出来。评委看完前面的介绍和亮点后，最需要补上的认识是：这些机制怎样在一项真实的多步骤任务中接起来。

## 三页各自回答什么问题

三页按一项工作的时间顺序组织，但不把它们画成固定流水线：

| 页面 | 评委要回答的问题 | 关注对象 | 需要留下的印象 |
| --- | --- | --- | --- |
| 第一页 | 同一份资料怎样交给不同角色继续使用？ | 当前任务中的输入、角色视图和来源 | 角色拿到的是适合自己的内容，来源仍然能追溯 |
| 第二页 | 计划写出来以后，怎样把任务继续跑下去？ | 当前任务中的步骤、结果和计划变化 | Runtime 把计划变成可执行步骤，前面的结果能接到后面 |
| 第三页 | 记忆检索到了，什么时候可以真正复用？ | 当前任务和历史任务的关系 | 找到相似记录只是开始，复用要看条件，方法可以在新输入上重算 |

可以用一句话记住三页的关系：

```text
资料怎样进入角色  →  任务怎样接着执行  →  过去的工作怎样带到下一次
```

这三个问题分别落在不同的层次：

- 第一页讲**内容**。同一个 `EvidencePack` 或相关对象，角色需要的字段、格式和范围不同。
- 第二页讲**进度**。Planner 的计划只是建议，Runtime 需要把它变成步骤，接收结果，再决定后续步骤怎样走。
- 第三页讲**时间**。历史记录被找到后，Runtime 要判断它能提供参考、提供方法，还是可以在严格条件下直接恢复。

这也是三页避免重复的关键：第一张不讲重试，第二张不重复解释投影，第三张不把当前任务的步骤调度再讲一遍。

## 和前面项目介绍的关系

项目介绍应该已经回答三件事：

1. 赛题提出了通信开销、中间状态和共享记忆的问题；
2. StateBus 由 Planner、Retriever、Executor、Summarizer 和 Runtime 组成；
3. Runtime 负责让角色共同完成一项多步骤任务。

技术难点部分不再重新画一张架构图，也不再逐个介绍 Agent。它要把“Runtime 负责协作”拆成三个评委能直接追问的问题：输入怎么给，步骤怎么接，历史怎么用。

介绍部分讲的是系统为什么存在；亮点部分讲的是协议、State、DSL/CodeAct 和 Memory 各自提供了什么能力；难点部分讲这些能力放到任务里之后，哪些地方需要 Runtime 作出具体判断和组织。

可以用下面的过渡语进入难点部分：

> 前面的亮点说明了 StateBus 能传什么、怎么执行、怎样保存结果。把这些机制放进一项多步骤任务后，还要处理三个实际问题：不同角色需要不同输入，计划执行过程中会产生新的结果和变化，历史记录找到以后也不能直接当成本轮答案。下面分别看这三个问题。

## 和亮点页的边界

### 第一页与结构化协议、Embedding 的关系

结构化协议页回答“请求里怎样表示动作、输入引用和输出合同”。Embedding 页回答“向量怎样被生成、传递、消费，再回到证据”。技术难点第一页回答更具体的任务问题：**这些对象进入不同角色以后，角色实际看到什么，来源怎样保留。**

页面重点是角色输入和证据来源，不重复协议字段表，也不把向量选择过程重新讲一遍。

### 第二页与 Runtime 架构、DSL/CodeAct 的关系

Runtime 架构图回答“系统由哪些部分组成”。DSL/CodeAct 页回答“Executor 有哪些执行路径”。技术难点第二页回答：**Planner 提出的步骤怎样变成可执行计划，某一步发生变化后，后续步骤怎样继续。**

页面重点是计划、步骤和结果之间的关系，不展开沙箱、Protobuf 或每个能力的实现细节。

### 第三页与 Memory 亮点页的关系

Memory 亮点页回答“怎样保存、检索和复用记忆”。技术难点第三页把问题再推进一步：**候选已经被检索出来以后，什么条件允许它进入当前步骤，复用的到底是答案、方法还是参考信息。**

页面重点是“检索结果如何变成实际使用”，不把 RRF 或存储文件名当成主角。

## 三页各自应该展示什么

三页都应遵循同一个展示顺序：先给出评委能理解的问题，再给出 StateBus 的处理选择，最后给出一条实现证据。页面主图只承担一个重点。

### 第一页：输入按角色整理

主图可以是同一份证据分成三种角色输入：

```text
EvidencePack
    ├── Retriever：候选范围和检索线索
    ├── Executor：可计算字段、数据行和来源定位
    └── Summarizer：已验证结果、证据定位和引用关系
```

图的中心不是“裁剪得更少”，而是“每个角色拿到能完成自己工作的输入，同时仍能回到原始来源”。

### 第二页：计划变成可执行任务

主图可以采用三个状态：

```text
PlanProposal
    ↓ Runtime 绑定能力、依赖、输入和输出合同
ApprovedPlan
    ↓ 执行一个个 attempt
已完成步骤 + 未执行步骤
    ↓ 某一步失败时只调整未执行部分
继续后续任务
```

页面要让评委看到 Runtime 在做实际组织工作：它检查计划是否能接入现有能力，确认前一步结果符合后一步要求，并在变化发生时保留已完成部分。

### 第三页：记忆从候选变成复用

主图可以采用下面的结构：

```text
历史记录
    ↓ 关键词 / 标签 / 语义检索
候选 Memory
    ↓ 任务条件、输入、输出合同和版本匹配
ASSIST / VALIDATED_REPLAY / REJECT
    ↓
目标角色实际读取
```

页面要让评委区分“搜到了”和“用上了”。最有力的例子是复用已验证的 execution recipe，在本轮输入上重新执行并生成新的 Artifact。

## 证据怎样分配

实验和源码证据要各自回答对应问题，避免把所有数字堆在难点部分。

| 要证明的内容 | 合适的证据 | 讲述边界 |
| --- | --- | --- |
| 角色输入可以按用途整理，并保留来源 | `RoleHydratedSlice`、`EvidenceProjectionAdapter`、证据 locator 和 lineage 记录 | 说明输入怎样组织，不声称所有角色收到同一份数据 |
| 多角色、多步骤主线能够跑通 | mainline 的 `48/48` 通过，以及配对任务记录 | 证明主流程可运行，不声称每个任务都触发重规划 |
| 计划变化后可以保留已完成部分 | `test_driver_replan_changes_only_unexecuted_subgraph` | 说明一次具体的重规划行为，不把集成测试扩大成所有场景的性能结论 |
| Memory 候选可以实际进入复用路径 | Memory-on/off 对照、`validated replay` 消费记录 | 区分 candidate hit、actual consumption 和 validated replay |
| 跨任务复用带来实际变化 | 逐任务 token、请求数、端到端时间和 recipe 使用记录 | 只引用当前实验中有记录的复用，不把所有命中都算成收益 |

难点页不承担完整性能结论。消息数、文本 token、状态字节、时延和总体收益放在测试部分集中比较；难点页只在需要时放一条最能说明问题的结果。

## 不应把三页串成的内容

三页之间有顺序，但不是每个任务都必须完整经过三页：

- 角色投影是输入组织方式，不要求所有中间状态都先经过 Embedding；
- 计划推进是 Runtime 的任务控制问题，不等于 Logit retry，也不等于 CodeAct fallback；
- Memory 可以在任务开始时提供 assist，也可以在步骤中提供 recipe，任务结束后才写入新的记忆；
- Embedding、Logit、KV 和 APC 仍按各自适用场景放在亮点部分，不能为了连接三页而画成一条固定流水线。

## 三页最后的共同认识

评委看完这部分，应当能把 StateBus 理解成一套真正组织任务的运行时：它把资料整理成不同角色能用的输入，把 Planner 的计划变成可推进的步骤，再把经过验证的工作带到下一次任务。

这比“系统有投影、重规划和 Memory 三个模块”更具体，也能直接对应赛题要求的多 Agent Runtime、复杂多步骤任务和跨任务记忆复用。
