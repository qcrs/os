# 项目介绍：前两页工作稿

这份文档只固定项目介绍的前两页。项目介绍总共准备三页：前两页说明为什么做、怎样设计；第三页再用一张简化的架构图说明这些角色和对象怎样落到系统中。架构图的具体画法另行确定。

介绍部分不使用财务、运营或报告等具体业务场景。赛题本身已经给出了足够清楚的观看框架：多 Agent 分工完成复杂任务，问题集中在通信、状态传递和跨任务复用。具体场景留给后面的 Embedding、Logit、KV 等页面，用来解释各机制适合解决什么问题。

两页的主线只有一个：**多 Agent 分工以后，前一步已经完成的工作怎样被后一步接着使用。**

## 第 1 页：多 Agent 分工以后，工作怎样接着做下去？

### 这一页的中心

多 Agent 把规划、检索、执行、总结分给不同角色以后，真正的系统问题出现在角色交接处：前一个角色做出的工作，怎样完整、低成本地交给下一个角色继续用？

这页先不讲 StateBus 的组件，也不放架构图。先让评委理解赛题为什么同时要求结构化通信、非文本状态和共享记忆。三项要求对应一次协作中的三种重复：交接时重复写，处理中重复转换，下一次任务重复做。

### 页面标题和中心句

**标题：**

> 多 Agent 分工以后，工作怎样接着做下去？

**标题下的一句话：**

> 分工解决了“谁来做”，交接决定了“前一步能不能被后一步继续使用”。

这句话把注意力从 Agent 数量带到赛题的系统层问题。它没有承诺任何具体性能数字，数字放在测试部分回答。

### 页面上展示的三个问题

页面主体使用三个并列区域，按“当前交接 → 当前处理 → 下一次任务”的顺序排列。每个区域都写清楚发生了什么，不写空泛的“效率低”或“信息孤岛”。

#### 1. 同一批内容反复写进消息

可以放一段很短的示意：

```text
Retriever → 一段资料说明 → Executor
Executor  → 重新组织后的资料 → Summarizer
```

旁边写三句话：

- 交接消息同时装着任务说明、资料和结果；
- 下游要从消息里重新找出自己需要的部分；
- 同一份资料在多步任务中可能被重复写入和解析。

这里的“文本”指承担交接的长段内容。文本仍然适合表达任务目标和结论，但当它同时装着指令、数据和结果时，每个角色都要重新找内容、重新理解一遍。

#### 2. 已经形成的状态要绕一圈才能交给下游

可以放一个简单的往返关系：

```text
向量 / 概率 / 模型计算状态
          ↓ 转成文本
       下游再解析
          ↓
      重新形成状态
```

旁边写：

- 上游已经算出的中间表示不能直接按原形式继续使用；
- 先转成文本会增加编解码和模型处理；
- 数值选择结果还需要回到原始证据，才能继续完成任务。

这里先提出问题，不在本页解释 Embedding、Logit、KV 的具体用法。后面的非文本专题分别说明它们在什么位置产生、怎样传递、谁来消费。

#### 3. 下一次遇到相似任务，还要从头组织

可以放一条时间线：

```text
任务 A：检索 → 处理 → 形成结果和方法
任务 B：相似输入 → 再检索 → 再生成同一类处理方法
```

旁边写：

- 一次任务中形成的证据、结果和处理方法没有被整理成可查找的记录；
- 后续任务即使目标相近，也很难直接找到上次留下的工作；
- 复用的对象必须和当前任务的输入、输出要求相符，不能把旧答案直接当成新答案。

这一块自然引出共享记忆，但不在这里展开检索排序或写入格式。

### 三个问题与赛题的关系

页面底部可用一行小字把三个问题对应到赛题要求：

```text
反复写入消息       → 结构化通信与通信开销
中间状态反复转换   → 非文本状态的生成、传递、接收和使用
相似任务重新开始   → 共享记忆的保存、检索和跨任务复用
```

这不是要求清单，而是说明后面为什么要讲这三类机制。赛题要求的多角色、多步骤任务和连续任务，会在第三页架构图及测试部分具体体现。

### 这一页不要放什么

- 不放 `Protobuf`、`UDS`、`shared memory` 等实现名词；评委还没有看到 StateBus 的设计，先讲通道会把注意力带到零件上。
- 不放 `SemanticStateRef`、`LogitStateRef` 或 `EngineLocalKVHandle` 字段；这些字段需要在对应亮点页解释。
- 不放通信 token、时延或命中率数字；此时只提出问题，测试页再给同条件对照。
- 不引入具体行业故事；过早绑定业务会让评委把系统理解成某一类应用。

### 这一页的讲解顺序

可以按下面的口头顺序讲，控制在一分钟左右：

> 赛题要求多 Agent 分工完成复杂任务。分工以后，难点集中在交接：检索结果交给执行角色，执行结果交给总结角色，下一次任务还可能需要以前的工作。现有做法常把指令、资料和结果一起写进消息，下游再从长文本里重新解析；向量、概率等中间表示也常常要先转成文本才能继续；任务做完以后，证据和方法又很难留给下一次任务。这三件事分别造成重复传递、重复转换和重复组织。下面介绍 StateBus 怎样把这三个问题接到同一个运行时中解决。

### 这一页的记忆点

评委最后应当留下这句话：

> 多 Agent 的难点不只在于把角色分开，还在于让前一步的工作能够被后一步和下一次任务继续使用。

## 第 2 页：StateBus 怎样把一项任务接起来？

### 这一页的中心

第 1 页提出了三个问题，第 2 页不再重复问题，而是说明 StateBus 的设计选择。核心是：**任务由 Runtime 组织，指令、输入对象、执行结果和历史记录各自有明确的承载方式，最后仍然回到同一项任务的步骤衔接中。**

这里的 Runtime 要讲得具体。它接收任务和计划，安排步骤；根据当前角色组织输入；接收执行结果并决定后续步骤如何继续。它承担的是任务连接工作，业务判断仍由相应的 Agent 和执行能力完成。

### 页面标题和中心句

**标题：**

> StateBus 怎样把一项任务接起来？

**标题下的一句话：**

> 每一步都说明做什么、用什么输入、产出什么结果，Runtime 负责把这些步骤接到一起。

这句话是整页的判断标准。后面所有对象和机制都要能回答“这一步做什么、拿什么做、结果给谁”。

### 页面主体：四个设计选择

页面可以用四个并列区域。每个区域对应第 1 页的一个具体问题，写法保持“问题 → 做法 → 评委看到的结果”。四个区域不代表所有任务都按四步固定执行，它们是四种协作需要。

#### 1. 先把任务交接说清楚

**解决第 1 页的问题：消息里混在一起，接收方要自己猜。**

StateBus 的一次请求至少明确四件事：

```text
做什么       operation
使用什么     input_refs / state_refs / artifact_refs
交给谁做     role / capability
产出什么     output_contract
```

Planner 提出的计划会被 Runtime 对照已登记的能力整理成可执行步骤。实际请求中，动作、参数、输入引用和输出要求各有位置；执行完成后，结果带着状态和结果引用回到 Runtime，再进入后续步骤。

这一块先让评委知道“协议约定了协作内容和交接顺序”。具体的 `CapabilityRegistry`、`ExecRequest`、ACK 和结果事件放到结构化协议亮点页。

#### 2. 数据和指令分开保存，角色按需取用

**解决第 1 页的问题：每个角色都收到一整段重复材料。**

资料、非文本状态和执行产物保存为可引用对象。消息携带引用和当前步骤需要的参数，较大的内容留在对应的状态载体或 workspace 中。Runtime 根据接收角色组织输入：

```text
同一个任务对象
  ├─ Retriever：检索范围和候选资料
  ├─ Executor ：可计算字段、证据定位和操作要求
  └─ Summarizer：已验证结果及其来源
```

这里要说清楚“引用”实际解决了什么：它让消息不必反复携带完整对象，同时保留对象的身份和来源；需要送进模型的内容仍会被整理成该角色能直接使用的输入。

这一块是后面结构化协议页和技术难点“同一份资料怎样交给不同角色继续使用”的共同入口。投影的字段和证据回溯留在后续页面。

#### 3. 按任务需要选择执行方式，并留下结果

**解决第 1 页的问题：执行过程产生的结果没有稳定的交付形式。**

Executor 处理输入时，能用已登记的确定性操作就走 DSL；需要开放式数据处理时才使用受限 CodeAct。两条路径都要交付可被后续步骤读取的 Artifact，并带有输出格式和来源关系。

```text
已登记的变换       → DSL
需要编写程序       → 受限 CodeAct
两条路径的共同出口 → Artifact
```

这页不展示代码或沙箱细节，只说明执行结果不再依靠一段自由文本交接。DSL 和 CodeAct 的选择及实现，在亮点页单独解释。

#### 4. 把可以留下的结果和方法交给下一次任务

**解决第 1 页的问题：每次相似任务都重新组织。**

任务完成后，系统可以保存带来源的结果、证据关系和处理方法。后续任务先检索历史记录，再根据当前任务的输入、输出合同和数据条件判断是否复用。Memory 保存的是可查找的工作记录，复用仍由当前任务决定。

```text
本次任务：结果 + 来源 + 处理方法
                     ↓ 保存
后续任务：检索 → 检查是否适用 → 复用或重新处理
```

这一块只说明 Memory 如何接回任务时间线。三类记忆、检索排序、recipe 复用和拒绝条件放到 Memory 亮点页。

### Runtime 在这一页要讲清楚的三件事

四个设计选择由 Runtime 接起来。页面中可以在四个区域下方放一条横向说明：

```text
Runtime：安排步骤  |  组织角色输入  |  接收结果并连接后续步骤
```

每件事都对应具体动作：

1. **安排步骤**：Planner 先提出计划，Runtime 按能力目录和步骤依赖形成可执行任务，再把任务交给 Retriever、Executor、Summarizer 等角色。
2. **组织输入**：Runtime 读取当前步骤的引用，根据角色和输入合同形成实际输入；同一份证据不要求每个角色看到完全相同的内容。
3. **连接结果**：Runtime 接收执行回执和结果引用，检查它们是否满足后续步骤需要，再把可用结果接下去；已完成的结果可以保留给后续步骤或记忆写回。

这里不展开授权、清理和异常策略。技术难点部分会说明“计划写出来以后怎样把任务继续跑下去”，亮点部分会说明协议字段和实际对象如何实现这三件事。

### 这一页怎样回应赛题

页面底部可以保留一条简短映射，不做功能清单：

| 赛题期待看到的内容 | 本页对应的设计 |
| --- | --- |
| 至少三个 Agent、复杂多步骤任务 | Runtime 按计划连接 Planner、Retriever、Executor、Summarizer 的不同职责 |
| 动作、参数、结果、能力与协议映射 | 一次请求说明 operation、输入引用、role/capability 和 output contract |
| 非文本状态的生成、传递、接收和使用 | 状态作为可引用对象，由产生它的角色发布、由下游按需消费 |
| 共享记忆和连续任务 | 任务结果、来源和方法进入 Memory，后续任务先检索再判断复用 |
| 纯文本与结构化协作对照 | 结构化交接成为主流程，效果放到测试页用同条件对照证明 |

这张表只作为讲稿核对，不建议在 PPT 中完整呈现。PPT 页面应该让评委先看懂设计，再在测试部分看到数据。

### 这一页可以出现的技术名词

页面正文最多出现下面这些词，并且都要有动作对应：

- `Runtime`：安排步骤、组织输入、连接结果；
- `Ref`：指向已保存的输入、状态或产物；
- `Artifact`：Executor 交付给后续步骤的文件、表格或计算结果；
- `Memory`：后续任务可以检索的结果、来源和处理方法。

`Protobuf`、`UDS`、`shared memory`、`mmap/CAS`、`CapabilityGrant`、`SemanticStateRef` 等实现名词放到后面的亮点页。它们在这里出现只会打断设计选择的理解。

### 这一页的讲解顺序

可以这样讲：

> 前一页提出了交接中的三个问题。StateBus 的处理方式先从任务本身开始：请求明确要做什么、使用什么输入、由哪个能力完成、结果按什么格式交付。资料、状态和产物单独保存，消息只带引用；Runtime 根据当前角色整理实际输入。Executor 能用固定操作时走 DSL，需要写程序时再使用受限 CodeAct，两条路径都交付统一的 Artifact。任务结束以后，结果、来源和处理方法可以进入 Memory，下一次任务先检索，再判断是否适用。Runtime 负责把计划、输入和结果接回步骤中。

最后用一句话收束：

> StateBus 关注的是一项工作怎样从一个角色交到下一个角色，并在后续任务中继续用起来。

### 这一页的记忆点

评委最后应当留下这句话：

> StateBus 把一项任务中的步骤、输入、结果和历史记录分开处理，再由 Runtime 把它们接回同一条任务链。

这句话给第三页架构图留出空间：架构图只需要把这条任务链中的角色、Runtime 和对象位置画清楚。

## 两页之间怎样衔接

第 1 页结束时，评委已经知道为什么需要改变交接方式；第 2 页开始直接给出设计选择，不再重新讲赛题背景。

建议的过渡句是：

> 问题已经明确：消息在重复搬运，状态在反复转换，任务做完以后工作又散掉。StateBus 的设计从一次交接开始，把动作、输入、结果和历史复用分开安排，再由 Runtime 负责把每一步接起来。

第 2 页结束后，再进入架构图：

> 上面讲的是设计关系，下一页把它放回系统中：哪些角色参与，Runtime 位于哪里，消息、状态、产物和记忆分别放在哪里。

架构图之后直接进入亮点总览或结构化协议页。亮点部分不要再回头解释“为什么有四个角色”，而是按下面四个具体问题展开：

```text
交接时要传什么？       → 结构化协议
中间状态怎样继续使用？ → Embedding / Logit / KV / APC
输入拿到以后怎样处理？ → DSL / CodeAct
以前做过的工作怎样复用？ → Memory
```

这四个问题是后续页面的阅读顺序，不表示每个任务都会依次启用全部机制。

## 事实核对

本稿中的系统事实按当前实现使用，讲解时需要保持以下边界：

- StateBus 支持 Planner、Retriever、Executor、Summarizer 等角色，但一次任务是否调用全部角色由任务计划决定；
- `Ref` 只表示对象的可定位引用，实际输入仍需按角色投影成模型或程序能够使用的形式；
- 控制消息可以经由 typed Protobuf 和 UDS 跨进程传递，当前系统也存在进程内 typed object 路径，不能说所有角色都通过 UDS 连接；
- shared memory、mmap/CAS 和 workspace 承载不同类型的状态与产物，介绍页只说明“对象与消息分开”，具体载体留到亮点页；
- Embedding 选择后仍需通过 manifest 回到原始证据，Logit 表示候选选择依据，显式 KV 在同一 vLLM Worker 范围内复用计算，APC 属于模型服务侧缓存；
- Memory 可以保存结果、来源和 execution recipe，后续任务仍需根据当前输入和合同判断能否复用，不能说直接复制旧答案；
- 介绍页提出目标，通信开销、任务时延、状态消费和记忆复用的具体效果由实验部分给出。
