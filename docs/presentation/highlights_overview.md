# 亮点总览：同一项工作怎样被交接、处理和复用

这份文档用于确定“项目介绍”到“项目亮点”之间的过渡页。它先说明这页在整套答辩中的作用，再固定页面上的文字、结构和讲解顺序。具体协议字段、非文本状态实现、执行路径和 Memory 检索分别放到后续页面展开。

## 这页在答辩中的位置

项目介绍已经完成两件事：

1. 说明赛题关注多 Agent 协作中的通信、状态传递和共享记忆问题；
2. 通过架构图说明 Planner、Retriever、Executor、Summarizer 和 Runtime 怎样组成一次任务。

亮点部分需要换一个角度。评委已经知道系统有哪些角色，接下来要知道：**这些角色之间到底怎样接着工作，为什么需要后面的几个机制。**

因此，这一页不再放 Agent 拓扑，也不重复 Runtime 架构。它只做一个连接：把介绍中的问题转换成后续亮点要回答的四个具体问题。

可以把它理解为一张“阅读地图”：后面的每一页都回答其中一个问题。

## 这一页要传达的中心意思

多 Agent 分工以后，前一步做出的工作需要被后一步接着使用。同一项工作在协作过程中有四个实际问题：

1. 交接时，接收方怎样知道这一步做什么、使用什么、交付什么；
2. 处理中，上游已经形成的中间状态怎样交给下游继续使用；
3. 输入准备好以后，怎样用合适的执行方式完成计算；
4. 这次形成的结果和方法，怎样留给下一次相似任务。

这四个问题对应 StateBus 的四组亮点：

| 协作中的问题 | StateBus 的处理方式 | 后续展开 |
| --- | --- | --- |
| 交接时传什么 | 结构化协议描述动作、参数、输入引用、输出合同和结果回执 | 结构化通信协议 |
| 中间状态怎样继续用 | 通过 StateRef 传递不同类型的非文本状态 | Embedding、Logit、KV、APC |
| 怎样完成不同复杂度的计算 | 已登记操作走 DSL，DSL 表达不了时使用受限 CodeAct | DSL 与 CodeAct |
| 做过的工作怎样再次使用 | 检索历史结果、证据和处理方法，在新任务中复用 | Memory |

这里的四项是四个设计问题，不是每个任务都必须依次执行的固定流水线。Embedding、Logit、KV 和 APC 处理的是不同位置的状态问题；Memory 也可能在当前任务开始时被读取，在任务结束后再写入。

## 适合这一页的开场说法

介绍页的架构图讲清了谁在协作。进入亮点时可以这样过渡：

> 多 Agent 分工以后，问题不只是让每个角色完成自己的工作，还要让前一步的工作能够被后一步接上。交接时要把任务说清楚，处理中间状态要能继续使用，执行方式要覆盖从固定变换到复杂计算的不同情况，已经做过的结果和方法还要能留给下一次任务。
>
> 所以下面我们不按模块重新介绍系统，而是按四个问题展开：交接时传什么，中间状态怎样继续用，拿到输入以后怎样完成计算，以及做过的工作怎样再次使用。

这段话直接承接赛题的三个重点，又给出了亮点部分的顺序。它不需要引入具体业务场景，也不需要在这里展示实验数字。

## 页面主题和页面文字

### 标题

建议标题：

> **亮点总览：同一项工作怎样被交接、处理和复用**

标题中的三个词有明确含义：

- **交接**：Agent 之间怎样传递任务和对象；
- **处理**：中间状态怎样被选择、消费或复用，输入怎样完成计算；
- **复用**：结果和方法怎样进入后续任务。

### 标题下方的说明

建议放一行：

> 多 Agent 协作中的重复，分别发生在交接、处理中、执行和后续任务四个位置。

这句话把页面从“功能介绍”拉回“问题和设计选择”。

### 四个展示区域

每个区域都只放三层内容：一个问题、一句回答、几个机制名称。不要把四个区域写成模块名列表。

#### 第一栏：交接时传什么？

```text
动作、参数、输入引用、输出合同
由 Runtime 组织请求和结果

结构化协议
```

这栏引出下一页的能力发现、`ExecRequest`、输入投影和结果回执。Protobuf、UDS 和 IPC 不在这里展开。

#### 第二栏：中间状态怎样继续用？

```text
状态按用途选择和复用

Embedding：选证据
Logit：判断是否补充材料
KV / APC：减少长上下文的重复计算
```

这栏只解释四种机制各自解决什么问题，不展示矩阵、概率公式、KV handle 或 vLLM 参数。那些内容留给非文本 State 的专项页面。

#### 第三栏：拿到输入以后怎样完成计算？

```text
已登记的操作走 DSL
DSL 表达不了时使用受限 CodeAct

DSL / CodeAct → verified Artifact
```

这栏要让评委先看到“执行分层”和统一出口。CodeAct 的代码生成、workspace、策略检查和业务校验在后续页面展开。

#### 第四栏：做过的工作怎样再次使用？

```text
保存结果、证据和处理方法
下一次任务检索后继续使用

Memory
```

这栏引出 Memory 的读取、匹配、复用和拒绝规则。此处不放 RRF 公式、存储字段或具体命中率。

页面视觉重点按下面的顺序安排：

1. 顶部中心句，让评委知道这页在回答什么；
2. 四个问题，让评委知道后面为什么有四组亮点；
3. 机制名称，让评委知道接下来会看到哪些内容；
4. 底部承接语，把视线带到结构化协议页。

## 这页怎样回应赛题

赛题要求可以在这页自然出现，但不要列成检查清单：

- “交接时传什么”对应结构化通信和能力发现；
- “中间状态怎样继续用”对应非文本状态的生成、传递、接收和后续使用；
- “怎样完成计算”对应完整的 Executor 和 Artifact 路径，CodeAct 作为扩展能力出现；
- “怎样再次使用”对应共享记忆的保存、检索和跨任务复用。

消息次数、文本开销、状态规模、任务时延和 Memory 命中率属于测试部分，不放在过渡页。过渡页只建立问题与设计的关系，数字随后用实验回答。

## “现有通信协议”的表达边界

页面上不要说现有协议只能传文本，也不要说 JSON 天然没有结构。JSON、RPC 或其他协议都可以承载字段。StateBus 要解决的是更具体的协作过程：

- 能力怎样被发现；
- 一次请求怎样说明动作、输入和输出要求；
- 大对象怎样通过引用关联；
- Runtime 怎样根据角色组织输入；
- 结果怎样带着状态和引用进入下一步。

因此可以使用下面的表述：

> StateBus 把任务指令、对象引用、执行结果和可复用记录分开管理，再由 Runtime 把它们接起来。

这句话足以引出结构化协议，不需要在过渡页提前讲完协议细节。

## 非文本状态在这页怎样定位

非文本部分也不应被讲成“一种格式解决所有状态问题”。四种机制处理的是不同对象：

| 机制 | 这一页只需要说明的用途 | 详细内容所在页面 |
| --- | --- | --- |
| Embedding | 从候选资料中选择需要交给下游的证据 | Embedding State |
| Logit | 根据选择分布判断是否需要补充材料 | Logit State |
| KV | 在同一模型 Worker 中继续使用公共长上下文的计算结果 | KV State |
| APC | 模型服务侧利用稳定公共前缀减少重复 prefill | APC State |

Embedding、Logit 和 KV 可以统一归入“中间状态继续使用”，但不能画成固定的 Embedding → Logit → KV 流程。APC 放在 KV 旁边时，要标明它是模型服务侧专项，不是 Runtime 在 Agent 之间传递的另一种通用 StateRef。

## CodeAct 在这页怎样定位

CodeAct 负责补足执行范围。它不承担结构化协议、非文本状态或共享记忆的全部作用，也不应被描述成“模型随时写代码”。这一页只需保留下面的关系：

```text
已登记操作可以表达 → DSL
需要开放计算         → 受限 CodeAct
两条路径             → verified Artifact
```

后续 CodeAct 页面再说明：输入由 `CapabilityGrant` 授权，模型生成候选 Python，源码经过策略检查，在受控 workspace 中执行，输出经过 schema 和业务质量验证后才能成为下游可用的 Artifact。

## Memory 在这页怎样定位

Memory 把时间范围从当前任务延伸到后续任务。过渡页只需要让评委知道它保存的不只是最终答案，还包括后续任务可能需要的证据和处理方法。具体的读取时机、匹配结果、复用 recipe 和拒绝条件，留给 Memory 页面。

可以这样说：

> 当前任务形成的结果和处理方法，下一次任务可以先检索，再决定复用哪一部分。

这句话比“系统具备持续学习能力”更准确，也不会把 Memory 说成自动改变模型参数。

## 这一页不放什么

- 不放新的 Agent 架构图；介绍部分已经说明系统由哪些角色组成；
- 不放完整协议字段、Protobuf 定义或 UDS 连接图；这些属于结构化协议页；
- 不放 Embedding 矩阵、Logit 公式、KV handle 或 APC 参数；这些属于非文本专项页；
- 不放 DSL 操作清单或 CodeAct 沙箱细节；这些属于执行页；
- 不放 Memory 的 RRF、标签和存储格式；这些属于 Memory 页；
- 不放实验数字；实验部分需要用对照结果证明前面提出的问题确实得到改善。

这一页的内容越少越好，但每个词都要能指向后续的一页。它的价值在于建立顺序和关系，不在于一次讲完所有实现。

## 亮点部分的承接顺序

建议从这张过渡页进入后续内容：

1. **结构化通信协议**：先说明 Agent 之间怎样发现能力、发起请求、交接引用和返回结果；
2. **非文本 State**：再说明交接的对象不只有文本，以及不同状态怎样被生成、传递和消费；
3. **DSL 与 CodeAct**：接着说明拿到输入以后怎样完成不同复杂度的计算，并统一产生 Artifact；
4. **Memory**：最后把视野从当前任务延伸到下一次任务，说明结果和方法怎样再次被使用。

这个顺序不是说每个任务严格按四步执行。它是评委理解系统的顺序：先知道怎么交接，再知道交接什么，接着知道怎样处理，最后知道怎样留下来。

## 评委看完这一页应形成的认识

这页不需要让评委记住所有机制名称，只需要形成下面的整体判断：

> StateBus 处理的是一项工作在多 Agent 之间怎样继续走下去：交接时有明确规则，处理中间状态可以继续使用，执行方式按任务需要选择，做过的工作还能留给后续任务。

后面的结构化协议、Embedding、Logit、KV、APC、DSL、CodeAct 和 Memory，分别把这句话中的一个具体问题讲清楚。

## 讲稿参考

> 介绍部分的架构图说明了 Planner、Retriever、Executor、Summarizer 和 Runtime 怎样组成一次任务。进入亮点后，我们换一个角度看：前一步做出的工作怎样被后一步接着用。
>
> 这里有四个问题。交接时，接收方怎样知道要做什么、使用什么、交付什么？处理中，上游已经形成的状态怎样交给下游继续使用？输入准备好以后，固定操作和复杂计算怎样选择执行方式？这次形成的结果和方法，下一次任务怎样找回来？
>
> StateBus 分别用结构化协议、非文本 State、DSL 与受限 CodeAct、Memory 来回答这四个问题。它们不是一条固定流水线，而是围绕同一项工作的四种处理方式。下面先看 Agent 之间的结构化交接。
