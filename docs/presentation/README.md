# StateBus 答辩叙事导航

本目录记录答辩内容的讲法和每页的取舍。下面的 18 页是**内容页顺序**，不包含封面、目录或致谢页；页数和版式在正式制作时仍可调整。页面具体文字、图和讲解依据见各自文档；[PPT 制作建议](ppt_production_plan.md)另行说明如何使用模板。

## 这套故事讲什么

赛题让多个 Agent 分工完成连续的复杂任务，并要求说明通信、非文本状态和共享记忆是否真正起作用。我们的切入点是：**Planner、Retriever、Executor、Summarizer 分开以后，前一步找到的资料、做出的计算和形成的方法，怎样交给后一步及下一次任务继续使用？**

介绍部分先把这个问题讲清，再给出 StateBus 的整体设计和架构。亮点部分回答具体怎样交接、筛选、判断、计算与复用。难点部分回到一项任务中，解释输入、步骤和历史记录怎样真正进入执行。测试部分用同任务对照、运行记录和专项实验回答这些做法产生了什么结果。

这是一套系统的讲法，不是一条要求所有任务都依次经过 Embedding、Logit、KV、Memory、CodeAct 和 APC 的固定流水线。

答辩时可以顺着一项工作讲：Planner 提出步骤，Retriever 找资料，Executor 处理数据，Summarizer 形成结论。角色分开以后，资料和结果每交一次都可能被重新整理，下一轮相似任务还可能重做。StateBus 让 Runtime 根据能力安排步骤，用协议交代这一步的动作和输入，让证据、数值状态、执行产物各有可以继续读取的对象，再把有用的结果和方法留给下一轮。具体实现并不只有一条路径：资料多时可用 Embedding 选证据，候选拿不准时可用 Logit 决定是否补充材料，长上下文可用显式 KV 或 APC 减少重复计算，Executor 则按任务选择 DSL 或 CodeAct。讲完这些，回头回答三个追问：角色实际拿到什么，计划变化后怎样继续，历史方法何时能用。最后用同任务对照和机制记录检验整套系统。

## 项目亮点：说明我们具体怎样做

| 内容页 | 主问题和展示重心 | 评委应记住什么 | 详细文档 |
| --- | --- | --- | --- |
| 5. 结构化协议 | 从能力目录到 `ExecRequest`、角色输入投影和结果回执。用一次具体交接展示动作、输入引用和输出合同；Protobuf/UDS 作为跨进程控制路径出现。 | Runtime 能按已登记能力发起任务，并把结果接到下一步；协议约束的是这次交接怎样发生。 | [结构化协议](structured_protocol.md) |
| 6. Embedding | 候选资料多而下游只需少量证据时，Retriever 生成向量矩阵；下游进程按 Ref 读取、选择行，Runtime 通过 manifest 找回原文。 | 向量负责选，交给 Executor 的仍是有来源的证据。 | [Embedding 状态](embedding_state.md) |
| 7. Logit | 候选已缩小，但短证据可能不足。展示选择位置的候选概率、`margin` 与 `other_mass` 怎样让 Runtime 决定继续、展开材料或最终 abstain。 | 先用紧凑证据判断，拿不准时才付出完整取证成本。 | [Logit 状态](logit_state.md) |
| 8. 显式 KV | 两个角色使用相同的长 parent。对照重复 prefill 与 `EngineLocalKVHandle` continuation，标出被复用的公共计算和仍需计算的后缀。 | 同一 vLLM Worker 内，后一个角色可以沿用前一个请求的 parent KV。 | [显式 KV](kv_state.md) |
| 9. 共享记忆 | 任务完成后保存结果、来源和方法；新任务用关键词、标签、语义检索形成候选，再决定参考、在新输入上重算或拒绝。 | 检索到历史记录只是开始；最有价值的复用是把已验证的方法用于本轮数据。 | [记忆复用](memory_reuse.md) |
| 10. DSL / CodeAct | 已登记的常见变换走 DSL，表达不了的开放计算走受限 CodeAct，两条执行路径交付同一种可供下游读取的 Artifact。 | Executor 有不同执行方式，但后续角色接收的结果合同一致。 | [执行分层](codeact_execution.md) |
| 11. APC | 多个长文本请求共享材料时，Runtime 对齐实际 token 前缀，并根据 vLLM 的命中反馈调整待执行任务顺序。 | StateBus 准备可命中的请求并使用反馈调度；缓存命中由 vLLM 完成。 | [APC 专项](apc_state.md) |

第 6 至 8 页是三种**非文本中间状态**：Embedding 选择资料，Logit 判断是否补充资料，显式 KV 复用模型计算。它们的整体关系见[非文本状态定位](non_text_state.md)，这份文档供讲述者统一口径，不另做一页。第 11 页 APC 放在模型服务侧专项：它与显式 KV 都关心长文本重复计算，但实现位置和对照条件不同，不画成同一条状态传递链。

Memory 放在执行页之前，是为了先把视野从“这次如何处理”扩展到“下一次还要不要重做”；随后再回到 Executor，说明一轮任务中的 Artifact 怎样生成。讲解时不要把这两页说成固定先后发生的操作。

## 技术难点：把能力放回一项任务

前面已经展示了协议、State、Memory 和执行能力。接下来不再增加模块清单，而是回答三个运行中很具体的问题。三页分别看内容、进度和跨任务使用。

| 内容页 | 评委可能追问什么 | 这一页的重点 | 详细文档 |
| --- | --- | --- | --- |
| 12. 角色输入 | 同一份资料怎样交给不同角色继续使用？ | 展示同一份 `EvidencePack` 被组织成不同角色的输入，重点放在 Executor 可计算数据行及其来源定位。 | [角色投影与来源](challenge_projection.md) |
| 13. 任务推进 | 计划写出来以后，怎样把任务继续跑下去？ | 展示 `PlanProposal` 如何成为可调度步骤；步骤变化时，已完成结果保留，调整未执行部分。 | [Runtime 任务衔接](challenge_runtime_continuation.md) |
| 14. 记忆使用 | 记忆检索到了，什么时候可以真正复用？ | 用当前任务的输入和输出条件区分候选命中、参考历史、方法重算与拒绝。 | [记忆复用判断](challenge_memory_reuse.md) |

[难点部分导航](challenges_overview.md)解释三页如何衔接及各自的证据边界。第 12 页不重复讲协议字段，第 13 页不重讲 DSL/CodeAct 细节，第 14 页不重讲 Memory 检索算法。这样，难点部分回答的是“这些能力怎样被 Runtime 用起来”。
