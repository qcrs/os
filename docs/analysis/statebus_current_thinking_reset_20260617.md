# StateBus 当前认知收口说明

日期：`2026-06-17`

相关文档：

- `docs/review/statebus_reset_plan_from_full_scan_20260617.md`

定位：

- 这不是新的全量审计报告。
- 这也不是执行计划。
- 这份文档只回答一件事：
  - 在当前文档、代码、benchmark、历史修补已经很多的前提下，我们现在最该怎么看这个项目，最该先想清楚什么。

---

## 1. 先给结论

当前最核心的问题，不是某个 pack 的结果低，也不是某个单点 bug。

当前最核心的问题是：

**项目的解释系统已经开始比方法系统更复杂。**

换句话说：

1. 系统本体还在
2. 主骨架没有坏
3. 也确实有一些真实成立的东西
4. 但为了证明这些东西、修 fairness、修 report、修 headline、修 support surface 读法，仓库已经堆出了很重的解释层

这会直接导致一个后果：

> 你越往后修，越容易陷入“每个局部都在变好，但整体越来越说不清”的状态。

这就是现在“文档乱，所以想法也乱”的根源。

---

## 2. 现在最该看清的，不是更多细节，而是四个层次

当前仓库里的内容已经很多，但真正需要先分清的只有四层。

### 2.1 第一层：赛题真正要什么

这是最高层，不应该被任何当前实现反过来绑架。

按 `docs/reference/题目.md`，赛题真正要的是：

1. 真实多 Agent 协作系统
2. 结构化通信协议
3. 非文本中间状态传递
4. 共享记忆与复用
5. 在相同任务条件下，对比纯文本协作与结构化协作

这意味着：

- 赛题不是要你证明“所有 benchmark 上 protocol 全面更优”
- 赛题也不是要你做无限多 pack 的实验分类学
- 赛题更不是要一个无限扩张的 audit framework

赛题真正关心的是：

> 你的系统机制是否真实成立，以及这种机制在合理对象上是否比纯文本协作更有意义。

### 2.2 第二层：当前系统真实做到了什么

这层不能靠愿望判断，只能靠代码和 run 判断。

当前真实成立的东西有：

1. 4 角色主骨架成立
   - Planner / Retriever / Executor / Summarizer
2. protocol 通信与 typed-state 主链路成立
3. StatePool / StateRef 成立
4. 共享记忆与 replay 成立
5. `contest_honest_headline_v1` 作为当前最诚实的 headline 对象已经成立

这是项目当前最重要的“真实资产”。

### 2.3 第三层：当前项目没有做到什么

这层同样必须诚实。

当前没有做到的关键点有：

1. 还没有用正式 repeat=10 把当前 honest headline 彻底坐实
2. protocol 还没有在当前 headline 上表现出明确的端到端优势
3. 当前任务对象偏薄，structured handoff 优势无法复利
4. 外部 pure-text baseline 还没有形成真实正式对象
5. 一些创新点仍停留在概念、半实现或支线路径

这几条如果不先承认，后面所有讨论都会飘。

### 2.4 第四层：当前复杂性主要长在什么地方

当前复杂性不是平均分布的。

它主要长在三块：

1. benchmark surface 与读法边界
2. 文档历史链条
3. report / fairness / object-definition 修补层

也就是说，当前最重的不是系统 runtime 本身，而是“如何解释系统”的那一层。

---

## 3. 为什么你会越来越觉得自己在原地打转

这不是错觉。

原因主要有四个。

### 3.1 你现在修的很多东西，不是能力层，而是解释层

最近很多重要工作，虽然都必要，但本质上是：

1. 区分 headline 和 support surface
2. 修 pure text 对象定义
3. 修 report 语义错误
4. 修 pack 的读法边界
5. 修 object parity

这些工作不是没价值。

但它们的性质更像：

> 让项目变得更诚实、更可辩护、更不误导。

而不是：

> 直接把方法能力再往前推一大步。

所以你会感觉：

- 做了很多事
- 但“效果没明显变强”

这个感受是对的，因为你最近主要修的是解释层，不是能力层。

### 3.2 当前 benchmark 太多，主问题被拆散了

现在 benchmark 已经不是“几个实验回答一个主问题”，而是“很多 pack 分别回答局部问题”。

这样做有好处：

- 更严谨
- 更诚实
- 更能分离对象

但坏处也很明显：

- 主线叙事被拆碎
- 每个结论都要解释“它不回答什么”
- 读的人越来越难抓住真正主问题

所以你会觉得“项目像石山代码一样越堆越高”，其实不只是代码，**benchmark 和文档也在石山化**。

### 3.3 当前任务对象太薄，导致方法优势没有空间展开

这是非常关键的一点。

当前 contest headline 下，主要还是：

1. 检索
2. 选 route/tool
3. 执行
4. 总结

这类任务的 handoff 跳数很少。

于是：

- protocol 的控制面节省是真的
- 但节省只发生一跳
- StatePool / typed packet 的工程成本也是真的
- 结果就是端到端收益被抵消

所以现在“结果总是差不多”，并不自动等于方法没价值。

更准确的说法是：

> 当前对象不足以稳定放大方法差异。

### 3.4 项目已经同时承担了太多目标

当前仓库同时在处理：

1. contest headline
2. fairness repair
3. typed-state authenticity
4. memory replay proof
5. planner openness
6. external/open comparison
7. LangGraph extension
8. 历史设计愿景与创新点保留

这会让你一直处在一种状态里：

> 每一条都好像合理，但没有哪一条足够强到统一整个项目。

这就是主线感消失的原因。

---

## 4. 我现在对这个项目的中立判断

### 4.1 不是方法已经死了

我不认为当前可以下结论说：

- StateBus 方向错了
- 方法无效
- 系统应该推翻重来

因为真实成立的东西仍然不少，而且主骨架是可运行、可审计、可解释的。

### 4.2 也不是只差最后一点点

我同样不认为当前状态是：

- 再补 1-2 个 bug 就可以自然收官
- 再跑几轮 repeat 就能自动证明优势

因为问题已经不只是数据量或稳定性，而是：

- 对象设计
- 任务厚度
- 文档层级
- benchmark 收缩

### 4.3 当前最真实的诊断是：

> 项目还在，但叙事已经被过多中间层稀释了。

这句话比“代码乱”更准确。

因为代码乱还只是实现问题；
而叙事被稀释，意味着你不知道哪些东西是主线、哪些只是为了保护主线而长出来的。

---

## 5. 现在最该做的认知动作

如果只说一条，我认为当前最重要的不是继续推进，而是：

**重新建立项目的“主资产清单”。**

不是所有已经存在的东西都值得继续背在主线上。

当前至少应该强行分成四类。

### 5.1 必须保留的真实主线资产

这些是当前系统真正最有价值的部分：

1. 4 Agent 主骨架
2. protocol + typed-state 主路径
3. StatePool / StateRef
4. 共享记忆与 replay
5. `contest_honest_headline_v1`
6. `typed_state_mechanism_v3`

### 5.2 有价值但不应当承担 headline 的支线

例如：

1. `memory_dual_mode_fairness_v3`
2. `planner_support_v3`
3. `typed_state_consumer_sensitivity_v3`
4. `external_text_baseline_audit_v3`
5. open / LangGraph extension

这些东西有价值，但不能再混到“主结论”里。

### 5.3 应归档的历史负担

例如：

1. 已被替代的旧 pack
2. 已经只剩历史说明价值的执行计划
3. 不再进入主路径的中间分析文档
4. 只用于证明某一轮修补有效的历史 run 解读

### 5.4 不应继续追的复杂性

例如：

1. 再扩新的 pack
2. 再扩新的 handoff variant
3. 再为解释去加一层 report payload
4. 再把 audit surface 包装得更像正式 surface

---

## 6. 现在真正需要先想清楚的三个问题

当前不需要先想 20 个问题。

先想清楚这三个就够了。

### 6.1 我们当前最可 defend 的主 claim 到底是什么

不是“所有东西都成立”，而是：

- 当前最强、最真实、最不依赖额外解释保护的 claim 是什么

如果这条不清楚，后面所有文档都会继续膨胀。

### 6.2 我们是要证明“机制真实成立”，还是要证明“端到端明显更优”

这两者不是一回事。

当前证据更强的是前者：

- 机制成立
- object 更诚实
- typed state 真实生产/传递/消费
- replay 真实成立

而不是：

- protocol 已在当前 headline 上明显打赢 text

如果这两者不区分，项目就会一直在“为什么还没赢得更明显”里内耗。

### 6.3 当前最应该收的是 benchmark，还是 runtime，还是任务对象

我的判断是：

优先级应当是：

1. benchmark / 文档 / surface 收口
2. 报表语义修正
3. 再决定是否厚化任务对象
4. 最后才是更深层 runtime 改造

现在不适合直接再往 runtime 主逻辑里埋新复杂度。

---

## 7. 我的建议不是“推翻重来”，而是“先把项目重新说清楚”

我现在最明确的建议是：

1. 不要再急着扩新东西
2. 不要再同时追太多条线
3. 先把当前项目重新归纳成一个简短、稳定、可 defend 的认知框架

这个框架至少要能回答：

1. 我们当前主线是什么
2. 我们当前真正最强的证据是什么
3. 我们当前没有证明什么
4. 哪些东西是支线，不再混进 headline
5. 哪些历史东西应该归档

如果这个框架还没立起来，后面继续修，只会继续积累“局部越来越合理，全局越来越混乱”。

---

## 8. 最后一句话

当前最危险的，不是某个单点 bug，也不是某个 pack 指标不够漂亮。

当前最危险的是：

**项目的认知地图已经开始落后于项目本身的复杂度。**

所以现在最重要的，不是再多做一点，而是先把这个项目重新看懂。
