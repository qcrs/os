  2. 赛题拆解与重点判断

  先讲赛题，不先讲代码。

  赛题真正的评分重心是三条系统机制，不是“能不能拼一个多 Agent demo”：

  - 低开销通信
  - 非文本状态传递
  - 共享记忆复用
  - 再加一层：实验验证可信度

  必须项很明确：

  - 至少 3 个 Agent，覆盖规划/检索/执行/总结等至少 3 类角色
  - 结构化通信协议，且不能只靠自然语言长文本透传
  - text / protocol 双模式对照
  - 一种非文本中间状态传递机制，并说明生成/传递/接收/使用
  - 共享记忆模块，带元数据、检索、复用
  - 至少 2 组关联连续任务
  - 指标统计与不少于 10 轮稳定执行
  - 最终 openEuler 交付可运行

  鼓励项不是必须项：

  - IPC / Socket / 共享内存 / 向量库 / WASM / 容器 / eBPF
  - CodeAct
  - hidden state / KV 之类更强中间态

  最容易被误判的点：

  - 赛题不是工作流编排题。重点不是“把四个角色名字摆上去”。
  - 赛题也不是纯 benchmark 题。不能拿一组受控结果掩盖机制本身的僵硬。
  - 赛题没有要求开放域通用性，但也没有允许“完全预制脚手架伪装成 agent system”。

  因此，即使字面满足要求，仍可能内部不合理的地方主要有三类：

  - 多 Agent 只是角色标签，实际仍是固定受控流水线
  - 检索只是 repo-local 提示包装，不是有实质不确定性的 retrieval
  - 共享记忆只是受控 replay 复用，不是更一般的 memory assist gain

  4. 当前主线到底是什么

  真实主线不是“开放域多 Agent 平台”，也不是“交付态系统”。

  真实主线是：

  - 一个 host-side、contest-shaped、四角色语义保留的运行时原型
  - 主流程稳定收敛成 retrieve -> execute -> summarize
  - Planner 和 Summarizer 走 live LLM
  - Retriever 建立在 repo-local corpus + 向量/词法/metadata hint 的混合检索上
  - Executor 建立在 route-aware playbook/tool registry 上
  - memory 目前正式成立到 replay/step-skipping，而不是 broad assist gain

  最重要的真实性证据有两条：

  - 这不是纯文档。核心模块确实都在代码里并进入主链。
  - 这也不是开放规划系统。Planner 被严格约束成固定三步骨架，agents/sample_agents.py:715 和 agents/sample_agents.py:814 明确要求第 1 步必须 retrieve，第 2 步必须 execute，第 3 步必须 summarize。

  所以当前对象更准确的描述是：

  - 不是假的
  - 但也不自然
  - 是一个赛题化、受控、机制验证导向的 host-side runtime prototype

  5. 结构性问题审计

  有结构性问题，而且不是小问题。

  1. Planner 不是实质规划器，而是固定三步模板的 LLM 包装层。
     证据：planner prompt 直接规定三步必须固定，agents/sample_agents.py:821；解析器也强制 3 步合同，agents/sample_agents.py:715。
     这意味着“多 Agent 规划”更多是受控协议演示，不是有真实结构选择空间的 planner。

  2. 当前系统本质上仍接近受控 pipeline，而不是更一般的多 Agent runtime。
     证据：tasks/sample_tasks.py 里也有同样三步固定 plan 模板，tasks/sample_tasks.py:207。
     即使 planner 走 LLM，系统拓扑并不开放。

  3. Retriever 有真实检索，但检索对象强依赖 repo-local corpus 和预设 incident families。
     证据：tasks/local_corpus.py 的检索目标就是本地 YAML corpus，tasks/local_corpus.py:1。
     这不是伪造，但也远不是开放 retrieval。

  4. Executor 的“执行”主要是 route-to-playbook/tool selection，不是一般化 action runtime。
     证据：ToolRegistry 注册的是一组 repo-local triage playbook，runtime/executor_runtime.py:156。
     即使加入 collect_more_evidence abstain，它仍主要是受控 incident family route selection。

  5. memory 设计里最强的收益路径不是 assist，而是 exact/validated replay。
     证据：Orchestrator 直接支持 _resolve_skip_retrieve_execute / _resolve_skip_execute，runtime/orchestrator.py:584 runtime/orchestrator.py:619。
     这让系统收益更依赖“匹配到可跳步回放”而不是更一般的共享记忆辅助。

  结论：

  - 当前主链是合理的赛题原型
  - 但它不是结构上很自然的多 Agent 系统
  - 更接近“有真实机制实现的受控 pipeline runtime”

  6. 哪些地方像是在为赛题过拟合

  这一节必须直说。

  1. Planner 的存在感被过度包装了。
     它保留了“有 planner agent”的赛题外形，但真实自由度极低。

  2. state_transfer lane 的 baseline 是被刻意收窄到 text brief handoff。
     这在 benchmark 公平性上是合理修正，但也说明当前 claim 不是“结构化状态全面优于所有纯文本中间态”，而是优于一个已定义收窄 baseline，runs/
     host_goal_eval_20260608_230711_26task_api_repeat10_serial/benchmark_report.md:136。

  3. memory 主收益来自 replay contract，而 replay 条件本身相当受控。
     这更像“可验证回放系统”而不是更一般的跨任务共享记忆增强。

  4. benchmark 任务族明显围绕少数 incident families 组织。
     这有利于 requirement closure，也提高了 route/tool/memory 命中稳定性，但泛化很弱。

  5. Executor 的 tool family 与 corpus hint 是强耦合的。
     这让“检索到 route，再执行 playbook”成立得比较顺，但更像 contest-shaped prototype，不像开放系统。

  7. 哪些地方虽然满足赛题字面要求，但内部链路并不合理

  1. “有 planner”这一点字面满足了，但内部并不自然。
     固定三步硬合同意味着它并没有承担真正的 planning uncertainty。

  2. “非文本状态传递”字面满足了，但其中一部分状态是为当前执行链专门设计的 FEATURE_BUNDLE。
     它是诚实的非文本中间态，不是假装 hidden state；但它明显服务于当前 repo-local route/tool 机制，不是更通用的中间表示。

  3. “共享记忆复用”字面满足了，但目前最强收益路径是 replay-based pruning。
     这比 assist-style memory 更像 workflow replay optimization，不像更通用的 memory intelligence。

  4. “Retriever”字面满足了，但它更多是在 repo-local 证据包里做 route disambiguation。
     这不是假的 retrieval，但检索问题被预设得很窄。

  5. “Executor 支持工具执行”字面满足了，但执行本体主要是预制 playbook 分发。
     其通用执行含量有限。

  8. 当前优化收益是否足够

  先说结论：收益有，但不均匀。通信和状态传递的收益足够可辩护；memory 的 broad headline 不够。

  1. communication 收益是成立的。
     正式 repeat=10 包中，protocol 相对 text：

  - control bytes 5832.70 -> 4986.00
  - tokens 1138.80 -> 747.40
  - task ms 4705.14 -> 3577.55
    依据：runs/host_goal_eval_20260608_230711_26task_api_repeat10_serial/benchmark_report.md:123

  2. state_transfer 收益也成立，但边界必须带上。
     正式 repeat=10 包中：

  - text handoff_nontext_bytes = 0
  - protocol handoff_nontext_bytes = 1704.67
  - 同时 tokens 和 task ms 下降
    依据同上，runs/host_goal_eval_20260608_230711_26task_api_repeat10_serial/benchmark_report.md:123

  3. assist_only 仍然不够。
     这是当前最关键的负面结论。
     repeat=10 formal 包中：

  - text: memory_off 4513.23, assist_only 4583.21
  - protocol: memory_off 3487.28, assist_only 3530.00
    即 assist_only 都更慢。
    依据：runs/host_goal_eval_20260608_230711_26task_api_repeat10_serial/benchmark_report.md:148

  4. replay_enabled 的收益是真实、稳定、可辩护的。
     同包中：

  - text 4046.16
  - protocol 3312.57
    并且 skipped_step_count = 1.43, reuse_gain = 0.48。
    这说明当前 memory 真正强的是 step-skipping replay，不是 assist memory。

  5. 为什么 assist_only 到现在仍然有问题。
     因为它增加了 memory lookup 和 prior 处理，但没有带来跳步；当前系统里的 assist 更像 route/tool narrowing diagnostics，而不是端到端成本收益器。

  6. 当前继续追 assist_only headline 不值得。
     因为正式证据已经连续说明它不优于 memory_off。再追很容易变成“为了赛题 claim 继续调 benchmark”。

  9. 当前系统是否仍然有意义

  有意义，但意义必须降级描述。

  最诚实的定位不是“接近通用多 Agent 平台”，而是：

  - 一个诚实的赛题化 host-side prototype
  - 一个包含真实协议、状态池、memory、评测链的系统原型
  - 但结构上已经有明显特化，继续投入的边际价值取决于你是否接受“先去特化，再谈深化”

  如果不考虑交赛题，它仍然有保留价值的技术含量主要在：

  - 结构化 control plane 的真实实现
  - StateRef + mmap/shared_memory 的 host-side 数据面
  - SQLite + FAISS + replay contract 的 memory pipeline
  - benchmark/report 证据层做得比较清楚

  但如果问“它现在是不是一个值得继续包装成更强通用系统的东西”，答案偏保守：

  - 目前还不是
  - 先去特化，否则继续包装收益不高

  10. 当前最重要的后续问题

  只保留最关键的问题。

  1. 要先决定是否接受“它现在主要是 contest-shaped prototype”这一定位。
     如果不接受，后续所有 benchmark 优化都会变成自欺。

  2. 最该处理的不是再抠 assist_only，而是去特化 Planner/Retriever/Executor 之间的关系。
     尤其是 planner 的伪自由度和 executor 的预制 playbook 依赖。

  3. benchmark 证据层虽然已经比以前干净，但仍不能把 replay gain 讲成 broad memory gain。
     这条边界必须继续守住。

  4. openEuler 交付、强沙箱、Docker 终态都还没闭环。
     这些现在不该拿来给当前主线加光环，但最终交付前也绕不过去。

  11. 最终判断

  直接说结论。

  - 当前技术上是相对诚实的。它不是 design-only，也不是纯 benchmark 造景；关键机制在代码里真实存在并跑进主链。
  - 当前系统主要仍是赛题化原型，不是开放域通用多 Agent runtime。
  - 当前值得继续推进，但前提不是继续包装 memory assist headline，而是先承认它的受控性、再做去特化。
  - 当前最应该停掉的是：
      - 把 assist_only 当成正式收益 headline
      - 把固定三步受控链路包装成“自由多 Agent 规划”
      - 把 repo-local incident-family route/playbook 说成更一般的 retrieval/execution intelligence

  - 当前最应该继续的是：
      - 保留 communication / state_transfer 这两条已成立的机制证据
      - 把 replay-enabled memory 明确限定为 replay/step-skipping gain
      - 优先审 Planner -> Retriever -> Executor 的真实性和去特化空间，而不是再堆一轮漂亮 benchmark

  整体一句话：

  > 这是一个已经实现主骨架、证据层也基本诚实的 host-side contest prototype；它有技术含量，但当前最明显的问题不是“没实现”，而是“结构仍然过于受控和赛题化”，继续推进前应先停止包装、先做真实性与去特
  > 化判断。
